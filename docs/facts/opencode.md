# OpenCode facts

What Nushi depends on, as seen when it was built against the versions named below. Read it before changing the code that talks to it.

## Agent facts (opencode 2.2.6)

What the code depends on (`internal/opencode*`), from driving Homebrew's `opencode` 2.2.6 on macOS on 2026-11-10 in a throwaway `HOME`, its turns against a fake model on localhost (a provider in its config; the adapter is bundled, nothing downloaded), and from its source (anomalyco/opencode, v2.2.6). "Seen" was run; "read" is its source, not run. Each heading says which, and a line says so where it differs.

**Start and version (seen)**
- `opencode acp` speaks ACP as JSON lines on stdio. It starts a server child of its own, `opencode serve --stdio --port 0`, in its own process group (127.0.0.1, a random port and password), and no background service. stderr is empty by default; its log is `log/opencode.log` in its data folder.
- `opencode --version` prints `opencode v2.2.6` and exits 0. Only its TUI checks for updates; `acp` doesn't (read).
- opencode 1 (npm's `opencode-ai`, 1.19.x) was neither installed nor run, so what its ACP does isn't known here; Nushi asks for 2.0.0 (`opencode.Min`). 2 takes over 1's sessions and sign-ins in the same data folder (read).

**initialize (seen)**
- `protocolVersion` 1, `agentInfo` `OpenCode` 2.2.6, `loadSession`, `sessionCapabilities` additionalDirectories, close, delete, fork, list and resume, `promptCapabilities` embeddedContext and image, `mcpCapabilities` http (no sse), one auth method (`opencode-login`: "Run `opencode auth login` in the terminal"), `_meta` `opencode/child-session-updates`. The answer is the same whatever the client declares.
- Of the client's capabilities it reads `elicitation.form`, `session.compaction` and `_meta["opencode/child-session-updates"]` (read); `fs` and `terminal` never: it reads and writes files and runs commands itself.
- Nothing tells signed in from not: a fresh `HOME` has a built-in `opencode` provider with free hosted models (the default `opencode/big-pickle`), so initialize and `session/new` succeed, while `opencode auth list` prints "No authenticated integrations" (the listing was seen; no prompt went to those models). With no model at all `session/new` fails after about 5 s, `-32603` "No models are available". A provider's 401 fails the prompt with `-32000` "Authentication required".

**Sessions (seen)**
- `session/new` (an absolute `cwd`, which needn't be in git; `mcpServers` required) answers `sessionId` (`ses_…`) and `configOptions`, with no legacy `modes` or `models`: `model` (`<provider>/<model>`), `effort` (category `thought_level`, only for a model with variants: its levels and `default`) and `mode` (`build`, the default, and `plan`). Then `available_commands_update`, and on a cold process one `config_option_update` with the model list grown.
- `session/set_config_option` answers with the whole list and `session/set_mode` with `{}`; neither sends an update. A model's value may carry an effort (`…/max`), and a new model puts the effort back to `default`. There's no `session/set_model`. All three are kept with the session and come back on load, resume and fork; a new session starts from the defaults.
- `plan` isn't read-only: write and edit fail outside opencode's plan folder, but shell runs unasked and can write files. So Nushi counts no mode of its as read-only.
- `session/list` (params required): `{sessionId, cwd, title, updatedAt}`, newest created first, 100 a page, `cwd` matched as the exact string. Every page with sessions has a `nextCursor`; the end is an empty page. A session is listed from `session/new` on, titled `New session - <time>` until it has a title. `session/close` by the process that made it removes one never prompted (2.2.6's changelog); input closing doesn't. A subagent's session is listed too, with nothing to tell it by.
- `session/load` replays the whole history before it answers: user messages, thoughts, agent messages, tool calls (pending, then one update) and a compaction (`session_info_update`), without times. `session/resume` replays nothing. Both answer `configOptions`, then send the commands.
- Errors, the same for load, resume and fork: an unknown id is `-32602` "Invalid params: session not found: <id>", not `-32002` (`Harness.Gone` reads it); a `cwd` other than the session's, a subfolder too, is `-32602` "session <id> does not belong to cwd".
- `session/fork` copies the whole session and its options, titled "<title> (fork #1)", with new message ids. It has no fork at a message (read: `_meta.messageId` is ignored), so nothing to rewind with. `session/close` answers `{}`; `session/delete` answers `{}` and deletes (gone from the list; load says not found).
- No title ever reaches the client. opencode writes one with a model request of its own, and `session/list` has it, but it sends `session_info_update` only for a retry and a compaction (read).
- Every session of a `HOME` is in one SQLite file, `opencode.db` in the data folder (WAL, 0600), which holds the sign-ins too. Nushi never opens it. Nothing locks a session: two `opencode acp` processes loaded one with no error, and neither heard of the other's changes (prompts from both weren't run).
- In a terminal, `opencode --session <id>` (or `-s`) opens a session from any folder (seen through a pty); without `--standalone` it starts or uses opencode's background service (read).

**Turns (seen)**
- A turn sends no echo of the user's message; then `agent_thought_chunk`, `agent_message_chunk` (a `messageId` per model step, text in batches of about 0.17 s) and `usage_update` (`used` the last step's tokens, `size` the model's context, `cost` so far); the result has `usage`. A prompt during a turn is refused at once, `-32603` "Session already has an active ACP prompt": no queue, no steering. `session/cancel` ends a turn `cancelled` within tens of ms, a running shell command's processes with it.
- Tool calls: `tool_call` pending with an empty `rawInput`, an update `in_progress` with the input (twice for shell and subagent), then `completed` or `failed`. Kinds: read; glob and grep search; write and edit edit; shell execute; webfetch fetch; subagent think; question, skill, execute and todowrite other. A title is the tool's name, shell's the command once it runs. An edit completes with its diff, a write without one (only its permission request has it). Shell's output comes at the end only, as text, and a non-zero exit still completes. There's no `plan` update (todowrite is off by default).
- Permissions: with no rules of the user's only reading `.env` and `.env.*` asks; write, edit, shell and webfetch run unasked, outside the folder too. The user's `permissions` make tools ask. A request comes after its call's `tool_call` and `in_progress`, titled with the path, command or URL, always with `once` (Allow once), `always` (Always allow) and `reject` (Reject). A reject, or a cancelled answer, fails the call and ends the whole turn `cancelled`. `always` is saved, for later sessions and processes too.
- Questions: to a client with form elicitation, `elicitation/create` with `q0` (a string with `oneOf`; an array when several may be picked) and `q0_custom`, "Type your own answer" (`Harness.Other`). Declined, the turn ends `cancelled`. To a client without, the tool fails and the turn goes on.
- Subagents: the parent's call is `subagent` (kind think, input `{agent, description, prompt}`), its result `<subagent sessionID="ses_…" state="completed">…</subagent>`. Without `opencode/child-session-updates` in initialize's `_meta`, the child's text and tool calls come mixed into the parent's `session/update`s, told apart only by `_meta["opencode/child-session"]`. With it, which Nushi sends, they come as `opencode/session/child_update` notifications, going on after the parent's prompt returned; acp-go ignores them, so a subagent is one tool call. Either way a child's permission is asked on the root session, with `toolCallId` `<childSessionId>:<id>`; rejected, the subagent's call fails "Subagent cancelled" and the parent's turn goes on. A background subagent's call completes at once, and when the child ends the parent runs a model step whose text never reaches the client.
- Compaction, to a client without `session.compaction` (Nushi): `session_info_update` with `_meta["opencode/compaction"]` (`started`, `completed` or `failed`; `manual` or `auto`). A failed automatic one fails that prompt and every later one of the session.
- A provider's 429 or 500 is tried again (`session_info_update`, `_meta["opencode/retry"]`); a content filter ends `refusal`. An image must carry its data; a `resource_link` to a file opencode reads itself. No revert or rewind over ACP. A line may be 32 MiB.

**Commands (seen)**
- `available_commands_update` lists `init`, `review`, `goal`, `compact` and the commands of the user's config. Skills aren't commands, and an unknown `/x` goes to the model as text.
- Only `/compact` runs in its prompt (the compaction's updates, then `end_turn`). Every other answers `end_turn` in 5 to 17 ms with no update, then runs its turn on the server unseen: the model is asked and tools really run (read: `if (prompt.command) return "succeeded"`, `cli/src/acp/turn.ts`). A prompt sent meanwhile waits behind it, and `session/cancel` doesn't stop it. A permission it needs is never asked: the next prompt then hung (120 s), later ones got "already has an active ACP prompt", and only a `session/cancel` (answered `cancelled`) freed the session.
- So Nushi offers only `compact` (`Harness.HidesCommand`): the rest are neither shown nor remembered. One typed by hand still goes out.

**Stopping and background commands (seen)**
- Input closed: `opencode acp` exits 0 at once and its server goes, but the shell commands it ran, a turn's and the background ones, are left running (alive 17 s later).
- SIGTERM: a running prompt answers `cancelled`, exit 143, and the server and every shell command are gone within 0.5 s. SIGKILL: the same, with no answer.
- So Nushi stops it with SIGTERM (`agentproc.StopBySignal`) and closes its input only once it has exited or the grace ran out. SIGTERM and then the input closing weren't traced as one run.
- A shell call with `background: true` completes at once ("Command moved to the background (shell ID: sh_…)"), its output in a file under the data folder's `shell/`. When it ends the client hears nothing, and the session runs a model step unseen. Nothing in ACP stops one, not `session/cancel` nor `session/close`; deleting the session does (read). Nushi doesn't follow them, and stopping the agent, as when a chat sleeps, ends them.

**A client's MCP servers (seen, with a stand-in server; Nushi hands opencode none)**
- Taken on `session/new`, load, resume and fork (stdio and http; sse is refused). A server belongs to a folder in one opencode process, not to a session: the newest of a name replaces the earlier for every session of that folder there, the user's own server of that name too, and a new process must be handed it again. It runs as a child of `opencode serve` in the session's `cwd`, with the agent's environment, the variables named and `OPENCODE_CLIENT=acp`.
- `session/new` waits until the server is connected and listed, and gives up after about 32 s (one run, 32.058 s; read: 30 s to start and 2 s of grace). It succeeds either way: a server that can't start is silent.
- Its tools sit behind opencode's Code Mode tool. The client sees one call, `execute` (kind other, no locations), whose input is `{"code": "<JavaScript>"}`; the inner calls show only when it completes, in `rawOutput.metadata.toolCalls` (`{tool: "nushi.show", status, input}`). A failing inner call still ends `completed`, with `metadata.error: true` and the inner `status: "error"`.
- `build` and `plan` ask nothing for an MCP tool. Where the user's rules ask, the request is for `execute` and its whole program, never the inner tool or its arguments. Direct tools (`nushi_show`) come only when the user's config denies `execute` (or sets `codemode: false` on a server of its own, read); a client can't ask for them.
- So what ADR 0068 needs (the harness asks, the card names the file) can't hold, and `ClientMCP` is off: an opencode chat gets none of Nushi's tools.

**What a folder brings (seen; `internal/opencodetrust`)**
- No trust prompt and no record of one. Opening a folder runs its code: starting in one imported and ran `.opencode/plugin/mark.ts` inside the server's process and started the project's local MCP server, with nothing asked; `session/new` loads the same (read).
- Its folders, the same on macOS and Linux (`opencode debug paths`): config `~/.config/opencode` (`$XDG_CONFIG_HOME/opencode`; `OPENCODE_CONFIG_DIR` replaces it), data `~/.local/share/opencode` (`$XDG_DATA_HOME/opencode`), cache `~/.cache/opencode`, state `~/.local/state/opencode`, tmp `$TMPDIR/opencode` (`HOME` alone doesn't move it).
- Config, earliest first: the system's folder (`/Library/Application Support/opencode`, `/etc/opencode`) and an MDM plist, the config folder, `OPENCODE_CONFIG`, each folder's `opencode.json` and `opencode.jsonc` from `/` down to the cwd, then each one's `.opencode/`, then `OPENCODE_CONFIG_CONTENT`. A folder's `opencode.json` and `opencode.jsonc` both load, as two documents, the first before the second (read). The walk takes every folder above the cwd up to `/`, past the repository's root: files above the repository loaded. `OPENCODE_DISABLE_PROJECT_CONFIG=1` stops it.
- Any config file may copy a file or a variable into a value: `{file:…}` and `{env:…}` (seen in a project's `opencode.json`).
- From each config folder (the global one and every `.opencode`): plugins (`plugin/`, `plugins/` and the config's list; an npm name is installed when missing), agents and modes (Markdown), commands (`command/`, `commands/`; a `` !`cmd` `` in one runs in the shell when it's used), skills, MCP servers, `shell`, formatters, LSP servers, `instructions`, `permissions` and `policies`. A project's `permissions` entry is added to every agent. 2.2.6 loads no loose tool files: tools come from plugins (the card still lists `.opencode/tool` and `tools`, which an older opencode loaded). Of instruction files only `AGENTS.md` is found (read).
- Policies add up over the documents and the earliest loaded decides (read: `core/src/config/plugin/policy.ts`), so a project can't undo a global deny (seen: a global `plugin.use` deny kept a project's plugin from loading).

**Skills (seen; `internal/opencodeskills`)**
- Where, the winner of a name first: a project's `.opencode/skills` (and `.opencode/skill`), the config folder's `skills`, a project's `.agents/skills`, `~/.agents/skills`, a project's `.claude/skills`, `~/.claude/skills`. A project's are the cwd's and every folder's above it up to `/`. Also the config's `skills` list of paths and URLs (read) and three built in: `opencode`, `report`, `browser`.
- Format: `<root>/…/<folder>/SKILL.md`, its id the folder's name. Groups nest (scanned six deep; a skill's own folder isn't entered), and a loose `<name>.md` at a root is a skill too. Front matter is optional, and `name` changes only what's shown. Links are followed.
- Off: `{"action": "skill.use", "resource": "<id>", "effect": "deny"}` in the global config's `policies` takes the skill out of the list, a built-in too, by id whatever its source; `resource` is a wildcard pattern. This is Nushi's switch. A deny in an agent's `permissions` only hides it from that agent.
