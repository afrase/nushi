# Codex facts

What Nushi depends on, as seen when it was built against the versions named below. Read it before changing the code that talks to it.

## Agent facts (codex-acp 2.2.2; Codex 0.160.1, then yours, 0.163.0)

Until milestone Z the adapter ran its own Codex, 0.160.1 (the facts below were seen with it). Since then it runs yours (`CODEX_PATH`, which codex-acp reads for its app-server, `codex app-server`): 0.163.0, tried by hand in milestone Z (a turn, a reopen after a daemon restart, on DeepSeek V4.1 Flash with a temp `CODEX_HOME`). `codex.Tested` lists both. When npm installed your `codex`, it is a `codex.js` launcher (Node, about 14 MB) that finds the native binary in the platform package (`@openai/codex-<os>-<arch>/vendor/<triple>/bin/codex`, nested in the package, hoisted beside it, or in the package's own `vendor/`) and runs it with `CODEX_MANAGED_PACKAGE_ROOT` (the package's real folder) and `CODEX_MANAGED_BY_NPM` (or bun's, pnpm's, Vite+'s, by its guess at the owner) set. Codex reads them to tell how it was installed: 0.163.0's binary holds a check that an npm-managed launch without the package root fails ("npm-managed launch is missing package-root provenance", seen in its strings, not run). codex-acp gets your `codex` as it is, launcher included. Nushi's Go agent gets the binary itself (`codex.Native`), with the package root and `CODEX_MANAGED_BY_NPM` (not the launcher's guess at bun, pnpm or Vite+), so no Node runs for Codex; the binary finds its `codex-path/rg` and `codex-package.json` beside itself. A Homebrew or standalone `codex` is already native and is passed as it is.

What the code depends on, and how the adapter behaves. Everything Nushi does about it is in `internal/codex*`.

**Sessions**
- `initialize`: `agentInfo.name` `@agentclientprotocol/codex-acp`, `loadSession`, `sessionCapabilities` resume, list, close, delete, fork, additionalDirectories, subagents; `promptCapabilities.image`; `_meta.steering.supported`. It advertises an `api-key` auth method (ChatGPT login too, unless `NO_BROWSER`); with a provider in `config.toml` no `authenticate` is needed. Without a login or provider, `session/new` fails "Authentication required". Its methods (2.2.2): `api-key` (`_meta.api-key`; the key from the request's `_meta` or `CODEX_API_KEY`/`OPENAI_API_KEY`), `chat-gpt` (unless `NO_BROWSER`: `authenticate` opens the browser on Codex's login page and answers once the login completes, or at once when a working ChatGPT login is there; a failed one is Authentication required "Sign-in did not complete"), `chat-gpt-device-code` only for a client with URL elicitation (the page and code go to the client as one), `gateway` only for a client that says it takes one. Nushi offers `chat-gpt` alone (ADR 0145).
- `session/new` returns legacy `modes` (read-only, workspace-write, agent "Auto review" (the default), agent-full-access "Full access"), the unstable `models` list (ids carry the effort as a suffix, `gpt-6.1-sol[medium]`; Nushi doesn't read it) and config options `mode`, `collaboration_mode` (default, plan), `model` (base ids), and, when the model has reasoning levels, `reasoning_effort` (category `thought_level`) and `fast-mode`. A custom model is listed only while it is the current one: after switching to a GPT model, switching back is "Invalid params" (with a model catalog it stays listed). Agent-full-access is a mode like Claude's Bypass permissions: shown, never picked by Nushi itself.
- codex-acp starts and forks every session with `projects.<cwd>.trust_level = "trusted"` as a config override (ADR 0029).
- `session/load` replays user messages (with `messageId`), agent messages (same `msg_…` ids as live), tool calls with their output, thoughts and the title; not the model-metadata warning, permission cards or questions. `session/list` works for a `/private/…` cwd.
- A prompt of two text blocks (2026-10-27, Codex 0.163.0, a temp `CODEX_HOME`; Nushi's note of a branch renamed, then the user's text): the rollout has one user `response_item` `message` with two `input_text` items, and an `item_completed` `UserMessage` with two `text` items, in that order; `session/load` replays them as one user message. `session_meta.git.branch` is the branch when the session started and isn't updated; the model's `<environment_context>` has the cwd, not the branch. Asked after the rename, it gave both names right.
- `session/fork` takes another `cwd` (so a move needs no history copy) and `_meta.jetbrains.air.fork = {version: 1, messageId}` for any client: the fork keeps the turns up to the one that has the message. It replays nothing. After a fork Codex titles the session after its next prompt.
- `session/load` (and `session/resume`) of a session Codex doesn't have (2026-10-26, a temp `CODEX_HOME`): an archived one fails `{"code": -32603, "message": "Internal error", "data": {"details": "session <id> is archived. Run `codex unarchive <id>` to unarchive it first."}}`, also once its rollout file is gone from `archived_sessions` (Codex's state database still has it); after `codex delete --force <id>` (deletes for good, asks first without `--force` and refuses without a terminal) or for an id never made, `"details": "no rollout found for thread id <id>"`. A rollout moved into `archived_sessions` by hand loads, but its next prompt fails with a bare Internal error.
- `session/delete` is `thread/archive`: the rollout moves to `$CODEX_HOME/archived_sessions/`; `codex resume <id>` then asks "Unarchive and resume". `codex delete <id>` would delete for good. History is `$CODEX_HOME/sessions/YYYY/MM/DD/rollout-…-<id>.jsonl`; `codex resume` in a terminal first asks to trust the folder, says when another app has the session open, and leaves a Codex app-server running in the background (`$CODEX_HOME/packages/app-server-daemon`).

**Updates**
- Commands are `exec_command` tool calls: `kind` execute (content a `terminal` reference even without the client's `terminal` capability) or read/search for listing commands (no content). A client that isn't AIR gets the output in `_meta.terminal_output_delta {data}` on `tool_call_update`s and the end in `_meta.terminal_exit {exit_code, signal}`; read commands send `rawOutput.exit_code`. After Stop a running command finishes on its own and its call completes then.
- Permission requests come before the call's `tool_call`; options "Yes, proceed" (allow_once), "Yes, and don't ask again for commands that start with …" (allow_always), "No, and tell Codex what to do differently" (reject_once). In Auto review nothing harmless asks; in Read-only writing a file does.
- Questions (`request_user_input`) only in collaboration mode Plan: an `elicitation/create` form tied to a call id it never sends as a tool call, each question a required string with `oneOf` plus "None of the above", then an optional `<id>_note` "Additional answer or note". The note goes to Codex after the choice, as `{"answers": ["<choice>", "user_note: <text>"]}` (2026-11-25, read in codex-acp-go v0.3.4's `codexacp/elicit.go`, which follows codex-acp).
- `session_info_update` carries the title (the first prompt, whole) and `_meta.codex.threadStatus`. `usage_update` gives used/size (no cost); the prompt result has `usage` and `_meta.quota`. Thoughts come as `agent_thought_chunk`s with `rs_…` ids.
- Without model metadata each turn starts with an agent message without `messageId`: "Warning: Model metadata for `…` not found…", and the window is 258,400.
- Plans come as agent text: codex-acp sends `plan` updates only to clients advertising a `plan` capability.

- Listing (milestone X): codex-acp's `session/list` pages through every thread (`thread/list`, sources cli, vscode, exec, appServer, unknown: no subagents; unarchived only) and then keeps those whose cwd equals the request's exactly (no link resolved: `/tmp` finds nothing, `/private/tmp` does); the title is the first prompt. A fork's rollout starts with `session_meta.payload.forked_from_id`.
- One writer at a time: whoever has a thread holds a lock on `$CODEX_HOME/thread-writer-locks/<id>.lock` (flock; F_GETLK sees it). The TUI then shows "This conversation is open in another app… press R" and is read-only; codex-acp's `session/load` fails "This Codex session is in use by another Codex client (the Codex app, the CLI or an IDE extension)". The TUI runs through a background app-server (`$CODEX_HOME/packages/app-server-daemon`), which keeps the thread, and its lock, after the TUI quits. A Nushi chat that sleeps lets go (the lock file goes).
- `codex login status` says "Not logged in" when a provider key is all it needs, so Nushi shows signed in or not for Claude only.
- The TUI asks to update itself at start: Enter there runs `npm install -g @openai/codex`. `check_for_update_on_startup = false` in `config.toml` stops it.

**Skills (Codex 0.163.0, 2026-10-27; a throwaway CODEX_HOME and HOME, `codex app-server` over stdio)**
- Where (`skills/list`, run): yours in `$CODEX_HOME/skills/<dir>/SKILL.md` and **`~/.agents/skills`** (both scope `user`); the preinstalled `$CODEX_HOME/skills/.system/*` (scope `system`: imagegen, openai-docs, review-agent, skill-creator, skill-installer); a project's **`.agents/skills` and `.codex/skills`** (scope `repo`) in the cwd and each folder above it up to the repository's root (`project_root_markers`, default `[".git"]`), not above it; outside a repository only the cwd's own. Enabled plugins' `skills/` (scope `user`, named `<plugin>:<skill>`, `pluginId` `<name>@<marketplace>`; a plugin with `enabled = false` under `[plugins."<id>"]` lists none). Scope `admin` exists in the protocol (not seen).
- Trust: `skills/list` lists a project's `.agents/skills` and `.codex/skills` whether `projects.<path>.trust_level` is `trusted`, `untrusted` or absent; only a trusted project's `.codex/config.toml` is read (a broken one there fails that cwd's entry: "failed to reload config: Error parsing project config file…"; untrusted, it isn't opened). codex-acp trusts every session's cwd (ADR 0029), so a Nushi chat gets the project's skills regardless.
- Format: front matter required ("missing YAML frontmatter delimited by ---"), `description` required ("missing field `description`"): either missing puts the file in the entry's `errors` (`{path, message}`), not `skills`. The name is the front matter's `name`, else the folder's. A name in two places is listed twice (a repo `user-c` beside yours; no precedence in the list).
- Links: a linked `.agents`, a linked `.agents/skills` and a linked skill folder are followed; a `SKILL.md` that is itself a link (in a real folder) is skipped silently. `path` is always the resolved `SKILL.md` (`/private/tmp/…` for a `/tmp/…` cwd); `cwd` echoes the request's.
- `skills/list` params `{cwds?: string[], forceReload?: bool}` (empty: the session's cwd); answer `{data: [{cwd, skills: [{name, description, shortDescription?, interface?: {displayName, shortDescription, iconSmall, iconLarge, iconSmallUrl, iconLargeUrl, brandColor, defaultPrompt}, dependencies?, path, scope: "user"|"repo"|"system"|"admin", enabled, pluginId: string|null}], errors: [{path, message}]}]}`. Notification `skills/changed` (empty) when watched files change. Also `skills/extraRoots/set {extraRoots}`.
- Off: `[[skills.config]]` entries in `$CODEX_HOME/config.toml`, each `path = "<abs>/SKILL.md"` or `name = "<name>"` (not both: "ignoring skills.config entry with both path and name selectors") with `enabled = false`. A path to the skill's folder matches nothing; a path through a link matches (resolved). A name matches every skill of that name (yours and the repo's), plugins' (`p1:plug-s`) and `.system`'s too. The last matching entry wins (name off then path on: on; path on then name off: off). `[[skills.config]]` in a project's `.codex/config.toml` is ignored, trusted or not. `[skills.bundled] enabled = false` drops the `.system` skills from the list altogether.
- `skills/config/write {path?|name?, enabled}` answers `{effectiveEnabled}`; exactly one selector ("requires exactly one of path or name", -32602); a relative path is refused (-32600). It edits `$CODEX_HOME/config.toml` in place: `enabled = false` adds an entry (or changes the matching one), `true` removes the entry; comments elsewhere, other tables and order stay, a comment just above a removed entry goes with it. A path is stored resolved; any absolute path is accepted (a skills folder too), checked nowhere.

**MCP on/off (2026-10-26; looked at in the binary, not run)**
- `enabled = false` under `[mcp_servers.<name>]` in `config.toml` turns a server off (as Codex documents it; not tried). Nushi's MCP view doesn't list Codex's servers at all, so it isn't offered.

**MCP tool calls (2026-10-31; read in codex-acp 2.2.2's source, not run)**
- A call comes as `tool_call` with title `mcp.<server>.<tool>`, kind `execute` and input `{server, tool, arguments}`; no locations. Its approval is an MCP elicitation Codex sends; a form with no fields becomes `session/request_permission` with only the call's id and kind (no title or input: the client has them from the call), options Allow, Allow for this session, Always allow and Cancel. Whether Codex 0.163.0 asks for a tool with no annotations wasn't run.
- The Go agent (codex-acp-go 0.3.4, read in its source, not run) sends an MCP call the same way (title `mcp.<server>.<tool>`, kind `execute`, input `{server, tool, arguments}`), and adds `_meta.is_mcp_tool_call: true` and the input to its end's update; progress comes as updates with only `_meta.mcp_output_delta`. Nushi takes such a call's kind as `other`, not a command (`codex.Harness.ToolCall`).

**Background commands (2026-10-29; read in codex 0.163.0's strings and codex-acp 2.2.2's source, not run)**
- `exec_command` leaves a command running past its wait ("Process running with session ID …"), a turn's interrupt too; Codex stops one only by `write_stdin` (Ctrl-C, with a terminal) or `kill`. Through codex-acp the call stays `in_progress` past the turn and ends with `terminal_exit`; its `_session/async_task/stop` (`thread/backgroundTerminals/terminate`) is only for clients declaring AIR's `asyncTasks`. Nushi shows no background row or Stop for Codex (the call reads as running; Cancel doesn't end it).

## The Go agent (codex-acp-go's `codexacp`)

Built from codex-acp 2.2.2's source and the schema Codex 0.163.0 prints (`codex app-server generate-ts --experimental`), tested against a fake app-server and, on 2026-11-21, a real Codex 0.163.0 run (a model and its key named in a temp `CODEX_HOME`'s `config.toml`; the live tests now in `github.com/afrase/codex-acp-go`, `codexacp/live_test.go`, run in process and once as `nushid codex-acp`). The agent lives in that library; Nushi runs it as `nushid codex-acp`, off by default: Settings › Agents, Run Codex without Node (ADR 0142).

**The app-server, as codex-acp speaks it**
- `codex app-server` over stdio: one JSON object a line, no `"jsonrpc"` member either way; `initialize {clientInfo, capabilities: {experimentalApi: true, requestAttestation: false}}`, and no `initialized` notification (codex-acp sends none, though the schema has one; seen: the app-server works without it). It exits (status 0) as soon as its stdin closes.
- A thread opens with `config` overrides: `projects.<cwd>.trust_level = "trusted"`, `features.cwd_relative_turn_diffs = false`, and the client's MCP servers under `mcp_servers` (name's whitespace as `_`; stdio `{command, args, env}`, http `{url, http_headers}`).
- Modes are per turn on `turn/start`: read-only `on-request` + reviewer `user` + `readOnly`; workspace-write `on-request` + `user` + `workspaceWrite`; agent (Auto review) `on-request` + `auto_review` + `workspaceWrite`; agent-full-access `never` + `user` + `dangerFullAccess`; with the model, the effort and `summary: "auto"`. Collaboration mode goes by `thread/settings/update` (experimental).
- An app-server error becomes Internal error with its message in `data.details`, as codex-acp's SDK answers any error thrown; that is how "no rollout found for thread id" reaches `codex.Harness.Gone`.

**What the Go agent does as codex-acp does (read in its source)**
- initialize, new (login check by `account/read`, models by `model/list`), close, set mode and options (mode, collaboration mode, model, effort), prompt (input as codex-acp builds it, tokens from the thread's totals), cancel (`turn/interrupt`, questions withdrawn), steering (`turn/steer`), load and resume (title, then items; a thread not yet written opens from `thread/read`; another writer refused), fork and fork at a message (`lastTurnId`), delete (`thread/archive`), list (one page, filtered by cwd), command, edit, MCP, web search, image view, compaction and subagent calls, `terminal_output_delta`/`terminal_exit`, permissions for commands (Codex's decisions, a prefix rule, network hosts) and edits, plan-mode questions as a form with `<id>_note`, MCP tool approvals as a permission request, MCP forms, warnings as agent text, plans as `plan`, the title from the first prompt, skills as `$name` commands, and sign-in (since v0.3.0: initialize's `api-key` and, unless `NO_BROWSER`, `chat-gpt` methods; `authenticate` with `api-key` sends the request's `_meta` key or `CODEX_API_KEY`/`OPENAI_API_KEY` by `account/login/start`; with `chat-gpt` it checks `account/read` first, starts Codex's login, opens its page in the browser (`Config.OpenURL`) and waits for `account/login/completed`, cancelling the login with the request).
- Where it departs: with no turn running, steering answers promptRequired when the client asks for it (Nushi does); codex-acp ignores the ask and starts a turn. A failed turn ends `end_turn` with Codex's error as agent text, as codex-acp does for a client without typed failures.

**Seen in a real Codex 0.163.0 run (2026-11-21)**
- Login: with a key in the config and no OpenAI login, `account/read` answers `{account: null, requiresOpenaiAuth: false}`, and sessions open (no Authentication required). `model/list` lists only OpenAI's models; a custom model is offered because it is the thread's (`thread/start` names it, `reasoningEffort: null`), with no effort option. A turn of an OpenAI model through such a provider fails: an `error` notification (the provider's JSON as the message, which isn't Codex's `{type: "error", status}` shape, so it shows as it is), then `turn/completed` `failed`; the prompt ends `end_turn` with it as agent text.
- A turn: `turn/start` is answered before `turn/started` and every item of the turn (a `warning` of the thread, the model-metadata one, can come before the answer); `thread/tokenUsage/updated {total, last, modelContextWindow}` comes before `turn/completed` (the window 258,400 without model metadata). Item ids reach the client as live: `msg_…`, `rs_…`, `call_…`; a reasoning summary's new part is a `\n\n` break.
- Commands: `item/started` (`commandExecution`, `source: "agent"` while it waits for approval, `unifiedExecStartup` once it runs) comes before its `item/commandExecution/requestApproval`, so the call's `tool_call` precedes the permission request (codex-acp 2.2.2 on 0.160.1 had it the other way). The command is the user's login shell's, `/opt/homebrew/bin/zsh -lc '…'` here: the permission's input keeps it whole, as codex-acp's prefix strip knows only `/bin/`. A command that asks for escalation in read-only listed `availableDecisions` `["accept", {acceptWithExecpolicyAmendment}, "cancel"]` (no `acceptForSession` or `decline`); `cancel` ends the turn `interrupted` and the call `declined` (the call `failed`, the prompt `cancelled`). A command that fails in the sandbox (read-only `touch`, workspace `curl` with no network) runs without asking, no network approval came, and in one run a sandbox failure sent no item at all.
- Every answered or withdrawn request (approval, question) is followed by `serverRequest/resolved {threadId, requestId}`.
- Interrupt: `turn/interrupt` is answered, then `turn/completed` `interrupted`; a command running then (`sleep 30`) isn't stopped: its `item/completed` comes when it ends, and the call completes then. Closing a session mid-turn interrupts it before `thread/unsubscribe`; the prompt ends cancelled.
- History: `thread/resume`'s `itemsBackwardsCursor` is an opaque JSON cursor; `thread/items/list` pages by `limit` both ways (`asc` from no cursor, `desc` from that cursor), `nextCursor` null at the end. A thread never prompted has no rollout: `thread/resume` fails "no rollout found", `thread/read` opens it. Load replays the same ids in the same order as live.
- `thread/list` with no `archived` lists unarchived threads only; `archived: true` lists the archived ones. Fork, delete (`thread/archive`) and list work as above; a mode isn't kept by a thread (load answers Auto review, as codex-acp does).
- Plan-mode questions: `item/tool/requestUserInput {questions: [{id, header, question, isOther, isSecret, options}], isBlocking, autoResolutionMs: null}`; answered as `{answers: {<id>: {answers: [...]}}}`, withdrawn as `{answers: {}}`.
- Steering: `turn/steer` during a turn adds a `userMessage` item to it, which the model reads.
