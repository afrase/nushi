# PiG facts

What Nushi depends on, as seen when it was built against the versions named below. Read it before changing the code that talks to it.

## Agent facts (PiG 0.8.0, through the bridge; 0.5.3's differences said)

What the bridge (`internal/pi`) depends on. First built against PiG 0.5.3, from driving `pig --mode rpc` (the darwin-arm64 release, checked against its `SHA256SUMS`, in a temp `HOME`) and from PiG's source and bundled docs (`pig docs`; `coding/cli/rpc_*.go`); re-measured against 0.8.0 on 2026-11-26 (below, [PiG 0.8.0 against 0.5.3](#pig-080-against-053-2026-11-26)). RPC mode is Pi 1.6.0's protocol in 0.8.0, Pi 1.4.0's in 0.5.3; where the bridge reads it the two agree but for what this section marks "0.5.3:".
- `pig --version` prints the Pi it ports, `1.6.0`, exactly as `pi --version` does; `pig version` prints `pig: 0.8.0`, then `upstream pi: 1.6.0`, `go: …`, `platform: …`, `build: <commit>`, one per line. Both write nothing (an empty `HOME`, `PIG_HOME` and agent folder stayed empty) and take about 30 ms; `pig --help` writes (the docs bundle into `PIG_HOME`, `models-store.json` and `auth.json` into the agent folder). 0.5.3: `--version` printed `0.5.3+1.4.0.74f46864` (PiG, then the Pi it ports and Pi's commit); whether it had `pig version` isn't known, and a pig without it would take `version` for a prompt. So the bridge and the Agents page read PiG's own version from `--version`'s build metadata, else from `pig version`'s first line, asked only of a pig whose `--version` is Pi 1.6.0 or later, and run bare (`PATH` and empty temp homes, no key; `pi.Flavor.ReadVersion`): a pig without the subcommand runs an unknown word as a prompt (`pig frobnicate` in an empty home wrote `auth.json`, `models-store.json`, a sessions folder and the docs bundle, and failed only for want of a key). Install: `curl -fsSL https://pi-in-go.dev/install.sh | sh`, `npm i -g @pi-in-go/pig`, or a GitHub release.
- Framing: a command per line, with an `id` the response repeats (`{"type":"response","id","command","success","data"|"error"}`); events carry no id. Responses can come out of order. A line that isn't JSON answers `"command":"parse"` without an id; an unknown command `success:false`. Closing stdin ends RPC mode after it cancels what runs.
- `prompt` (`message`, `images: [{type:"image", data, mimeType}]`) answers once accepted, before the run: `disposition` `started`, or `handled` when an extension's command took it (the answer comes after the command ends, its dialogs included). A run ends with `agent_settled {aborted}`; several `agent_end`s can come before it (retries, compaction). A second prompt during a run is refused without `streamingBehavior`.
- A session's first prompt brings a message of role `system` (`content: ""`, its prompt in `sections`) before the user's, as `message_start` and `message_end`, and saved as the session's first `message` entry; a reload doesn't bring it again. 0.5.3: none.
- Events: `message_start` (an assistant message has its `timestamp` from the start, `content: []` and `stopReason: "pending"`; 0.5.3 also had its `responseId` there, which 0.8.0 gives at `message_end`), `message_update` (`assistantMessageEvent`: `text_start`, `text_delta`, `text_end {content}`, `thinking_start/delta/end`, `toolcall_start {id, toolName}`, `toolcall_delta`, `toolcall_end` with the call in `toolCall` or `partial.content[contentIndex]`; each update also carries the message's `usage` so far), `message_end` (the final message: `usage`, `stopReason` `stop`/`length`/`toolUse`/`error`/`aborted`, `errorMessage`); `tool_execution_start {toolCallId, toolName, args}`, `_update {args, partialResult}` (a command's output so far; a bash call's first has `content: []`, no output yet; 0.5.3: not seen), `_end {result: {content, details|structuredContent}, isError, durationMs}` (bash's `structuredContent {output, truncated, exit_code, wall_time_seconds}`, an edit's `details {diff, patch, firstChangedLine}`), a tool result's message as `message_start` and `message_end`; `turn_start`, `turn_end {message, toolResults}` around each model call, `agent_end {messages, willRetry}`; `queue_update`, `session_info_changed {name}`, `thinking_level_changed`, `compaction_*`, `auto_retry_*`, `extension_ui_request`, `extension_error`. A message's `timestamp` is the one in the session file; no event carries a message's entry id.
- Tools: `read {path, offset, limit}`, `bash {command, timeout}`, `edit {path, edits: [{oldText, newText}]}` (its result's `details.patch`), `write {path, content}`, `grep`, `find`, `ls`; extensions and MCP servers add theirs. Calls in one message run at once (an edit and a write started together). **No permission prompts and no modes**: every call runs without asking (only an extension can block one).
- `abort` (answers after the run settled): a running command ends "Command aborted" (failed); a model call ends `stopReason: "aborted"`, "Request was aborted". A steer queued when the abort comes stays queued, and the next prompt's run takes it after that prompt's own message (`queue_update` empty, then the steer as a user message's events): the model would see it a turn late. `clear_queue` after the abort answers it (`{steering: [text], followUp: []}`, after a `queue_update` empty) and the next run holds its own prompt alone. So the bridge sends `clear_queue` as every turn ends with a steer it hasn't seen taken, and answers what comes back as not taken (`promptRequired`): the chat takes the message out of the transcript and puts it back in its queue, as for a steer no agent took. A steer pi brings in is answered `injected` as its user message comes (the turn's own prompt first, then the steers in order). 0.5.3: it came into the stopped run as a user message, and the model call it started ended `stopReason: "error"`, "This operation was aborted"; its `clear_queue` then has nothing. `steer` queues a message "after the current tool batch and before the next model call" (`queue_update {steering, followUp}`, then `disposition: queued`); it comes back as a user message's events.
- Models: `get_available_models` lists every model PiG has a key for (`FIREWORKS_API_KEY`: Fireworks' 24, `fireworks/accounts/fireworks/models/…`); `set_model {provider, modelId}`. Thinking levels are the model's (`get_available_thinking_levels`: DeepSeek V4.1 Flash off, low, high, max). The session keeps both (`model_change`, `thinking_level_change` entries), so a reload is on the model it had. A new session starts on `defaultProvider`/`defaultModel`/`defaultThinkingLevel` from `<agent dir>/settings.json`, else (Fireworks) Kimi K3.
- `get_session_stats`: `sessionFile`, `sessionId` (0.8.0), `contextUsage {tokens (null right after a compaction, until the model answers again), contextWindow, percent}`, `cost` (USD, the session's, compactions' summaries included), `tokens {input, output, cacheRead, cacheWrite, total}` (the session's), `userMessages`, `assistantMessages`, `toolCalls`, `toolResults`, `totalMessages`. No breakdown of the context, and no count of compactions (the bridge counts the branch's `compaction` entries).
- `get_commands`: extensions' commands, prompt templates and skills (`/skill:<name>`); a prompt `/name args` runs or expands them. PiG's own slash commands (`/model`, `/compact`, `/name`, `/tree`, `/trust`…) are the terminal's: sent as a prompt they reach the model as text. RPC mode has commands for what some of them do (`set_model`, `compact`, `set_session_name`, `fork`); the bridge offers `/compact` and `/name` itself (below). Stock pig's built-in extensions: llama.cpp, codemode, tool-search, mcp, pig-login (`/llama`, `/mcp`, `/sprite`).
- Compaction: `compact {customInstructions?}` aborts a running prompt first, then answers once done: `{summary, firstKeptEntryId, tokensBefore, estimatedTokensAfter, usage?, details?}`, or `success:false` ("Nothing to compact (session too small)", "Already compacted", "Compaction cancelled" after an `abort`, which cancels it). Every compaction, asked for or PiG's own, is `compaction_start {reason: manual|threshold|overflow}` then `compaction_end {reason, result?, aborted, willRetry, errorMessage?}`, written before the command's answer; PiG's own come inside a run, before `agent_settled` (one can come before the model call, when the context is already past the line). The session gets a `compaction` entry (`summary`, `firstKeptEntryId`, `tokensBefore`, `details {readFiles, modifiedFiles}`); the summary is markdown with fixed sections and ends with `<read-files>`/`<modified-files>` lists.
- **Automatic compaction is on by default** (`compaction.enabled: true`): when the context passes the window minus `compaction.reserveTokens` (16,384), keeping the last `keepRecentTokens` (20,000) whole; per-model overrides in `compaction.modelOverrides`. `set_auto_compaction` writes `compaction.enabled` to PiG's global settings, not the session's; each pig reads its settings when it starts.
- `set_session_name {name}` writes a `session_info` entry and `session_info_changed {name}` before its answer.
- Plans: PiG has no todo tool. Pi's todo extension (in PiG's bundled examples) keeps its list in its tool's result `details.todos [{id, text, done}]`, which RPC mode passes whole in `tool_execution_end` and the session's tool result message; its plan-mode extension in an entry of its own (`appendEntry`: `entry_appended {entry: {type: "custom", customType, data: {todos: [{step, text, completed}]}}}`) and a widget's text lines.
- Extensions' dialogs: `extension_ui_request` `select {title, options}`, `confirm {title, message}`, `input {title, placeholder}`, `editor {title, prefill}`, each with an optional `timeout` (ms, after which it answers itself), answered by `extension_ui_response {id, value | confirmed | cancelled}`; `notify {message, notifyType}`, `setStatus`, `setWidget`, `setTitle`, `set_editor_text` want no answer. **`/sprite`, answered or cancelled, hangs pig in RPC mode** (it stops answering anything, `abort` and `get_state` too, until stdin closes; seen in 0.5.3 answered, in 0.8.0 both ways); an extension of ours (a Node `select`, `confirm`, `input`, and a tool that asks) worked.
- Sessions: `<agent dir>/sessions/--<cwd, / as ->--/<time>_<uuid v7>.jsonl` (the agent folder `~/.pig/agent`, or `$PIG_CODING_AGENT_DIR`, `$PIG_HOME/agent`, `$XDG_CONFIG_HOME/pig/agent`; `$PIG_CODING_AGENT_SESSION_DIR` or the settings' `sessionDir` move the sessions; files 0644, folders 0700). A header line `{type:"session", version:3, id, timestamp, cwd, parentSession?}`, then entries `{type, id, parentId, timestamp, …}` making a tree; the leaf is the last appended. A new session's file is written with its first message: a session whose prompts were only extensions' commands has none.
- `--session <file>` opens a session (pig moves to the header's cwd; a gone folder is an error); an id found only in another folder's sessions makes pig ask on stdin "Fork this session into current directory? [y/N]", so the bridge passes the file. Opening appends nothing (unless an old file migrates or the branch has no thinking level entry). `get_entries` answers every entry of every branch and `leafId`.
- `fork {entryId}` (a user message's; answers `{text, cancelled}`) and `clone` (`{cancelled}`) switch the process to a new session: the branch before that message, or all of it, entry ids kept, header `parentSession` = the source's path, written at once when it holds a message; the source isn't changed. A fork at the first message has no message of the user's or the model's (0.8.0 keeps the model, thinking level and system entries) and no file.
- `session_start` is no RPC event: it is an extension's hook (`{type, reason: startup|new|resume|fork, previousSessionFile?}`; a pig started on `--session` says `startup`), and what an extension does in it (a `notify`, an entry) is what a client sees. 0.8.0 runs it once as `fork`, `clone` or `new_session` replaces the session, before the command's answer (its `rpc.md` says twice, as in Pi 1.6.0; not seen: a further second after a 1 s wait). 0.5.3 ran it a second time after the answer (from issue #121; 0.5.3 isn't on hand to see again). The bridge waits for neither: the new session's pump passes on what came, in order. A fork's pig is started on the source's file (`--session <file>`) before its `fork` or `clone`, so an extension's startup notice (`reason: startup`, about the source session) comes first and lands in the fork's transcript too, ahead of the fork's own (seen with the fake's greeting extension, both versions).
- An answer cut at the model's limit (`stopReason: "length"`) is followed, between `agent_end` and `agent_settled`, by `entry_appended` of a `context_edit` entry (`{targetId, replacement: null}`: the cut message is left out of the model's context; the transcript keeps it). With tight compaction settings (`keepRecentTokens` 1, `reserveTokens` 1000) an overflow compaction follows it there too (`compaction_start`/`_end {reason: overflow}` after the `entry_appended`, before `agent_settled`; seen in the review's probe, 2026-11-26), which the bridge shows as any compaction inside a run; with the defaults, none. 0.5.3: not seen.
- Two writers: PiG takes no lock or owner file (each entry is appended by an open, write, close). Nushi and a terminal `pig -p --session` on one session each appended to their own branch; a later resume followed the last writer's.
- Delete in PiG's `/resume` runs `trash <file>`, else unlinks.
- Trust: RPC mode can't ask; a folder's `.pig/{settings.json, mcp.json, extensions, skills, prompts, themes, SYSTEM.md, APPEND_SYSTEM.md}` and `.agents/skills` load only with a decision in `<agent dir>/trust.json` (`{"<canonical path>": true|false}`, the nearest ancestor's), `defaultProjectTrust: "always"` in the user's settings, or `--approve` (checked: a project prompt template loaded only once `trust.json` said true). Regardless of trust: `AGENTS.md`/`CLAUDE.md` from the folder up to `/` and the agent folder, the project `sessionDir`, and a migration that renames a project's `.pig/commands` to `.pig/prompts`.
- MCP: `<agent dir>/mcp.json` and a trusted folder's `.pig/mcp.json` (`{"mcpServers": {…}}`); the built-in mcp extension connects them in RPC mode too; `pig mcp list --json` starts every server to check it.
- An extension that fails to load stops pig at start ("Error: Failed to load extension …: TypeScript extensions need Node.js 22.13 or newer"); the bridge's error then carries that line.

**Skills (PiG 0.5.3, 2026-10-27; `pig --mode rpc` `get_commands` in a throwaway `HOME`, and its source `internal/codingagent/{resource_paths,skills,trust_manager}.go`, `coding/packagecontent`)**
- Where, in precedence order (the first of a name wins; a later one is a collision diagnostic, dropped): the project's `skills` settings entries, the project's `.pig/skills` (in the cwd only, not above it), every `.agents/skills` from the cwd up to the git root (the folder holding `.git`), or to `/` outside git, nearest first; then your `skills` settings entries, `<agent dir>/skills` (`~/.pig/agent`, or `$PIG_CODING_AGENT_DIR`, seen), and `~/.agents/skills` (`$HOME`'s; skipped as a project folder when the walk meets it); then packages' (`pig install`). No built-in skills (stock pig's built-ins are extensions with commands only); extensions can add inline ones. `.claude/skills` and `.codex/skills` aren't read. `--skill <path>` adds one, `--no-skills` turns discovery off.
- **Trust**: the project half (project settings, `.pig/skills`, every ancestor `.agents/skills`) loads only when the cwd is trusted (`<agent dir>/trust.json`, the nearest ancestor's decision: a repository root's `true` covers a subfolder, a subfolder's `false` wins; `defaultProjectTrust: "always"`; `--approve`); untrusted, only yours and `~/.agents/skills` show (seen).
- Format: a folder holding `SKILL.md`; the name is front matter `name`, else the folder's (`folder-name/` with `name: front-name` is `skill:front-name`); names breaking the Agent Skills rules (`Upper_Case`) only warn. **No `description` (or no front matter): not loaded** (seen). Discovery recurses (`skills/group/x/SKILL.md` is a skill; a folder with `SKILL.md` isn't walked further), skipping dot-entries, `node_modules` and `.gitignore`/`.ignore`/`.fdignore`d paths. In `.agents/skills` a Markdown file at the root is documentation and a nested one a skill; in `.pig/skills` and `<agent dir>/skills` a root `.md` is a skill.
- Symlinks are followed everywhere: a linked `.agents/skills` root, a linked skill folder, a linked `SKILL.md` all load (seen); the path reported is the link's.
- **Off**: the `skills` array of a settings file, with `-<path>` (exact) or `!<glob>` entries (`+<path>` forces on): `<agent dir>/settings.json` for your skills (agent dir and `~/.agents/skills`), the cwd's `.pig/settings.json` for the project's (`.pig/skills` and every ancestor `.agents/skills`); each file's patterns reach only its own scope (seen: your settings can't turn a project skill off, nor the reverse). There's no local (uncommitted) project settings file. A relative path is matched against the skill's base folder, which is `.agents` for an `.agents/skills` skill, so `pig config`'s own form (`-../.agents/skills/x` from `.pig`, `-../../.agents/skills/x` from the agent dir) **doesn't** turn an `.agents` skill off (seen); an absolute path does (`-/abs/repo/.agents/skills/x`, seen), and so does one relative to that base folder: `-skills/x` in the cwd's `.pig/settings.json` turned off both `<repo>/.agents/skills/x` (from a subfolder) and `.pig/skills/x` (seen 2026-10-27; `matchesAnyExactPattern` compares the skill folder's path relative to `.pig` or to each `.agents`), so it catches every project skill in a folder named `x`. `!<name>` (a glob on the folder or file name) works too but catches every skill of that name. `pig config` is a TUI only. A skill off is left out of `get_commands`.
- Listing: RPC `get_commands` (no model call, no key needed) gives each skill as `{name: "skill:<name>", description, source: "skill", sourceInfo: {path (its SKILL.md), source ("auto" found, "local" a settings entry), scope ("user" | "project"), origin: "top-level", baseDir}}`; `enableSkillCommands: false` didn't hide them there. `disable-model-invocation: true` skills are listed too. Running it means a pig in the folder (its trusted extensions start).

**MCP servers (PiG 0.8.0, 2026-11-26; the darwin-arm64 release, checked against its `SHA256SUMS`, run with `HOME`, `PIG_HOME` and `PIG_CODING_AGENT_DIR` in empty temp folders, no key and no model call, against a stdio server and a Streamable HTTP one on 127.0.0.1 of our own; and its bundled `mcp.md`)**
- Where: yours in `<agent dir>/mcp.json`, the project's in `.pig/mcp.json` of the folder pig runs in (only that folder's: a parent's `.pig/mcp.json` isn't read, seen from a subfolder of a trusted folder). Both `{"mcpServers": {"<name>": {…}}}`; other top-level keys (`autoEnableCodemode`) sit beside it.
- **Trust**: the project's file loads only once the folder is trusted (trust.json's nearest decision, a key with a trailing slash matching too (seen in the review's probe, 2026-11-26), the exact key winning when both are there, either way round (`diagnose`, the second review's probe), or `defaultProjectTrust: "always"`); untrusted, `pig mcp list` leaves it out, and `--json` says so in a top-level `"note"` ("… is ignored because the project is not trusted …"; seen in the review's probe, 2026-11-26), and `pig mcp login`/`add -l` say "… is ignored because the project is not trusted. Start pig in the project to trust it." The only way to trust is pig's own (its prompt at start, `/trust`). `defaultProjectTrust: "always"` is honoured by a session (an RPC pig started the project's servers) but not by `pig mcp list`, which leaves the project's file out with the same note (seen in the review's probe): so Nushi's check, the list, shows such a folder's project servers unchecked.
- **Which wins**: a project entry replaces your entry of its name (listed as the project's, seen). A project entry with no `command`, `url` or `type` is an override: it changes only `enabled`, `exposure` and `toolExposure` of your entry and keeps the rest (listed as yours, its `enabled` the override's, seen both ways); with no entry of yours to override it's an error ("needs \"command\" or \"url\", or a global server to override"). A project entry PiG refuses (`"type": "sse"`) replaces nothing: yours of that name is used and listed as `global`, and the project entry's error is in `errors` (seen in the review's probe), so Nushi matches the list's results by scope and name.
- An entry: stdio `command` (one program, not a shell line), `args`, `env`, `cwd` (relative to the session's folder; the default is the session's folder, seen); HTTP `url`, `headers`, `oauth {clientId, clientSecret, callbackPort, callbackUrl, clientName, clientRegistration, scope, authServerMetadataUrl}`; both `timeout` (seconds per request, default 60: `"timeout": 3` failed a hung server after 3 s, seen), `enabled`, `exposure` (`codemode` default, `deferred`, `direct`, `hidden`), `toolExposure`, `description`. `type` is optional (`stdio`, `http`, `streamable-http`); `"type": "sse"` is refused ("legacy SSE transport is not supported"). With both `command` and `url`, the URL is used (seen). `auth {provider}` (a `/login` provider's token) counts only in your file. `env`, `headers` and `url` take `${VAR}`, and a value that is wholly `!command` runs it. Keys it doesn't know are ignored (seen). Names: letters, digits, `_`, `-`, a `-` first too (`-dash` listed, seen in the review's probe, 2026-11-26). Nushi still refuses a name that starts with `-` for edit, remove, switch and sign-in, as for every agent (a name the other agents' CLIs would read as a flag), so such a server shows but is changed only in PiG or its file.
- **Off**: `"enabled": false` keeps the entry, unconnected (`pig mcp list` says `disabled`, seen); in a project's file, `{"enabled": false}` under your server's name turns it off there, and `{"enabled": true}` turns one of yours that is off back on there (seen).
- **What it can't read** is skipped and reported, never fatal: a file that isn't strict JSON (comments, trailing commas, empty: "Unexpected end of JSON input") or has no `mcpServers` object is left out whole, the other file's servers still listed; a bad entry (not an object, a bad name, SSE, neither command nor URL) is left out alone. Each lands in `errors` as `<file>: <why>`, most naming the server (`server "<name>" …`, `invalid server name "<name>" …`).
- **`pig mcp list --json`** (in the folder; loads no extensions) connects to every enabled server at once and prints `{"servers": [{name, scope ("global" | "project"), source (the file), enabled, exposure, transport (the command line or URL), state, tools, error?}], "errors": [...]}`, servers in file order, yours first, and only the one used of each name; exit 1 when an entry is bad or an enabled server didn't connect. States seen: `connected`; `failed` with `error` (a stdio server's stderr after "MCP connection closed", "fork/exec …: no such file or directory", "MCP request timed out after 3000ms", "fetch failed"); `needs-auth` (an HTTP server that answered 401 with OAuth metadata; no error); `disabled`. 0.25 s for five servers here; a hung server holds it for its `timeout`.
- **Sign-in**: OAuth for an HTTP server with no `Authorization` header. `pig mcp login <name> [--timeout <s>, default 300]`, in the folder (the server used there; `-l` only the project's), prints the authorization URL, opens it with `open` (seen through a fake `open` on `PATH`), needs no terminal (stdin `/dev/null`) and waits for the browser's redirect to `127.0.0.1:<port>/callback`; not finished in time: "Sign-in to MCP server … was cancelled or not completed within N seconds.", exit 1. Tokens in `<agent dir>/mcp-auth.json` (0600, keyed `mcp__<name>|<url>`; `pig mcp list` makes it, `{}`, when an HTTP server is listed); a running session uses new ones on its next turn. `pig mcp logout <name>` deletes them (exit 0 also with none stored; exit 1 for an unknown name). Both take the name after `--`.
- **A running session keeps the servers it started with**: an RPC pig started its servers once, didn't start one added to `mcp.json` 3 s later, and started it on `new_session` (seen); the docs say the terminal's `/reload` does the same. So a chat picks up a change when its pig starts again (Nushi reloads or resumes it).
- **Its own writes** (`pig mcp add/remove`, `/mcp`'s switches): the file rewritten whole, keys in their order, other top-level keys and other servers' unknown keys kept, its indentation kept (4 spaces stayed 4) but compact objects expanded; the mode kept (0600 stayed 0600, a new file 0644), a link followed (the link stays), written atomically since 0.8.0 (its release notes, D651). `add` replaces an entry whole (its unknown keys go). `add -l` writes the project's file even when the folder isn't trusted, and says it's ignored until then. `remove` of a name not there: exit 1.
- Missing files are no servers, no error.

**Background commands (2026-10-29; PiG 0.5.3's docs)**
