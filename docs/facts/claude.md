# Claude facts

What Nushi depends on, as seen when it was built against the versions named below. Read it before changing the code that talks to it.

## Agent facts (claude-agent-acp 0.94.0; Claude Code 2.1.303, then yours, 2.1.310)

Until milestone Z the adapter ran the Agent SDK's own Claude Code, 2.1.303 (the facts below were seen with it; this file said 2.1.308–309, the terminal's `claude` of the time, which ran only `claude mcp`). Since then it runs yours (`CLAUDE_CODE_EXECUTABLE`): 2.1.310, tried by hand in milestone Z (a turn with a command, a reopen after a daemon restart). `claude.Tested` lists both; a failed start with another version says so.

What the code depends on, and how the adapter behaves. Everything Nushi does about it is in `internal/claude*`.

**Sessions**
- `session/new` requires `mcpServers`: send `[]`, never `null`. Claude starts a session in the mode its settings say; it reports modes both as legacy `modes` and as a `mode` config option (Nushi shows only the option). Config options: `mode` (Manual, Accept edits, Plan, Auto, Bypass permissions), `model` (Default, Opus 5.5, Fable 5.1, Sonnet 5.5, Haiku 5.5), `effort` (category `thought_level`), `fast` (category `model_config`, a select), `agent` (no category). `set_config_option` answers with the full set.
- Claude names a session itself soon after the first prompt (`session_info_update`), with a model call of its own; until then Nushi uses the prompt's first line. After a short first turn (about 4 s, a one-line answer; 2026-10-27) the title came about 0.1 s after the turn's end. A fork is titled "<title> (fork)", a fork of a fork "(fork) (fork)": ignored, so a moved or rewound chat keeps its title. Asking `/context` before the first message made Claude name the chat after it; Nushi no longer sends `/context` (2026-11-25: the Context widget asks `get_context_usage`, below, which runs no turn).
- A worktree's branch renamed between turns (2026-10-27; Claude Code 2.1.310 in one long `claude -p` stream-json process, as the adapter keeps one, in a throwaway repository with a bare remote): Claude's system prompt holds a git status snapshot taken when the session started, the branch included, and it isn't taken again. Asked from memory, Claude named the old branch. Asked after the rename to push "this branch", it ran `git push -u origin <old name>` first (failed: "src refspec … does not match any"), then `git branch --show-current`, and pushed the new name, saying the branch had been renamed since. Asked in another run to commit and push right after naming the old branch, it checked first, saw the new name and stopped to ask instead. Nothing went to the remote under the old name; the cost is a failed command or a question. Seen again on 2026-10-27 (Claude Code 2.1.310 through claude-agent-acp 0.94.0, a dev daemon and a throwaway repository): the snapshot is taken when the session starts (`session/new`), before any prompt: renamed before the first prompt and asked from its context only, Claude named the old branch; with Nushi's note before that prompt it named the new one and said its snapshot still had the old. A prompt of two text blocks (the note, then the user's) is one user entry in the transcript with `content` `[{type: text, text: <note>}, {type: text, text: <user's>}]`; `session/load` replays both, which Nushi joins into one message and takes the note out of. Asked after Nushi's rename following the first turn, it gave both names right without running anything.
- Claude keeps a session on disk only once it has a message: `session/load` of an empty one fails, and Nushi then starts a new one. `session/load` replays the user's and agent's messages and the tool calls (final status and output, `messageId`s included), not permission prompts or questions; a cancelled turn replays as a user message "[Request interrupted by user]" (the Go agent does the same), which Nushi leaves out (`claude.Harness.Interrupted`): its own "Stopped" notice says it. It sends no `usage_update`. Loading takes under a second. A loaded session is on Claude's default model and effort, not the ones picked before (Haiku came back as Opus 5.5): Nushi sets the chat's picks again (ADR 0060).
- Compaction (Claude Code 2.1.310, 2026-10-26, `/compact` through the adapter in a throwaway folder, ACP recorded): live, `/compact` is a `tool_call` "Compact conversation", kind `think`, `_meta.claudeCode.toolName` `compact`, then `completed` and an update with `rawOutput` `{trigger: "manual", preTokens, postTokens, durationMs}`; no text. `session/load` afterwards replays only what follows the last compaction: first a `user_message_chunk` (a UUID `messageId`, no `_meta`) holding the summary, which starts "This session is being continued from a previous conversation that ran out of context." and ends saying the messages after it are "the most recent messages from before compaction, kept verbatim"; then those kept messages (here the agent's last message before `/compact`, with its live `msg_…` id, but not the user message it answered), then what came after. Neither the `/compact` prompt nor its call is replayed. Agent messages and tool calls keep their live ids in a replay; user messages, which a client names itself live, come with Claude's UUIDs. Nushi shows the summary as "Compacted here" and the earlier part from its own copy (ADR 0047). Forking at an agent message from before the compaction (a rewind, tried 2026-10-26) works: the fork has the conversation up to it whole, not the summary (asked, Claude named what it had done before and nothing after).
- Claude's history folder for a session is named after its cwd: the real path (symlinks resolved, `/tmp` is `/private/tmp`), NFC, every UTF-16 unit that isn't an ASCII letter or digit replaced by `-`; past 200 characters cut, with a base-36 hash of the path. `CLAUDE_CONFIG_DIR` moves the projects folder.
- A session Claude no longer has (Claude Code deletes transcripts older than `cleanupPeriodDays`, 30 by default, when it starts; reproduced on 2026-10-26 by moving a throwaway chat's `<id>.jsonl` out of its project folder): `session/load` fails with `{"code": -32002, "message": "Resource not found: <id>", "data": {"uri": "<id>"}}` after about 1.3 s (the adapter maps Claude Code's "No conversation found with session ID" to it). The adapter answers the same when Claude Code quits before answering its first request ("Query closed before response received"), so the code alone doesn't prove the session is gone: Nushi also checks that the folder's history folder can be read and the transcript isn't in it (`claudehistory.Local.HistoryGone`). The project folder itself stayed (with its `memory/` folder).
- `sessionCapabilities`: `fork`, `close`, `resume`, `list`, `delete`. `session/fork` copies the transcript into a new session on the same process (updates come tagged with the fork's id). The adapter's, with another `cwd`, failed, since it looked for the source only in the new folder's history; Nushi's Go agent finds it in any folder's and writes the fork into the new folder's, which is all a move does ([ADR 0014](../adr/0014-moving-a-chat-forks-it.md)). After a fork the reported cost starts again near zero.
- Forking at a message: `_meta.jetbrains.air.fork = {version: 1, messageId}` on `session/fork` keeps the conversation up to that agent message, it included, for any client, after `session/load` too ([ADR 0020](../adr/0020-rewind-through-a-vendor-fork.md)). Nushi sends it without asking the agent's name (since 2026-11-25; its Go agent takes it from any client).
- `session/delete` (for clients that aren't AIR, which get archiving) deletes `<id>.jsonl` and `<id>/` in whichever project folder has them, succeeds for a session never written, and leaves the history folder behind. Deleting a session the process has open, or closing it, makes Claude write a ~700-byte stub back as it ends; a second delete a few seconds later removes it. So side chats ended other than by closing them are deleted by a fresh agent once the one they ran on has stopped.

**Updates**
- Every `agent_message_chunk` has a `messageId`; chunks group by it. Claude sends no `agent_thought_chunk`s here (thinking is "omitted" for recent models).
- A tool call arrives as a `tool_call` with a generic title and empty `rawInput`, then `tool_call_update`s with the real title, `locations` and content; each update's content replaces the last. A command's first content is its description, the last its output in a fence; a failed command's output starts with `Exit code N`. An `Edit`'s diff holds the snippet, not the file. One update carries only `_meta.claudeCode.toolResponse`. Claude searches and lists with `Bash`, not Grep and Glob.
- MCP tool calls (2026-10-28; claude-agent-acp 0.94.0, Claude Code 2.1.312, a throwaway stdio MCP server and a fake Messages API on localhost, `ANTHROPIC_BASE_URL`, a dummy key, a throwaway `CLAUDE_CONFIG_DIR` and `HOME`): the `tool_call`'s title is the raw `mcp__<server>__<tool>` (no ACP kind: `other`), with `content: []` and `rawInput: {}`; the whole input comes in a later `tool_call_update` with only `rawInput`, and the adapter shows no copy of it (its generic reporter adds one only for a tool named `Other`). A `_meta.claudeCode.toolResponse` update follows, then the result: status, `rawOutput` (Claude Code's `tool_result` content: a string, or a list of text and image blocks) and `content` with the same as text. Claude Code turns every MCP result into text first: a structured-only result (`content: []` plus `structuredContent`) becomes the JSON of `structuredContent`; an embedded resource "[Resource from <server> at <uri>] <text>"; a `resource_link` "[Resource link: <name>] <uri>"; an image an image block plus "[Image: source: <file it saved>]"; `isError` a failed call whose content is the text fenced; an empty result "(<tool> completed with no output)". A large result (142 KB here; the threshold wasn't looked for) is saved to a file and comes as `<persisted-output>\nOutput too large (141.7KB). Full output saved to: <path>\n\nPreview (first 2KB): …</persisted-output>`. So a finished MCP call always has text. Text starting with a tag (`<persisted-output>`, or a server's own `<result>…`) is an HTML block to Markdown, which flutter_markdown drew as nothing: a result wrapped in a tag showed as an empty box, a saved one lost its first lines. `markdown_view` shows an HTML block as its text now. `session/load` replays each call the same way, the input in the `tool_call`.
- Claude Code's own notices (claude-agent-acp 0.94.0, which Nushi runs): a client without `clientCapabilities.session.notices` (Nushi) gets them as an `agent_message_chunk` with **no `messageId`**, a bold label and `_meta.claudeCode = {kind: "informational", level}` (`**Notice:** …`, `**Warning:** …`; no label for `info`); a client with it would get ACP's `notice` update instead. Some notices come without the `_meta` (`**Model fallback:** …`, `**Fast mode turned off:** …`, "Task stopped by user"). None is replayed by `session/load`. Nushi shows the marked ones as notice lines (`claude.Harness.Notice`), not as text appended to the message before (what a chunk without an id did).
- Safeguards stopping a response (2026-10-28; read in the adapter's source and Claude Code 2.1.312's, then reproduced through the adapter with a fake Messages API on localhost answering `stop_reason: "refusal"` with `stop_details`, a throwaway `CLAUDE_CONFIG_DIR` and `HOME`, no key of the owner's): what streamed of the refused response comes live as ordinary chunks under its API message id; then the notice "Opus 5.5's safeguards stopped the response above · continuing once with that noted" (`informational`, level `notice`, no id); then Claude Code retries the same model once with a meta user message ("Your response above was stopped by a safety classifier … Do not produce that content again"), whose reply streams under a new id. The stopped part is **not** in Claude's history (neither the retried request nor the transcript has it; tool calls in it get "Not run: …stopped by a safety classifier"), so only Nushi's copy keeps it: Nushi marks that message `stopped_by_safeguards` (folded, "Stopped by safeguards") and never forks at it. Opus 5.5 thinks first and its thinking is omitted, so a response stopped while thinking streams nothing: "above" is then empty in Nushi (as on the work Mac) and shows only Claude Code's thinking line in its terminal. A refusal Claude Code doesn't retry ends the turn with stop reason `refusal` and the classifier's explanation as text.
- Plans (2026-11-03, Claude Code 2.1.314 through the adapter, the `plan` parity scenario): Claude keeps a to-do list only with its todo tools on. Its own check turns them on for older models (Claude 3, Opus 4.0–4.7, Sonnet 4.x, Haiku 4.5) and otherwise only with `CLAUDE_CODE_ENABLE_TODO_TOOLS=1` in its environment; without them neither the adapter nor the Go agent ever sends a `plan`. Nushi sets it in the agent's environment (`claude.Environ`) unless the user's agent environment (the login shell's, ADR 0048) sets it, and both agents pass it on to claude. With it claude has TaskCreate, TaskUpdate, TaskList and TaskGet (TodoWrite instead only with `CLAUDE_CODE_ENABLE_TASKS=false`), and the adapter shows them as `plan` updates, never as tool calls: the whole list each time, an entry's `content` the task's subject, or its `activeForm` while it's `in_progress` ("Reading the notes", then "Read the notes" once `completed`), `priority` always `medium`. Each TaskCreate sends the list twice (as the call comes and as it's answered); each TaskUpdate once. `session/load` replays one `plan` per call in order (in between a step may show `in_progress` beside the next), ending on the last list, and the next prompt starts by sending the current list again, which a load never replays: Nushi adds a turn's card only once the plan differs from the chat's latest (`planLocked`), so live and a reload show the same cards. The Go agent sends the same (`claudeacp/plan.go`; the parity test holds it).
- `available_commands_update` (about 80 commands, plugins' and skills' too) comes after `session/new` and `session/load`. A command is an ordinary prompt starting with `/name`; a `resource_link` to a `file://` URI makes Claude read the file.
- Commands claude refuses headless (2026-11-04; Claude Code 2.1.314, read in its binary, then each typed into claude run as both the adapter and the Go agent run it, stream-json, on `fakeapi` with a throwaway `HOME` and `CLAUDE_CONFIG_DIR`; 2.1.318 is out and not looked at): a built-in command, or an alias of one, that isn't among the commands claude runs non-interactive is answered `/<name> isn't available in this environment.` (a `<synthetic>` assistant message, then a `success` result with that text); nothing reaches the model and the text after the name is dropped. Refused: `add-dir`, `advisor`, `artifacts`, `autofix-pr`, `background` (`bg`), `branch`, `brief`, `btw`, `bug`, `cd`, `cloud-plugins`, `copy`, `design-consent`, `design-login`, `design-revoke`, `desktop` (`app`), `diff`, `exit` (`quit`), `export`, `extra-usage`, `feedback`, `fork`, `help`, `hooks`, `ide`, `import`, `install-github-app`, `install-slack-app`, `keybindings`, `login`, `logout`, `loops`, `memory`, `mobile` (`ios`), `passes`, `pause-memory` (`memory-pause`), `permissions` (`allowed-tools`), `plan`, `plugin` (`plugins`, `marketplace`), `powerup`, `privacy-settings`, `pro-trial-expired`, `radio`, `rate-limit-options`, `release-notes`, `remote-control` (`rc`), `remote-env`, `restart` (`update`), `resume`, `rewind` (`checkpoint`, `undo`), `schedule` (`routines`), `scroll-speed`, `session` (`remote`), `setup-bedrock`, `setup-vertex`, `skills`, `status`, `statusline`, `stickers`, `stop`, `subtask`, `tasks` (`bashes`), `teleport` (`tp`), `terminal-setup`, `theme`, `tui`, `ultraplan`, `ultrareview`, `upgrade`, `usage-credits`, `vim`, `voice`, `web-setup`, `wellbeing` (`breaks`), `workflows`. `/daemon`, `/install`, `/version`, `/review`, `/pr-comments`, `/todos` and `/output-style:new` aren't refused: claude has no such command headless and sends the text to the model. `model`, `effort`, `fast`, `config`, `color`, `focus`, `rename`, `usage` (`cost`, `stats`) and the rest of `initialize`'s list run. Neither `initialize`'s commands nor `system/init`'s `slash_commands` lists a refused one (`terminal_slash_commands`, here `doctor`, `color`, `focus`, `reload-plugins`, are ones that run but are meant for a terminal), so neither agent offers one: the adapter lists claude's commands less its own `UNSUPPORTED_COMMANDS` and the terminal ones, plus its `/mcp` and, when the SDK can, `/remote-control`; the Go agent claude's less `hiddenCommands` and the terminal ones. Typing one is the only way to meet the refusal.
- `/plan` in claude's terminal (2.1.314's source): not in plan mode, it switches the session to plan mode and prints "Enabled plan mode"; text after it other than `open` or `share` then goes to the model as the command's arguments; with no text, and a plan already written in the session, it also shows the plan. In plan mode already it changes nothing and sends nothing, text or not: it shows the plan ("Current Plan", its path, `"/plan open" to edit this plan in <editor>`) or "Already in plan mode. No plan written yet." `/plan open` opens the plan file in your editor. Nushi runs it for both agents (`claude.Harness.TerminalCommand`): `/plan` sets the `mode` option to `plan` as the mode menu does and leaves the notice "Enabled plan mode"; `/plan <text>` then sends the text as the prompt (claude gets it as your message, not as the command's arguments); in plan mode already, `/plan` alone leaves "Already in plan mode." and `/plan <text>` sends the text with no notice (where the terminal drops it). It shows no plan and opens no editor: `/plan open` and `/plan share` are `/plan`. No other refused command sets a chat option: Nushi's equivalents of the others are its own controls (Rewind and Fork under a message, side chats, the Background tasks widget, History, Settings, its own `/copy`).
- Usage: each turn ends with two `usage_update`s, `{used, size}` and the same with `cost` (USD, the session's so far; not reliable across processes). One carried `_meta._claude/rateLimit`. The prompt result's unstable `usage` sums the turn's model calls.
- `session/cancel` ends the turn in a second or two with `cancelled`; streamed text stays. A command Claude ran in the background can finish later and Claude writes on its own, outside any turn.
- A cancel kills the background subagents too (and the commands they started: their output files end "[killed]"), and no update says so, unless the session's `_meta.claudeCode.options.perTaskStopAffordance` is true (on `session/new`, `load`, `fork`: the adapter passes `claudeCode.options` to Claude Code as host options). Claude Code 2.1.310's own description of the option: a host that renders a per-task stop control declares it, and "an interrupt … spares running background agents/workflows (Stop only aborts the turn)"; "ABSENCE also fails closed: the interrupt kills background tasks, since the user would otherwise have no way to stop a runaway one". Claude Code's terminal has that stop (its task list), so Esc there spares them. Nushi declared it from 2026-10-26, and its Go agent declares it itself (claudeacp options.go; Nushi stopped sending it on 2026-11-25): a cancel then leaves a background subagent running, it reports, and Claude answers the report on its own. The per-task stop the option promises, `_session/async_task/stop {sessionId, asyncTaskId}`, answers `{stopped: false}` for a client that isn't AIR (its tasks are never "announced"); Claude's deferred `TaskStop` tool stops one when asked, and with the subagents capability `session/cancel` on a subagent's session stops it (below).
- Background subagents hold the turn (claude-agent-acp 0.94.0, `Turn.deferredSettle`, for v1 clients only: a v2 client is told "idle" instead): when the turn's model work ends (its result) while subagents the turn started run in the background, the adapter keeps `session/prompt` unanswered until they have ended and Claude has answered their reports, so that their permission requests land inside a turn. Seen: a reply at 10:24:29, `end_turn` at 10:26:09 after the subagent's `sleep 90`. The turn's result is the `usage_update` with `cost` and `_meta._claude/origin {kind: "human"}`; a subagent's report is answered under `{kind: "peer", from: <agentId>, name, body: "[Subagent hand-back] …"}`, then the task notification `{kind: "task-notification", producer: "session-task"}`, and the held prompt is answered between the two. Asked to wait for its subagent, Claude does the same (no tool call waits: it ends its turn saying it will report when the subagent does). While the turn is held: a new `session/prompt` answers the held one at once (`end_turn`) and is answered itself at once, the subagent running on (the user "moving on outranks the hold"); `_session/steering` is `injected` and answered at once, but the prompt stays held; `session/cancel` answers it `cancelled`. After a steered message, the result of the work it cut short comes too (cost, `human`), before the steered work's own. Nushi treated the held turn as over at its result (ADR 0044) until 2026-11-25; the Go agent doesn't hold (its recordings, below), so a turn now ends at the prompt's answer.
- Permissions: in Manual mode Claude asks with "Yes" (`allow_once`) and "No" (`reject_once`); the request names the tool call sent just before. `.claude/settings.json` = `{"permissions":{"defaultMode":"default"}}` starts a folder in Manual mode, for testing.
- Questions (AskUserQuestion) need `elicitation.form` in the client capabilities: a `tool_call` ("Asking for your input"), then `elicitation/create` in form mode tied to it. Each question is `question_N`, a `string` with `oneOf` or an `array` with `items.anyOf`, followed by an optional free-text `question_N_custom` titled "Other"; nothing is `required`, and the properties must be read in wire order. An empty accept reads to Claude as "no answer". The Other's text beside a pick (2026-11-25, read in claude-acp-go v0.8.1's `claudeacp/question.go`, which follows claude-agent-acp 0.94.0): for a one-choice question the pick is the answer and the text a note on it, in the tool's input as `annotations: {"<question>": {"notes": "<text>"}}`; for a multi-select the text is one more answer, joined after the picks with ", "; with nothing picked it is the answer.
- Subagents: with `_meta: {"subagent-transcript": true}` in `initialize`'s client capabilities, a subagent's tool calls, text and thinking all carry `_meta.claudeCode.parentToolUseId` (tool calls also `toolName`); the Agent call's `subagent_type` is in its `rawInput`, maybe in a later update. Background subagents: the Agent call completes at once with "Async agent launched…", and the subagent ends with a `SubagentHandback` call whose `rawInput.message` is its report (its own output is only an acknowledgement). After `session/load` the Agent calls come back, but not a background subagent's steps or report. Messaging one: `SendMessage`'s `rawInput.to` is the subagent's `agentId`.
- Subagents (Claude Code 2.1.303): foreground subagents end with a `SubagentHandback` too, and their Agent call's output is then only a pointer ("This agent's report was delivered to you as a message from \"<agentId>\" (its SubagentHandback call)…"). The Agent call's `rawInput` comes in pieces over several `tool_call_update`s: `description`, `subagent_type`, `model` (`sonnet`, `haiku`, `opus`: the model option's values), `effort` (`low`…: the effort option's values), `prompt`, `run_in_background`; `model` and `effort` only when Claude picks them. The call's last update carries `_meta.claudeCode.toolResponse` with `agentId`, `agentType`, `resolvedModel` (`claude-sonnet-5-5`: the model it ran on, even when inherited), `totalDurationMs`, `totalTokens`, `totalToolUseCount`, `usage`, `handbackReport.text`; no effort. The subagent's own updates carry only `parentToolUseId` and `toolName`, no model. `session/load` replays the Agent call with its whole `rawInput` but no `toolResponse`, and no subagent's steps or report, foreground ones included. A background subagent's Agent call ends at once (no totals); its totals come only in claude's `task_notification` as it ends, `usage: {total_tokens, tool_uses, duration_ms}` (seen in the `subagent-background` recording), which claude-acp-go passes on since v0.6.0 as a `tool_call_update` of the Agent call with only `_meta.claudeCode.toolResponse` `{totalTokens, totalToolUseCount, totalDurationMs}` (a load replays it), so a background subagent's row has its tokens as a foreground one's. `async_task_*` updates go only to AIR clients; the ACP subagents RFD form (child sessions) only to clients that advertise `subagents` (Nushi does since 2026-10-27: below).
- Background shells (what a client that isn't AIR sees): a Bash call with `rawInput.run_in_background: true` completes at once; its last update's `_meta.claudeCode.toolResponse.backgroundTaskId` is the task's id and its output text says "Command running in background with ID: <id>. Output is being written to: <tmp>/claude-<uid>/<project>/<session>/tasks/<id>.output. You will be notified when it completes. To check interim output, use Read on that file path." That file fills as the command writes and ends with "[exited with code N]" or "[killed]". Claude 2.1.303 has no BashOutput (it said so, and reads the file with Read); stopping is the deferred `TaskStop` (found through `ToolSearch`), input `{task_id}`, response `{message, task_id, task_type: "local_bash", command}`. When a command ends, Claude gets a task notification, which claude-agent-acp never passed on (claude-acp-go does since v0.5.0, as an update of the Bash call: the Go agent's section); Claude then runs a turn of its own, whose last `usage_update` has `_meta._claude/origin = {kind: "task-notification", producer: "session-task", runId}`, naming no task. `async_task_*` updates and the `_meta.jetbrains.air` `backgrounded` marker go only to AIR clients. A client that sets `_meta.terminal_output: true` in its capabilities gets Zed's terminal extension instead: every Bash call's output moves to `_meta.terminal_output` (content becomes a terminal reference), and a background command's `terminal_exit` (exit code null) comes when its task ends; Nushi doesn't use it, since it would change how every command reads. Background commands outlive Claude: after the daemon stopped (and Claude with it), `sleep 300` still ran, and its file never got an end line.
- Messaging a subagent: claude-agent-acp 0.94.0's child sessions (the RFD form) take only `cancel`; a v1 client has no way to prompt one. Claude Code 2.1.303's deferred `SendMessage` tool (`{to: <agentId>, message, summary, type: "message"}`) reaches a subagent by the id the Agent call's result gives (a background call's output ends "agentId: <id>"; a foreground one's names it in its pointer to the report; `toolResponse.agentId` too). It answers `{success, message: "Resuming agent …", resumedAgentId}`: a finished subagent runs again under its first Agent call (its steps carry that call's `parentToolUseId`) and ends with another `SubagentHandback`; a running one takes the message as it goes. Tried five times (three finished, one running, one finished after a daemon restart): Claude passed the text verbatim each time and the subagent acted on it; Claude then relays the reply in its own words, sometimes adding its own checks.
- Stopping subagents (2026-10-27; claude-agent-acp 0.94.0, Claude Code 2.1.310, recorded through a `node` that tees the adapter's stdin and stdout; trimmed recordings in `internal/features/chats/testdata/subagents`). Without the `subagents` client capability (Nushi before 2026-10-27) a client hears nothing when a background subagent ends unless it calls `SubagentHandback`, and 2.1.310's often don't: one ended with a plain message under its `parentToolUseId` ("done"), then Claude's turn of its own (`_claude/origin` `{kind: "task-notification"}`, naming no task) and the held prompt's answer. Stopped by Claude's `TaskStop` (`{task_id: <agentId>}`, found through `ToolSearch`), the call's `toolResponse` is `{message: "Successfully stopped task: <id> (<description>)", task_id, task_type: "local_agent", command: <description>}` and nothing else follows: no update for the Agent call, no task notification turn; the subagent's open tool call ends `failed` ("The user doesn't want to proceed with this tool use…"), or completes if it was about to. A task already ended makes `TaskStop` fail with "Task <id> is not running (status: killed)" (Claude may report that as "it came back as killed"). Steps are keyed by the launching Agent call's id (`parentToolUseId`); a subagent started after stopping one with a similar description had only its own (the owner's "both show 63 tool calls" wasn't reproduced; a `SendMessage` to the stopped one would run it again under its first call, as below).

Nushi's own ACP agent for Claude (`claudeacp` on `claudeagent`, the module `github.com/afrase/claude-acp-go`, [ADR 0066](../adr/0066-claude-through-nushis-go-agent.md)), Claude's only agent since 2026-11-04. It is built from what the official SDKs do (the Python SDK's source), what Claude Code 2.1.312's schema and binary say, and the adapter's behaviour as read in its source, and held to the adapter by the parity scenarios: 33 runs of the adapter on the real `claude` (a fake Messages API, a throwaway `CLAUDE_CONFIG_DIR` and `HOME`), replayed to the Go agent (`internal/features/chats/testdata/claude-parity`), and since 2026-11-25 39 runs of the Go agent itself on Claude Code 2.1.331 (the adapter's `load` kept in `testdata/claude-adapter-load`). What those runs showed is under "Seen in the Go agent's recordings" and "Seen in the parity recordings" below; the rest of this section is still what the Go agent relies on unseen.

**How it runs claude**
- One `claude` a session, the user's (`CLAUDE_CODE_EXECUTABLE`), with no `-p`: claude runs non-interactive whenever its stdout isn't a terminal. Arguments: `--output-format stream-json --verbose --input-format stream-json`, `--session-id=<the ACP session's id>` (so the ids, the transcripts and `claude --resume` are the adapter's), `--setting-sources=user,project,local`, `--include-partial-messages`, `--replay-user-messages`, `--allow-dangerously-skip-permissions` (not as root without `IS_SANDBOX`), and `--permission-prompt-tool=stdio` once it answers permissions; never `--bare`.
- Environment: the chat's, without `CLAUDECODE` and `NODE_OPTIONS`, plus `CLAUDE_CODE_ENTRYPOINT=sdk-cli` (claude's own value for a run with no official SDK, as under the adapter), `CLAUDE_CODE_EMIT_SESSION_STATE_EVENTS=1` and `CLAUDE_AGENT_SDK_CLIENT_APP=claudeagent-go/<version>` (claude's User-Agent).
- Each claude runs in the agent's process group, as the adapter's does, so the daemon's kill of the agent's group (after `stopGrace`) takes claude and what stays in its group, its stdio MCP servers and its hooks; not its Bash commands, background ones included, which lead groups of their own (above) and outlive the kill, as they did under the adapter; the agent's own close (an interrupt, at most 2 s, then stdin's end and 2 s more) fits within that grace. No version is pinned: the agent logs `claude --version` at each start (INFO, `msg=claude version=…`), and claude's stderr at INFO (a few lines a second a session). An `initialize` answer naming no account is a WARN: a claude started without the user's login.
- A resume claude quits on before answering `initialize` is -32002 only when `claudeagent/sessions` finds no transcript of it any more; otherwise an internal error with the end of claude's stderr, so the session isn't taken for gone.

## Claude desktop's launch.json

Claude desktop's dev servers (its Browser pane's "Dev servers"), as read on 2026-11-06 in the desktop app's bundle (version 4.23118.0: `.vite/build/index.chunk-BBUaTQ8d.js`, `parseLaunchJson`, `parseConfiguration`, `extractPortFromCommand` and the url check `JVa`; `index.chunk-CpYh0TRT.js`, the tool's errors; `index.chunk-Wliylfb_.js`, the start) and its docs (https://code.claude.com/docs/en/desktop, "Configure preview servers" and "Port conflicts", whose examples are `internal/launchfile/testdata/docs`). Claude Code's CLI, which Nushi runs, wasn't seen to have any of it (unverified). Nushi reads the same files (ADR 0095, `internal/launchfile`); where it differs is said below.

**The file**
- `.claude/launch.json` at the root of the session's selected folder only (no subfolder, no repository root), JSON with comments and trailing commas (its parser keeps what it could parse: a file with a syntax error still counts when some entry is usable; Nushi refuses the file).
- Top level: `version` (written `"0.0.1"`, never read), `configurations` (a list, else the file is invalid; absent is no entries) and `autoVerify` (on unless `false`; Nushi ignores it). Unknown keys are ignored, and keys match by exact case.
- A bad entry is skipped and named in a warning; none usable is `launch_config_invalid` for the agent. A missing file is `launch_config_missing`, a name not found `launch_config_name_not_found`, matched without case (the first entry of that name).

**An entry**
- The command: `runtimeExecutable` with `runtimeArgs`, then `program`, then `args`; with no `runtimeExecutable`, `node program args`. Spawned directly, no shell.
- No command: a `url` alone attaches to a server already running; an entry with no command and a `type` or a `command` key, or no `url`, is skipped ("VS Code "command" / "node-terminal" style entries are not supported").
- `${workspaceFolder}` and `${workspaceRoot}` become the folder in the command, its arguments and `cwd` (not in `env` or `url`). `cwd` is relative to the folder (or absolute) and must resolve inside it, checked only at the start ("cwd must be a relative path within the project root."); Nushi checks it at reading and again just before the start (`CheckCwd`), through `os.Root`, and wants an existing folder.
- `autoPort` must be a JSON boolean when present (`null` too is refused). `port`: 0, `""`, `false` and `null` are unset; else a whole number from 1 to 65535, or a string of one to five digits making one (`"0"` is refused).
- `url`: a non-empty string, http or https, no user name or password. Localhost is `localhost`, `*.localhost`, `127.0.0.1`, `0.0.0.0` and `::1`; a dotted `localhost.`, another address in 127/8 or an IPv4-mapped IPv6 address is refused as not written the usual way (the host as a browser parses it, so `127.1` is `127.0.0.1`, and IDNA's mapping makes a full-width `ｌｏｃａｌｈｏｓｔ` or `127。0。0。1` localhost too). Claude takes `:0` as a url's port; Nushi refuses it. A localhost url must be the bare origin (no path, query or fragment), on the entry's port when one is given.
- The port: the entry's, else a localhost url's (the scheme's own when none is written), else the command's, else 3000 when there is a command (0 for an attach elsewhere with no `port` or `env.PORT`). The command's: `env.PORT` when set (JavaScript's `parseInt`, so `"auto"` gives none and stops the search), else the first `--port N`, `-p N`, `--port=N` or `-p=N` among `program`, `runtimeExecutable`, `runtimeArgs` and `args` as written (`--port 0` gives none, and stops), else the first word matching `(--port|--PORT|-p)\s+N`, then `localhost:N`, then `:NNNN` (four or five digits) before a space or the end. Claude doesn't check that port's range; Nushi refuses one outside 1–65535.
- The name: `name` when given, else the last argument without its extension (`.[^.]+` at the end) with `:` made `-`, or `preview` when that leaves under two characters (JavaScript's length: UTF-16 units, so one emoji is two); for an attach, the url's host (with a port that isn't the scheme's). Detection's candidates must match `^[a-zA-Z0-9][a-zA-Z0-9:_.-]{0,63}$`; written entries' names aren't checked.
- `env` is passed as is (the docs: no secrets, the file is committed); Nushi takes strings only, and refuses an entry whose `env` has an empty name or one with `=` or NUL.
- Before a spawn Claude asks with a card showing the command. What it remembers the answer by, and so whether an edited entry asks again, wasn't found in the bundle (unverified).
- Running one (from the design's reading of the same bundle; Nushi's in ADR 0098): spawned directly in a process group of its own with the login shell's environment, `FORCE_COLOR`, `env` and `PORT`; ready on a connection and an HTTP HEAD, marked running but "timed_out" after 180 s; its listener checked to be in its process tree; `autoPort` scans 20 past the port and rewrites `--port`/`-p`, holding a reservation for 30 s; unset `autoPort` looks through package.json's scripts for a pinned port first, which Nushi doesn't (unset is true; a script that pins its own port ignores the port Nushi picked, and isn't seen there). At most 5 a worktree, keyed by session and folder (Nushi: by folder, shared by its chats); stopped with SIGTERM to the group, SIGKILL after 3 s, and with the app.
