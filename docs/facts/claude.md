# Claude facts

What Nushi depends on, as seen when it was built against the versions named below. Read it before changing the code that talks to it.

## Agent facts (claude-agent-acp 0.94.0; Claude Code 2.1.303, then yours, 2.1.310)

Until milestone Z the adapter ran the Agent SDK's own Claude Code, 2.1.303 (the facts below were seen with it; this file said 2.1.308–309, the terminal's `claude` of the time, which ran only `claude mcp`). Since then it runs yours (`CLAUDE_CODE_EXECUTABLE`): 2.1.310, tried by hand in milestone Z (a turn with a command, a reopen after a daemon restart). `claude.Tested` lists both; a failed start with another version says so.

What the code depends on, and how the adapter behaves. Everything Nushi does about it is in `internal/claude*`.

**Sessions**
- `session/new` requires `mcpServers`: send `[]`, never `null`. Claude starts a session in the mode its settings say; it reports modes both as legacy `modes` and as a `mode` config option (Nushi shows only the option). Config options: `mode` (Manual, Accept edits, Plan, Auto, Bypass permissions), `model` (Default, Opus 5.5, Fable 5.1, Sonnet 5.5, Haiku 5.5), `effort` (category `thought_level`), `fast` (category `model_config`, a select), `agent` (no category). `set_config_option` answers with the full set.
- Claude names a session itself soon after the first prompt (`session_info_update`), with a model call of its own; until then Nushi uses the prompt's first line. After a short first turn (about 4 s, a one-line answer; 2026-10-27) the title came about 0.1 s after the turn's end. A fork is titled "<title> (fork)", a fork of a fork "(fork) (fork)": ignored, so a moved or rewound chat keeps its title. Asking `/context` before the first message makes Claude name the chat after it, so it isn't asked then.
- A worktree's branch renamed between turns (2026-10-27; Claude Code 2.1.310 in one long `claude -p` stream-json process, as the adapter keeps one, in a throwaway repository with a bare remote): Claude's system prompt holds a git status snapshot taken when the session started, the branch included, and it isn't taken again. Asked from memory, Claude named the old branch. Asked after the rename to push "this branch", it ran `git push -u origin <old name>` first (failed: "src refspec … does not match any"), then `git branch --show-current`, and pushed the new name, saying the branch had been renamed since. Asked in another run to commit and push right after naming the old branch, it checked first, saw the new name and stopped to ask instead. Nothing went to the remote under the old name; the cost is a failed command or a question. Seen again on 2026-10-27 (Claude Code 2.1.310 through claude-agent-acp 0.94.0, a dev daemon and a throwaway repository): the snapshot is taken when the session starts (`session/new`), before any prompt: renamed before the first prompt and asked from its context only, Claude named the old branch; with Nushi's note before that prompt it named the new one and said its snapshot still had the old. A prompt of two text blocks (the note, then the user's) is one user entry in the transcript with `content` `[{type: text, text: <note>}, {type: text, text: <user's>}]`; `session/load` replays both, which Nushi joins into one message and takes the note out of. Asked after Nushi's rename following the first turn, it gave both names right without running anything.
- Claude keeps a session on disk only once it has a message: `session/load` of an empty one fails, and Nushi then starts a new one. `session/load` replays the user's and agent's messages and the tool calls (final status and output, `messageId`s included), not permission prompts or questions; a cancelled turn replays as "[Request interrupted by user]". It sends no `usage_update`. Loading takes under a second. A loaded session is on Claude's default model and effort, not the ones picked before (Haiku came back as Opus 5.5): Nushi sets the chat's picks again (ADR 0060).
- Compaction (Claude Code 2.1.310, 2026-10-26, `/compact` through the adapter in a throwaway folder, ACP recorded): live, `/compact` is a `tool_call` "Compact conversation", kind `think`, `_meta.claudeCode.toolName` `compact`, then `completed` and an update with `rawOutput` `{trigger: "manual", preTokens, postTokens, durationMs}`; no text. `session/load` afterwards replays only what follows the last compaction: first a `user_message_chunk` (a UUID `messageId`, no `_meta`) holding the summary, which starts "This session is being continued from a previous conversation that ran out of context." and ends saying the messages after it are "the most recent messages from before compaction, kept verbatim"; then those kept messages (here the agent's last message before `/compact`, with its live `msg_…` id, but not the user message it answered), then what came after. Neither the `/compact` prompt nor its call is replayed. Agent messages and tool calls keep their live ids in a replay; user messages, which a client names itself live, come with Claude's UUIDs. Nushi shows the summary as "Compacted here" and the earlier part from its own copy (ADR 0047). Forking at an agent message from before the compaction (a rewind, tried 2026-10-26) works: the fork has the conversation up to it whole, not the summary (asked, Claude named what it had done before and nothing after).
- Claude's history folder for a session is named after its cwd: the real path (symlinks resolved, `/tmp` is `/private/tmp`), NFC, every UTF-16 unit that isn't an ASCII letter or digit replaced by `-`; past 200 characters cut, with a base-36 hash of the path. `CLAUDE_CONFIG_DIR` moves the projects folder.
- A session Claude no longer has (Claude Code deletes transcripts older than `cleanupPeriodDays`, 30 by default, when it starts; reproduced on 2026-10-26 by moving a throwaway chat's `<id>.jsonl` out of its project folder): `session/load` fails with `{"code": -32002, "message": "Resource not found: <id>", "data": {"uri": "<id>"}}` after about 1.3 s (the adapter maps Claude Code's "No conversation found with session ID" to it). The adapter answers the same when Claude Code quits before answering its first request ("Query closed before response received"), so the code alone doesn't prove the session is gone: Nushi also checks that the folder's history folder can be read and the transcript isn't in it (`claudehistory.Gone`). The project folder itself stayed (with its `memory/` folder).
- `sessionCapabilities`: `fork`, `close`, `resume`, `list`, `delete`. `session/fork` copies the transcript into a new session on the same process (updates come tagged with the fork's id); with another `cwd` it fails, since it looks for the source only in the new folder's history, so a move copies the transcript there first ([ADR 0014](../adr/0014-moving-a-chat-forks-it.md)). After a fork the reported cost starts again near zero.
- Forking at a message: `_meta.jetbrains.air.fork = {version: 1, messageId}` on `session/fork` keeps the conversation up to that agent message, it included, for any client, after `session/load` too ([ADR 0020](../adr/0020-rewind-through-a-vendor-fork.md)). The adapter is recognized by `agentInfo.name` `@agentclientprotocol/claude-agent-acp`, Nushi's Go agent by `claudeacp`.
- `session/delete` (for clients that aren't AIR, which get archiving) deletes `<id>.jsonl` and `<id>/` in whichever project folder has them, succeeds for a session never written, and leaves the history folder behind. Deleting a session the process has open, or closing it, makes Claude write a ~700-byte stub back as it ends; a second delete a few seconds later removes it. So side chats ended other than by closing them are deleted by a fresh agent once the one they ran on has stopped.

**Updates**
- Every `agent_message_chunk` has a `messageId`; chunks group by it. Claude sends no `agent_thought_chunk`s here (thinking is "omitted" for recent models).
- A tool call arrives as a `tool_call` with a generic title and empty `rawInput`, then `tool_call_update`s with the real title, `locations` and content; each update's content replaces the last. A command's first content is its description, the last its output in a fence; a failed command's output starts with `Exit code N`. An `Edit`'s diff holds the snippet, not the file. One update carries only `_meta.claudeCode.toolResponse`. Claude searches and lists with `Bash`, not Grep and Glob.
- MCP tool calls (2026-10-28; claude-agent-acp 0.94.0, Claude Code 2.1.312, a throwaway stdio MCP server and a fake Messages API on localhost, `ANTHROPIC_BASE_URL`, a dummy key, a throwaway `CLAUDE_CONFIG_DIR` and `HOME`): the `tool_call`'s title is the raw `mcp__<server>__<tool>` (no ACP kind: `other`), with `content: []` and `rawInput: {}`; the whole input comes in a later `tool_call_update` with only `rawInput`, and the adapter shows no copy of it (its generic reporter adds one only for a tool named `Other`). A `_meta.claudeCode.toolResponse` update follows, then the result: status, `rawOutput` (Claude Code's `tool_result` content: a string, or a list of text and image blocks) and `content` with the same as text. Claude Code turns every MCP result into text first: a structured-only result (`content: []` plus `structuredContent`) becomes the JSON of `structuredContent`; an embedded resource "[Resource from <server> at <uri>] <text>"; a `resource_link` "[Resource link: <name>] <uri>"; an image an image block plus "[Image: source: <file it saved>]"; `isError` a failed call whose content is the text fenced; an empty result "(<tool> completed with no output)". A large result (142 KB here; the threshold wasn't looked for) is saved to a file and comes as `<persisted-output>\nOutput too large (141.7KB). Full output saved to: <path>\n\nPreview (first 2KB): …</persisted-output>`. So a finished MCP call always has text. Text starting with a tag (`<persisted-output>`, or a server's own `<result>…`) is an HTML block to Markdown, which flutter_markdown drew as nothing: a result wrapped in a tag showed as an empty box, a saved one lost its first lines. `markdown_view` shows an HTML block as its text now. `session/load` replays each call the same way, the input in the `tool_call`.
- Claude Code's own notices (claude-agent-acp 0.94.0, which Nushi runs): a client without `clientCapabilities.session.notices` (Nushi) gets them as an `agent_message_chunk` with **no `messageId`**, a bold label and `_meta.claudeCode = {kind: "informational", level}` (`**Notice:** …`, `**Warning:** …`; no label for `info`); a client with it would get ACP's `notice` update instead. Some notices come without the `_meta` (`**Model fallback:** …`, `**Fast mode turned off:** …`, "Task stopped by user"). None is replayed by `session/load`. Nushi shows the marked ones as notice lines (`claude.Notice`), not as text appended to the message before (what a chunk without an id did).
- Safeguards stopping a response (2026-10-28; read in the adapter's source and Claude Code 2.1.312's, then reproduced through the adapter with a fake Messages API on localhost answering `stop_reason: "refusal"` with `stop_details`, a throwaway `CLAUDE_CONFIG_DIR` and `HOME`, no key of the owner's): what streamed of the refused response comes live as ordinary chunks under its API message id; then the notice "Opus 5.5's safeguards stopped the response above · continuing once with that noted" (`informational`, level `notice`, no id); then Claude Code retries the same model once with a meta user message ("Your response above was stopped by a safety classifier … Do not produce that content again"), whose reply streams under a new id. The stopped part is **not** in Claude's history (neither the retried request nor the transcript has it; tool calls in it get "Not run: …stopped by a safety classifier"), so only Nushi's copy keeps it: Nushi marks that message `stopped_by_safeguards` (folded, "Stopped by safeguards") and never forks at it. Opus 5.5 thinks first and its thinking is omitted, so a response stopped while thinking streams nothing: "above" is then empty in Nushi (as on the work Mac) and shows only Claude Code's thinking line in its terminal. A refusal Claude Code doesn't retry ends the turn with stop reason `refusal` and the classifier's explanation as text.
- Plans (`plan` updates, the full list each time) come only when Claude's todo tools are on (`CLAUDE_CODE_ENABLE_TODO_TOOLS=1` in its environment); Nushi doesn't set it.
- `available_commands_update` (about 80 commands, plugins' and skills' too) comes after `session/new` and `session/load`. A command is an ordinary prompt starting with `/name`; a `resource_link` to a `file://` URI makes Claude read the file.
- Usage: each turn ends with two `usage_update`s, `{used, size}` and the same with `cost` (USD, the session's so far; not reliable across processes). One carried `_meta._claude/rateLimit`. The prompt result's unstable `usage` sums the turn's model calls.
- `session/cancel` ends the turn in a second or two with `cancelled`; streamed text stays. A command Claude ran in the background can finish later and Claude writes on its own, outside any turn.
- A cancel kills the background subagents too (and the commands they started: their output files end "[killed]"), and no update says so, unless the session's `_meta.claudeCode.options.perTaskStopAffordance` is true (on `session/new`, `load`, `fork`: the adapter passes `claudeCode.options` to Claude Code as host options). Claude Code 2.1.310's own description of the option: a host that renders a per-task stop control declares it, and "an interrupt … spares running background agents/workflows (Stop only aborts the turn)"; "ABSENCE also fails closed: the interrupt kills background tasks, since the user would otherwise have no way to stop a runaway one". Claude Code's terminal has that stop (its task list), so Esc there spares them. Nushi declares it since 2026-10-26: a cancel then leaves a background subagent running, it reports, and Claude answers the report on its own. The per-task stop the option promises, `_session/async_task/stop {sessionId, asyncTaskId}`, answers `{stopped: false}` for a client that isn't AIR (its tasks are never "announced"); Claude's deferred `TaskStop` tool stops one when asked, and with the subagents capability `session/cancel` on a subagent's session stops it (below).
- Background subagents hold the turn (claude-agent-acp 0.94.0, `Turn.deferredSettle`, for v1 clients only: a v2 client is told "idle" instead): when the turn's model work ends (its result) while subagents the turn started run in the background, the adapter keeps `session/prompt` unanswered until they have ended and Claude has answered their reports, so that their permission requests land inside a turn. Seen: a reply at 10:24:29, `end_turn` at 10:26:09 after the subagent's `sleep 90`. The turn's result is the `usage_update` with `cost` and `_meta._claude/origin {kind: "human"}`; a subagent's report is answered under `{kind: "peer", from: <agentId>, name, body: "[Subagent hand-back] …"}`, then the task notification `{kind: "task-notification", producer: "session-task"}`, and the held prompt is answered between the two. Asked to wait for its subagent, Claude does the same (no tool call waits: it ends its turn saying it will report when the subagent does). While the turn is held: a new `session/prompt` answers the held one at once (`end_turn`) and is answered itself at once, the subagent running on (the user "moving on outranks the hold"); `_session/steering` is `injected` and answered at once, but the prompt stays held; `session/cancel` answers it `cancelled`. After a steered message, the result of the work it cut short comes too (cost, `human`), before the steered work's own. Nushi treats the held turn as over at its result (ADR 0044).
- Permissions: in Manual mode Claude asks with "Yes" (`allow_once`) and "No" (`reject_once`); the request names the tool call sent just before. `.claude/settings.json` = `{"permissions":{"defaultMode":"default"}}` starts a folder in Manual mode, for testing.
- Questions (AskUserQuestion) need `elicitation.form` in the client capabilities: a `tool_call` ("Asking for your input"), then `elicitation/create` in form mode tied to it. Each question is `question_N`, a `string` with `oneOf` or an `array` with `items.anyOf`, followed by an optional free-text `question_N_custom` titled "Other"; nothing is `required`, and the properties must be read in wire order. An empty accept reads to Claude as "no answer".
- Subagents: with `_meta: {"subagent-transcript": true}` in `initialize`'s client capabilities, a subagent's tool calls, text and thinking all carry `_meta.claudeCode.parentToolUseId` (tool calls also `toolName`); the Agent call's `subagent_type` is in its `rawInput`, maybe in a later update. Background subagents: the Agent call completes at once with "Async agent launched…", and the subagent ends with a `SubagentHandback` call whose `rawInput.message` is its report (its own output is only an acknowledgement). After `session/load` the Agent calls come back, but not a background subagent's steps or report. Messaging one: `SendMessage`'s `rawInput.to` is the subagent's `agentId`.
- Subagents (Claude Code 2.1.303): foreground subagents end with a `SubagentHandback` too, and their Agent call's output is then only a pointer ("This agent's report was delivered to you as a message from \"<agentId>\" (its SubagentHandback call)…"). The Agent call's `rawInput` comes in pieces over several `tool_call_update`s: `description`, `subagent_type`, `model` (`sonnet`, `haiku`, `opus`: the model option's values), `effort` (`low`…: the effort option's values), `prompt`, `run_in_background`; `model` and `effort` only when Claude picks them. The call's last update carries `_meta.claudeCode.toolResponse` with `agentId`, `agentType`, `resolvedModel` (`claude-sonnet-5-5`: the model it ran on, even when inherited), `totalDurationMs`, `totalTokens`, `totalToolUseCount`, `usage`, `handbackReport.text`; no effort. The subagent's own updates carry only `parentToolUseId` and `toolName`, no model. `session/load` replays the Agent call with its whole `rawInput` but no `toolResponse`, and no subagent's steps or report, foreground ones included. `async_task_*` updates go only to AIR clients; the ACP subagents RFD form (child sessions) only to clients that advertise `subagents` (see NOTES.md, Later ideas).
- Background shells (what a client that isn't AIR sees): a Bash call with `rawInput.run_in_background: true` completes at once; its last update's `_meta.claudeCode.toolResponse.backgroundTaskId` is the task's id and its output text says "Command running in background with ID: <id>. Output is being written to: <tmp>/claude-<uid>/<project>/<session>/tasks/<id>.output. You will be notified when it completes. To check interim output, use Read on that file path." That file fills as the command writes and ends with "[exited with code N]" or "[killed]". Claude 2.1.303 has no BashOutput (it said so, and reads the file with Read); stopping is the deferred `TaskStop` (found through `ToolSearch`), input `{task_id}`, response `{message, task_id, task_type: "local_bash", command}`. When a command ends, Claude gets a task notification the client never sees; Claude then runs a turn of its own, whose last `usage_update` has `_meta._claude/origin = {kind: "task-notification", producer: "session-task", runId}`, naming no task. `async_task_*` updates and the `_meta.jetbrains.air` `backgrounded` marker go only to AIR clients. A client that sets `_meta.terminal_output: true` in its capabilities gets Zed's terminal extension instead: every Bash call's output moves to `_meta.terminal_output` (content becomes a terminal reference), and a background command's `terminal_exit` (exit code null) comes when its task ends; Nushi doesn't use it, since it would change how every command reads. Background commands outlive Claude: after the daemon stopped (and Claude with it), `sleep 300` still ran, and its file never got an end line.
- Messaging a subagent: claude-agent-acp 0.94.0's child sessions (the RFD form) take only `cancel`; a v1 client has no way to prompt one. Claude Code 2.1.303's deferred `SendMessage` tool (`{to: <agentId>, message, summary, type: "message"}`) reaches a subagent by the id the Agent call's result gives (a background call's output ends "agentId: <id>"; a foreground one's names it in its pointer to the report; `toolResponse.agentId` too). It answers `{success, message: "Resuming agent …", resumedAgentId}`: a finished subagent runs again under its first Agent call (its steps carry that call's `parentToolUseId`) and ends with another `SubagentHandback`; a running one takes the message as it goes. Tried five times (three finished, one running, one finished after a daemon restart): Claude passed the text verbatim each time and the subagent acted on it; Claude then relays the reply in its own words, sometimes adding its own checks.
- Stopping subagents (2026-10-27; claude-agent-acp 0.94.0, Claude Code 2.1.310, recorded through a `node` that tees the adapter's stdin and stdout; trimmed recordings in `internal/features/chats/testdata/subagents`). Without the `subagents` client capability (Nushi before 2026-10-27) a client hears nothing when a background subagent ends unless it calls `SubagentHandback`, and 2.1.310's often don't: one ended with a plain message under its `parentToolUseId` ("done"), then Claude's turn of its own (`_claude/origin` `{kind: "task-notification"}`, naming no task) and the held prompt's answer. Stopped by Claude's `TaskStop` (`{task_id: <agentId>}`, found through `ToolSearch`), the call's `toolResponse` is `{message: "Successfully stopped task: <id> (<description>)", task_id, task_type: "local_agent", command: <description>}` and nothing else follows: no update for the Agent call, no task notification turn; the subagent's open tool call ends `failed` ("The user doesn't want to proceed with this tool use…"), or completes if it was about to. A task already ended makes `TaskStop` fail with "Task <id> is not running (status: killed)" (Claude may report that as "it came back as killed"). Steps are keyed by the launching Agent call's id (`parentToolUseId`); a subagent started after stopping one with a similar description had only its own (the owner's "both show 63 tool calls" wasn't reproduced; a `SendMessage` to the stopped one would run it again under its first call, as below).
- With `clientCapabilities.subagents: {}` (ACP's subagents RFD; Nushi since 2026-10-27) the adapter uses its "rfd" form: each subagent is a session of its own whose id is its `agentId`. On the parent's session, `subagent_update {sessionId: <child>, title, description, capabilities: {cancel: {}}, state: {state: "running"}}` announces it, then the child's first `session_message` has `messageId` = the Agent call's id; the subagent's tool calls, text and thinking come on the child's session, still with `_meta.claudeCode.parentToolUseId`; the Agent call itself stays on the parent's. Its end is `subagent_update` with `state: {state: "idle", stopReason: …}`: `end_turn` when done, `cancelled` when stopped (by `TaskStop`, by `session/cancel` on the child, or with the turn), `error` for a failure; `{state: "idle"}` with no reason when the adapter can't say (its process went). `session/cancel` with the child's session id stops that subagent alone (the adapter's `query.stopTask`), idle or mid-turn, foreground or background, and the parent's turn goes on (a foreground one's Agent call fails "[Request interrupted by user for tool use]" and Claude's turn goes on with that); for a background one Claude gets a task notification and answers it on its own, briefly. `perTaskStopAffordance` is implied. `session/load` announces every child again (running), replays its steps on its session, then each child's end: the last task notification's status, else `cancelled` if the user stopped it, else its foreground launch's result (an error result naming no stop reads as `failed`, so a subagent stopped with the turn replays `error`), else idle with no reason; a background subagent killed with the agent replays `{state: "idle"}`. The capability changes nothing else Nushi reads (the held turn, `usage_update`s, the Agent call's own updates). The other forms: AIR's (`_meta.jetbrains.air` with `nativeSubagentSessions`) and its async tasks (`asyncTasks`: `async_task_*` updates and `_session/async_task/stop` for background commands, never `local_agent`) both switch the adapter to AIR's behaviour throughout.
- Stopping a background command: there is no client-side stop for a client that isn't AIR. Claude's `TaskStop` with the command's background task id ends its file with "[killed]" and answers `task_type: "local_bash"`; Claude gets no task notification for it. Killing the command's process group from outside (it runs as `zsh -c …` in a group of its own under the `claude` process, its output file open) ends the file "[exited with code 144]" and Claude, notified, reports that it failed.
- A background command's process (Claude Code 2.1.312, seen with `ps` and read in the binary; the commands made up): Claude Code runs every Bash command as `<shell> -c [-l] <script>` (`-l` only without a shell snapshot), detached, so the shell leads a process group of its own under the `claude` process; a pipeline's or subshell's fork has the same command line but isn't the group's leader. The script is Claude Code's steps joined by ` && `: `source <snapshot> 2>/dev/null || true`, `setopt …` (zsh) or `shopt -u extglob` (bash), an `unalias`, then `eval <command> < /dev/null` (no `< /dev/null` for a heredoc or a command reading `<` itself), then `pwd -P >| <tmp>/claude-<hex>-cwd`. The command is quoted in single quotes, each `'` as `'"'"'`, newlines kept, backslashes as written (`echo a\\b "x" !` gave `eval 'echo a\\b "x" !'`); `CLAUDE_CODE_SHELL_PREFIX` wraps the whole script, and `>NUL` becomes `>/dev/null` first. Nushi finds a command's shell by unquoting the eval back to the call's input (ADR 0065).
- A background command killed from outside (2026-10-29, Claude Code 2.1.312 as the session building it ran its own commands): SIGTERM to its group ends the file "[exited with code 144]", SIGKILL "[exited with code 1]". Claude Code's task status is `failed` (only its own stops, `TaskStop` or an interrupt, give `killed`: "was stopped"), and Claude gets `<task-notification>` with `<status>failed</status>` and `<summary>Background command "<description or command>" failed with exit code 144</summary>`, the output file's path, no output; delivered at once into a running turn, else as a turn of its own (`_claude/origin` `task-notification`). So the client's own record of the end is the file's last line; Claude knows only that the command failed. Nushi marks the row "stopped" itself and tells Claude in a note before the next prompt.
- Stop as a prompt (2026-10-29): "Stop background task <id>: call TaskStop with task_id "<id>", then reply only "stopped" or "not running"." for subagents, and for commands Nushi can't find. Not yet tried live; the earlier prompt (2026-10-27), which named the task and said "Do nothing else", took `ToolSearch`, `TaskStop` and a one-line reply.
- Steering: `initialize`'s top-level `_meta.steering.supported` (not `agentCapabilities._meta`, which has `claudeCode.promptQueueing`) advertises `_session/steering`, answered `injected` while a turn runs or `promptRequired` (doing nothing). An injected message pre-empts the model and moves a foreground tool to the background, so Nushi steers right after a tool call ends; the running prompt ends once the steered messages are answered; the adapter echoes nothing.
- Code review findings (2026-10-26, `/code-review medium` on a throwaway repository, ACP recorded through a `node` that tees the adapter's stdin and stdout). Claude Code has a `ReportFindings` tool (input `{level?, findings: [{file, line?, summary, short_summary?, failure_scenario, category?, verdict?, outcome?}]}`, 32 findings at most, `file` repository-relative; it answers "N findings reported."), and the adapter offers it (the `claude_code` tool preset) and has a reporter for it. But Claude Code's `/code-review` uses it only when `CLAUDE_CODE_REPORT_FINDINGS` is set in its environment (and the output format isn't text or JSON, and the tool is in the session's tools); nothing in ACP, no client capability or `_meta`, turns it on, and the adapter never sets it. Without it the review ran as a forked command (its message's `_meta.claudeCode.parentToolUseId` was `forked-command-code-review`, with no tool call of that id) whose message was the findings as a fenced JSON array, followed by a second message (a UUID `messageId`) listing them again as Markdown. ## Go agent (unverified until recorded)

Nushi's own ACP agent for Claude (`claudeacp` on `claudeagent`, [ADR 0066](../adr/0066-claude-through-nushis-go-agent.md)), run with `NUSHI_CLAUDE_ADAPTER=go`. Nothing here has been seen with a live `claude`: it is what the official SDKs do (the Python SDK's source), what Claude Code 2.1.312's schema and binary say, and the adapter's behaviour as read in its source. The tests run on a fake claude and hand-written cassettes. A point moves into the sections above once a recorded run (a fake Messages API, a throwaway `CLAUDE_CONFIG_DIR` and `HOME`) shows it.

**How it runs claude**
- One `claude` a session, the user's (`CLAUDE_CODE_EXECUTABLE`), with no `-p`: claude runs non-interactive whenever its stdout isn't a terminal. Arguments: `--output-format stream-json --verbose --input-format stream-json`, `--session-id=<the ACP session's id>` (so the ids, the transcripts and `claude --resume` are the adapter's), `--setting-sources=user,project,local`, `--include-partial-messages`, `--replay-user-messages`, `--allow-dangerously-skip-permissions` (not as root without `IS_SANDBOX`), and `--permission-prompt-tool=stdio` once it answers permissions; never `--bare`.
- Environment: the chat's, without `CLAUDECODE` and `NODE_OPTIONS`, plus `CLAUDE_CODE_ENTRYPOINT=sdk-cli` (claude's own value for a run with no official SDK, as under the adapter), `CLAUDE_CODE_EMIT_SESSION_STATE_EVENTS=1` and `CLAUDE_AGENT_SDK_CLIENT_APP=claudeagent-go/<version>` (claude's User-Agent).
- Each claude runs in the agent's process group, as the adapter's does, so the daemon's kill of the agent's group (after `stopGrace`) takes claude and what stays in its group, its stdio MCP servers and its hooks; not its Bash commands, background ones included, which lead groups of their own (above) and outlive the kill, as they did under the adapter; the agent's own close (an interrupt, at most 2 s, then stdin's end and 2 s more) fits within that grace. No version is pinned: the agent logs `claude --version` at each start (INFO, `msg=claude version=…`), and claude's stderr at INFO (a few lines a second a session). An `initialize` answer naming no account is a WARN: a claude started without the user's login.
- A resume claude quits on before answering `initialize` is -32002 only when `claudeagent/sessions` finds no transcript of it any more; otherwise an internal error with the end of claude's stderr, so the session isn't taken for gone.

**What it relies on, not yet seen**
- A prompt's turn starts at claude's echo of its user message (`--replay-user-messages`) and ends at the first top-level `result` after it, unless that result's `origin.kind` is a task notification's, a peer's, a coordinator's or an observer's and it names none of the waiting prompts (`user_message_uuids`). Claude folds queued prompts into one turn and names them there.
- `session_state_changed: idle` after a turn started, with no result, fails the turn (`no_result`). A cancel interrupts claude and the turn ends `cancelled` at its next result or idle, or after 30 s.
- Usage: `{used, size}` from each top-level `message_start` and `message_delta` (input, output and both cache counts), the window from the result's `modelUsage[*].contextWindow` (kept for the agent's later sessions on the same backend and model, as the adapter keeps it), else claude's answer to `get_context_usage` (`detail: "summary"`, `rawMaxTokens`), asked without waiting as claude starts and after a model change unless that window is kept, as the adapter asks it (both write it right after `initialize`'s answer; a usage update sent with the guess before the answer is sent again), else 1,000,000 when the model's names say `1m`, else 200,000; cost and `_claude/origin` at every result that followed a model call (a top-level message's counts, or tokens in the result's `usage`), `{kind: "human"}` when a prompt's result has none; none at a result without one, as the adapter (below).
- A turn that streamed no text shows its result's text, as for a slash command claude answers itself.
- `session/load` resumes claude (`--resume=<id>`) and replays the transcript as `claudeagent/sessions` reads it (the chain from the last message, from the last compaction's summary on; meta records left out): user text under the record's uuid, cleaned of the command and context tags claude-agent-acp cleans, a command as typed, `/context`, `/compact` and the like left out; the model's text and calls under the API ids; no usage. Subagents' transcripts (`<id>/subagents/agent-<agentId>.jsonl`, the call from their `.meta.json`'s `toolUseId`, else the call's `toolUseResult.agentId`) replay on their sessions, and their ends come from `<task-notification>`s' `<task-id>` and `<status>` in user messages, which assumes claude keeps those in the transcript as non-meta user text. Fork-at takes the last record of the message named, on any branch and from before a compaction too. `session/delete` waits for claude's exit before deleting.
- Subagents, as recorded (2026-10-30; Claude Code 2.1.312 through claude-agent-acp 0.94.0 with a fake Messages API, the `subagent-*` and `sendmessage` parity scenarios): every Agent call ran in the background, `run_in_background` or not (`task_started.is_backgrounded: true`, the call's result "Async agent launched…" at once), so a "foreground" subagent too outlives a cancel of the turn. `session_state_changed: idle` came only once no task ran and no notification waited: never after the result while a subagent ran on or a notification turn followed (`subagent-foreground`, `-background`, `-stop-turn`, `sendmessage`), and after the result when `TaskStop` had ended the last one (`subagent-stop-taskstop`). So rule 4 (idle without a result) never met a turn here. A subagent's end is `task_updated {patch: {status}}` then `task_notification` (`completed`; `stopped` after `TaskStop` or `stop_task`, with `task_updated` saying `killed`), both before the next result. The notification then reaches the model as a turn of its own (`result.origin {kind: "task-notification", producer: "session-task", runId}`) when claude is idle, kept in the transcript as a non-meta user message `<task-notification>…` with that origin; delivered into a running turn it is an `attachment` record of type `queued_command` instead, and one queued when the session closed only a `queue-operation`. A notification turn can run while the client's next prompt waits: claude says the prompt `queued` (`command_lifecycle`) and starts it after that turn's result. A cancel that lands while claude waits on the Agent call's PostToolUse hook: claude sends `control_cancel_request` for the hook, the call's result is "The user doesn't want to proceed with this tool use…" (`is_error`), yet the subagent runs on, and no task event says so. The tool's result is claude's rejection text (`is_error`), then a user text `[Request interrupted by user for tool use]`, then a `result` (`error_during_execution`, `is_error`, `terminal_reason: aborted_tools`, naming the prompt), then idle. The prompt is answered `cancelled` at that result.
  - A prompt queued behind a running command and then cancelled: the adapter writes `cancel_async_message` for it, then the `interrupt`, waiting for neither answer. claude answers `{cancelled: true}` and says `cancelled` in `command_lifecycle`, and the prompt never reaches the API.
  - Permission suggestions for a command are its exact text (`addRules`, `localSettings`), not a prefix, and the same command isn't asked again once allowed. For `mkdir` in the session's folder they also add that folder (`addDirectories`, `session`) and switch to `acceptEdits` (`setMode`), with `blocked_path`. The adapter offers no "don't ask again" then, since its label can't say a mode change. A refused command's result is `User refused permission to run tool`, fenced plainly by the adapter, as any error for a client without terminals.
  - `can_use_tool`'s input is claude's parse of the streamed one. AskUserQuestion's comes with `options` before `multiSelect`. The adapter shows the streamed input and doesn't show the call again.
