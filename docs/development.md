# Development

How to build, run and test Nushi from source. The rules for working in this repository (commits, size limits, words, docs) are in [AGENTS.md](../AGENTS.md); the decisions are in [`docs/adr/`](adr/README.md), the security notes in [`security.md`](security.md), the plans in [GitHub issues](https://github.com/afrase/nushi/issues), the decisions still open in [`roadmap.md`](roadmap.md).

## What you need

- Go (current stable) and Flutter on `PATH`.
- For `make gen`, nothing more: it activates the Dart protoc plugins at the versions it pins, and buf runs through `go run`.

## Make targets

```sh
make run         # starts nushid in the background (if it isn't running), then the app
make stop        # stops nushid
make lint        # the linters and format checks, below (lint-go, lint-dart, lint-linux, lint-windows, ci-changes.sh's self-test)
make check       # lint, every test and the desktop build: the one check before a push
make test-go     # Go's tests (also test-packages, test-app, test-web without Chrome a skip, test-window)
make test-timings RUN=<id>  # app/test/timings.tsv from that CI run's app shards
make gen         # regenerate the API code after editing proto/
make lines       # hand-written line counts
make package     # a release "Nushi.app" with nushid inside (signed: Install, below, says with what)
make install     # package, then copy it to ~/Applications (Linux: package-linux, then its install.sh)
make package-linux  # Linux's package, app/build/linux/nushi (tools/package-linux.sh)
make icons       # redraw the app icon and the mark (tools/icongen)
make adapters    # an adapter's lockfile again after its version changed
make relay       # the relay, bin/nushi-relay
make relay-web   # the relay with the phone's web app built in, as a release's
make web         # the phone's web app, into app/build/web
make screenshots # the README's screenshots, into docs/images
make renders TEST=test/chat_spacing_test.dart  # its windows as PNGs, into app/build/renders
tools/release.sh 1.2.0   # a release's files into dist/, as the release workflow builds them
                         # (or one part: app, relay, web, linux)
tools/linux-smoke.sh dist/nushi-1.2.0-linux-amd64.tar.gz  # install and start it, as CI does
```

- With `make run`, start and stop the daemon yourself.
- Debug and Profile builds of the Mac app are `com.nushihq.Nushi.dev`, so Homebrew's reopen after an upgrade (`open -b com.nushihq.Nushi`) opens the installed release, not a build in `app/build`. Their settings (`~/Library/Preferences`) are the dev id's.
- `make package` checks the bundle's layout and signatures (`tools/check-bundle.sh`); `make package-linux` the Linux package's layout, nushid's version against the app's, and the newest glibc it needs (no newer than `NUSHI_GLIBC` when set).
- To try a build beside a Nushi that's in use, give both another data folder: `NUSHI_DATA=~/Library/Application\ Support/Nushi\ Dev make run` (and the same for `make stop`). On Linux the usual folder is `$XDG_DATA_HOME/nushi` (else `~/.local/share/nushi`), `make app` runs `flutter run -d linux`, and `make stop` needs psmisc's `fuser`.

## Lint

`make lint` runs:

- golangci-lint (with gofmt and goimports) and govulncheck;
- `make lint-linux`: every Go package linted (golangci-lint, which type-checks it, tests included, and vets it) with `GOOS=linux CGO_ENABLED=0`, so macOS-only code outside a `_darwin.go` file fails (ADR 0097) and the `_linux.go` files, which the Mac's lint never sees, are linted (ADR 0101);
- `make lint-windows`: every Go package built, vetted and linted (golangci-lint on amd64, `unused` off) with `GOOS=windows CGO_ENABLED=0`, tests included, so a Unix-only call outside a `_unix.go` or `_unix_test.go` file fails and the `_windows.go` files and their tests are checked on any OS (ADR 0124);
- `tools/native-edge` (first in `make lint-dart`): a platform channel or message (a `BinaryMessenger`, a `MethodCall` or its codec, `SystemChannels`) or `dart:ffi` in the app's or a Dart package's `lib` outside a `*_macos.dart`, `*_linux.dart` or `*_windows.dart` file fails, named with its line, as do `webview_flutter_wkwebview` outside a `*_macos.dart` file, `dbus` outside a `*_linux.dart` one, `url_launcher` outside a `*_macos.dart` one and `web_views.dart` (the phone's web path; Linux opens links through its runner, ADR 0104), and a platform's file named (an import, export or part) anywhere but in that platform's own files and in `main.dart` (only `native_macos.dart`, `native_linux.dart` and `native_windows.dart`); protoc's and Connect's output is left out (ADR 0097, 0104, 0125);
- `tools/design-check` (next in `make lint-dart`): app code that goes around the shared pieces of [`docs/design.md`](design.md) fails, named with its line: a raw `Tooltip(`, a Material button, an `AlertDialog(` outside `nushiDialog`, a tooltip's shortcut in brackets or after spaces (`withKey` instead), a `Color(0x…)` or a `Colors.<name>` other than `transparent`, a `fontSize:` number, a raw `SnackBar(` (`showToast`), a `Duration(milliseconds: …)` outside `motion.dart` (its `Motion` or `Waits`), a corner as a number (`Radius.circular(6)`, `radius: 6`; a radius token, ADR 0110; `// not a corner: <why>` keeps a size that isn't one) and a number given to `ui(size:)` or `code(size:)` off the type scale (design.md's Type). The controls' files (`controls*.dart`, but for durations, corners and the type scale), `theme/` and generated code make the pieces and are left out; a deliberate use stays with `// design: <why>` on its line or alone on the line above;
- `tools/test-shards -check` (next): every app test file in exactly one shard of its set for any shard count, no file that builds Go or tests Linux in the macOS set (the files with goldens), and `app/test/timings.tsv` well formed; it notes how many files the table lacks;
- `buf lint`, `buf breaking` (WIRE, ADR 0004: a field removed or renumbered without its number reserved fails) against the commit the branch grew from (`git merge-base HEAD origin/main`; `BREAKING_BASE=<ref>` for another, CI's change's base), and `buf format`;
- `flutter analyze` and `dart format`, for the app and each package.

`make check` runs it, the tests and the desktop app's build (`tools/check`): the app's suite (`--concurrency 3`) and then the web's tests in one lane, the lints and the other tests in another beside it, then `flutter build macos` (`linux` on Linux). A failure stops nothing, so one run shows every failure; each step's log is in `bin/check-logs`.

**Go.** golangci-lint and govulncheck are pinned in their own module, `tools/lint/go.mod`. `make lint` builds them into `bin/` and runs them: nothing to install, and the daemon's `go.mod` doesn't take their dependencies.

- `.golangci.yml` turns every linter on, and lists each one that's off with the reason.
- govulncheck checks the daemon, the relay and the tools against vuln.go.dev (so `make lint` needs the network), and fails on a vulnerability the code calls.
- The Go version is the `go` line in `go.mod`, which the go command fetches if yours is older.
- To format: `bin/golangci-lint fmt ./...`.

**Dart.** Every package and the app include [very_good_analysis](https://pub.dev/packages/very_good_analysis) (strict casts, inference and raw types, and nearly every lint rule), then `analysis_options.yaml` at the root, which adds a few rules and turns off the ones that don't fit, each with why. The app also turns off `public_member_api_docs`, since it isn't a library. `dart fix --apply` in a package fixes much of what it reports.

### Lint exclusions

The whole rule (ADR 0040; AGENTS.md has it in brief). A report wrong for one line: `//nolint:<linter> // <why>` on it, or on the function's line when it covers the function (contextcheck's mark on a function that rightly starts its own context stops the report spreading to callers); nolintlint refuses one without both, or one that silences nothing. Exclude by path in `.golangci.yml`'s `exclusions.rules` only where a whole package or kind of file is what the linter reports on (tests' temp files for gosec, the proto int32s), with a comment why; `disable` a linter only when it doesn't fit the code at all, the reason on its line. No comment needed for `_ = json.Unmarshal(…)` on an agent's payload (best effort; what's missing stays zero) or `defer f.Close() //nolint:errcheck // read-only`. Dart: `// ignore: <rule>` below a comment saying why, `// ignore_for_file:` when the whole file is about it; a rule that doesn't fit goes `false` in `analysis_options.yaml` with the reason. govulncheck: a standard-library finding is fixed by the `go` line's patch version (`go.mod` and `tools/lint/go.mod`), a module's by `go get` of the fix; one with no fix goes under [Security notes](security.md) with its id.

## ACP

Agents are spoken to through the library [`github.com/afrase/acp-go`](https://github.com/afrase/acp-go) (its `unstable` package), at the version in `go.mod` ([ADR 0041](adr/0041-acp-through-acp-go.md)).

To change it and Nushi at once:

1. Clone it beside Nushi and run `go work init . ../acp-go` here. The `go.work` (ignored by git) makes Nushi build with your checkout.
2. Remove it to build with the tagged version again.
3. Run `go get github.com/afrase/acp-go@vX.Y.Z` once the library has the release you need.

With a `go.work`, `make lint` builds golangci-lint into `bin/` because `go tool -modfile` refuses a workspace; before committing a version change, `GOWORK=off make check` against the tag in `go.mod`. A library fix is its own release there, then `go get` here.

The same goes for Claude's library, `github.com/afrase/claude-acp-go` (`go work init . ../claude-acp-go`), and Codex's, `github.com/afrase/codex-acp-go` (`go work init . ../codex-acp-go`).

## CI

CI (`.github/workflows/ci.yml`) runs the same parts as `make check`, as parallel jobs, in about 5–6 minutes when it runs them all (ADR 0129):

- on macOS: Go's lint and tests side by side (`make -j2`) with the window's placement maths, and the app's test files that need a Mac (those with goldens, and the Mac's fonts) in three shards (`make test-app SET=macos SHARD=1/3`);
- on Linux: the protos' and Dart's lint (with `tools/native-edge`), the Dart packages' tests, the web app's end-to-end test in Chrome (`make test-web`) and then the relays with the web app built in as a release builds them (`tools/release.sh 0.0.0-ci relay`, so a Flutter bump without `make web-fonts`, or `app/fonts` changed without `make web-cut`, fails here rather than on a release), every Go package's tests (`make test-go`, with bubblewrap from apt for npm's sandbox and AppArmor's rule on unprivileged user namespaces off) and `go mod tidy -diff`, and beside them `make lint-linux` and `make lint-windows` (ADR 0101, 0124);
- on macOS, when the change touches `app/macos`, the app's plugins (`app/pubspec.*`), `cmd/`, the Makefile, `tools/`, `packaging/` or CI: the Mac app packaged as a release packages it (`tools/release.sh 0.0.0-ci app`, signed ad hoc, build only; not in the release's call, whose app job is the same build);
- on Windows: the daemon built, and the Windows tests listed under Windows below (ADR 0124); and when the app changes, the Windows app built (`flutter build windows` in `app/`, build only: the one place its C++ runner compiles, fetching WebView2's pinned SDK; nothing of it runs, ADR 0125);
- the Linux app (ADR 0104): every other app test file, in three shards (`make test-app SET=linux SHARD=1/3`; a golden there fails), and on each architecture (Ubuntu 22.04, amd64 and arm64) its package built as a release builds it (`tools/release.sh 0.0.0-ci linux`, glibc 2.34 at most), installed into a throwaway home and started on a virtual display until it connects to the daemon it started (`tools/linux-smoke.sh`, whose screenshot is the job's artifact), and on amd64 the runner's channels (`tools/linux-channels.sh`).

**Which app test files run where.** `tools/test-shards` puts each file in one set: the macOS set is every file that calls `matchesGoldenFile(` or reads the Mac (`Platform.isMacOS`, `/System/Library/`), the Linux set the rest. Each set is split into its matrix's count of shards by `app/test/timings.tsv`, slowest file first to the least loaded shard, and each shard starts its slowest files first. CI runs each file's tests in a random order (`--test-randomize-ordering-seed=random`), as it shuffles Go's: a test that needs the one before it fails there. A failed shard's log starts with the seed; `make test-app FLUTTER_TEST_FLAGS=--test-randomize-ordering-seed=<seed>` runs that order here. A golden belongs in the test file itself, so the tool sees it; one it misses fails its Linux shard. `make lint-dart` runs `test-shards -check`, which fails on a file in the wrong set or a split that drops or repeats one. The table only balances the shards: rewrite it with `make test-timings RUN=<id>` from a CI run of every job (each app shard uploads its times) when `-check` reports more than 30 files missing from it, or when one shard runs more than a quarter longer than its siblings over three runs, and commit it on its own.

**What a change runs.** The changes job (`tools/ci-changes.sh`) reads a pull request's whole branch or a push's own commits. Docs (`docs/`, the root's Markdown, `LICENSE`) and the promo site (`site/`) run nothing, Go's folders all but the golden shards and the Windows app's build, the app's and the Dart packages' all but Go's four jobs, the Mac app's build only what it reads (`app/macos`, `app/pubspec.*`, `cmd/`); anything else (CI, the Makefile, `tools/`, protos), any path it can't place, and any other event run everything. `tools/ci-changes.sh --self-test` checks its table (`make lint`). Main's runs don't cancel each other, so each push's change is tested. The release checks a commit only with a run that skipped no job but the Mac app's build (its own app job is that build), or runs CI in full itself: a push's run, or a pull request's into `main` while `main` is an ancestor of the commit (then the merge it tested has the commit's files), so a beta reuses its pull request's green run.

### The daemon's tests on Linux

On a Linux machine (x86_64 or arm64) with Go: `make test-go` (or `go test -race -shuffle=on ./...`) and `make lint-linux`, as CI's Linux job runs them. Some tests need programs there and skip, naming them, without (in CI they fail instead, `testcheck.Lacks`, so the Linux job installs them): bubblewrap (`bwrap`, npm's sandbox; it must be able to make user namespaces, so on Ubuntu `sudo sysctl -w kernel.apparmor_restrict_unprivileged_userns=0`), `flock` (util-linux), `gio` (a skill to the Trash), `dbus-daemon` (the keychain's fake Secret Service); `script` (util-linux) is assumed, and zsh and fish, if there, are tried as login shells. The live keychain test against a real keyring, in a throwaway session with a throwaway home (a subshell, so your shell keeps its own; `HOME` is set before the lines that use it, since one `export` expands every word first):

```sh
go test -c -o /tmp/kc.test ./internal/keychain
(
  export HOME="$(mktemp -d)"
  export XDG_DATA_HOME="$HOME/.local/share" XDG_CONFIG_HOME="$HOME/.config" XDG_CACHE_HOME="$HOME/.cache" XDG_RUNTIME_DIR="$HOME/run"
  mkdir -m 700 "$XDG_RUNTIME_DIR"
  dbus-run-session -- sh -c 'printf test | gnome-keyring-daemon --unlock --components=secrets >/dev/null; NUSHI_KEYCHAIN_TEST=1 /tmp/kc.test -test.run TestKeychain -test.v'
  rm -rf "$HOME"
)
```

The Linux app's runner channels (`app/linux/runner`: the clipboard, default apps, the window), for real, in a debug build: `tools/linux-channels.sh` from the repository root, with Flutter, the Linux build's packages (clang, cmake, ninja, GTK 3's headers), `xvfb-run`, `dbus-run-session` and `xclip`; it opens nothing of the machine's (fake default apps in throwaway XDG folders) and passes other arguments to `flutter test`.

On a Mac, an OrbStack machine works (`orb create arch nushi-linux`; it can't see your files unless you copy them in). Under Rosetta (an x86_64 machine on Apple silicon) bubblewrap 0.13 can't mount anything ("Can't open source /: Function not implemented"), so npm's sandbox tests skip there unless an older `bwrap` is first on `PATH`; an arm64 machine or CI runs them.

On a Windows machine with Go (ADR 0124; no make or cgo needed): `GOOS=windows CGO_ENABLED=0 go build ./...`, as `make lint-windows` does, and `go test ./internal/procgroup ./internal/filelock ./internal/logs ./internal/shellenv ./internal/batchfile ./internal/terminal ./internal/proctree ./internal/listeners ./internal/footprint`, `go test -run 'TestAlive|TestOpenWindows' ./internal/claudehistory` and `go test -run 'TestOwnDataFolder|TestWTDefaultLine|TestMachineFragment|TestStopEvent' ./cmd/nushid`, the Windows tests so far (every package's tests build there, but the rest assume Unix: its paths, mode bits, signals). Clone with `core.autocrlf` false, or gofmt reports every file. `go build -o bin/nushid.exe ./cmd/nushid` runs on a short `NUSHI_DATA` (the socket's path has a limit); its API answers on `nushid.sock` over HTTP/2 without TLS, which neither Git for Windows' curl nor Windows' own speaks to a Unix socket, so call it from a few lines of Go (`http.Protocols`' unencrypted HTTP/2 and a `unix` dialer).

The app on Windows (ADR 0125) needs Flutter, Visual Studio's Build Tools with the C++ desktop workload, and Developer Mode on (Settings › System › For developers: Flutter links plugins by symlink). `cd app && flutter build windows --debug` builds `build\windows\x64\runner\Debug\nushi.exe`; build the daemon beside it (`go build -o app/build/windows/x64/runner/Debug/nushid.exe ./cmd/nushid`) and the app starts it on `%LOCALAPPDATA%\Nushi`, or `NUSHI_DATA`. Rebuild both after pulling: a running `nushi.exe` can't be overwritten, and a running `nushid.exe` neither: Restart daemon (Ctrl+K) stops it and starts the new one (ADR 0134), or end it in Task Manager. Start it from Explorer or a shell of your own, not a packaged (MSIX) app's terminal: Windows redirects that app's children's `AppData` into its package folder, and a Unix socket made there can't be connected to, so the app says the daemon isn't answering (a `NUSHI_DATA` under `%TEMP%`, which isn't redirected, works there). `flutter test test/fonts_windows_test.dart test/shell_windows_test.dart` are the app's Windows tests, and `test/*_windows_test.dart` the rest (the spell checker's, the stop event's and presenting's run only there); `NUSHI_DATA=C:\nd flutter test integration_test/windows_web_views_test.dart -d windows` runs the runner's WebView2s for real (pages and diagrams, ADR 0134; diagrams after `make mermaid`, or `go run ./tools/mermaid`). The first build downloads WebView2's SDK (below) into `build\windows`.

## Install, releases, logs

- **Install**: `make install` packages a release app (`make package`: the app, the daemon in `Contents/Helpers/Nushi Daemon.app`, signed with the first "Apple Development" identity in the keychain (or `NUSHI_SIGN`; ad hoc when there is none, and then the keychain asks again after every install), checked by `tools/check-bundle.sh`), puts it in `~/Applications`. The running installed daemon keeps the old build until it restarts: restart it only when no chat's agent runs (stop it by its PID, then `open -n -g "$HOME/Applications/Nushi.app/Contents/Helpers/Nushi Daemon.app" --args -login` as the app does, and check `nushid started … api=<n>` in `nushid.log`); otherwise say so: an app of API 77 on asks it to restart itself once nothing runs (ADR 0056). On Linux, `make install` runs `make package-linux` and the package's own `install.sh`: the package to `~/.local/opt/nushi`, its `.desktop` file (its `Exec` naming the package there) to `$XDG_DATA_HOME/applications` and its icons (`app/linux/packaging/icons`, drawn by `make icons`) to `$XDG_DATA_HOME/icons/hicolor`, as the release's tarball installs.
- **Releases** (ADR 0055): publishing a GitHub release (tag `vX.Y.Z` on `main`) runs `.github/workflows/release.yml` (about 5 minutes): the app (macOS), the Linux app (`nushi-X.Y.Z-linux-<arch>.tar.gz`, on Ubuntu 22.04 for amd64 and arm64: Flutter doesn't cross-build, and the oldest Ubuntu keeps the glibc it needs at 2.34), the relays with the web app built in (Linux, ADR 0113) in parallel jobs, each `tools/release.sh X.Y.Z <part>` (try it here: with no part it writes what this machine builds into `dist/`; CI builds and starts the Linux part, and builds the relay part, on every push, since the release can't run before one), and the commit checked (a passing CI run on it that skipped no job, else CI's own workflow, called, which runs every job); then the files attached to the release, and the cask (`packaging/homebrew/nushi.rb`) pushed to `afrase/homebrew-tap` with the `HOMEBREW_TAP_TOKEN` secret, for the latest release only. The run makes a published release a draft at once (the `draft` job) and publishes it again only once its files are attached and its casks written (`undraft`, before the tap is pushed; a pre-release stays one), so neither the update check nor the casks offer one without its files. A run that fails or is cancelled leaves a draft (`withdraw` makes sure): Actions › the run › Re-run failed jobs finishes it once what failed is fixed (a fix in the code needs a new tag; delete the draft first), and publishing the draft again builds it all again. A run by hand (Actions › Release › Run workflow) rebuilds a release's files and leaves it public or a draft as it was, as does a run on a release already public with its files (Re-run all jobs on a green run). `make package` stamps `NUSHI_VERSION` (else the newest tag's) and the commit count into the app, the helper and the daemon (`api.Release`, Ping's `version`), and builds for macOS 13 (`MACOS_MIN`). The lead architect cuts a release once CI is green on `main`, without asking; an agent working on a brief never tags, publishes or pushes to the tap.
- **Beta versions** (ADR 0108): a change to try before it's released stays a pull request, `main` merged into its branch. Its beta is a pre-release cut from the branch's head, `gh release create vX.Y.Z-beta.N --prerelease --target <branch> --notes-file <notes>` (X.Y.Z the release it would be), which runs the same workflow; `gh release create` without `--prerelease` would make it the latest release. The workflow updates the tap's `nushi@beta` cask for the newest beta, and both casks for the latest release (`tools/cask.sh which <tag> <latest> [<newest beta>]` says which, `write` writes one from `packaging/homebrew/nushi.rb`); a Nushi that cask installed, or one that is a beta, is told of it. Accepted, the pull request merges and `vX.Y.Z` is released from `main`; dropped, it's closed. A beta never writes stored data the latest release can't read, and the relay and the phone's web app are deployed from releases only.
- **Debugging from the logs**: `nushid.log` in the data folder (Settings › Logs; `.1` and `.2` are older, 10 MB each), `app.log` beside it for what the app wrote while the daemon didn't answer; `NUSHI_LOG=debug` or the Settings switch for debug lines. One chat: `grep 'chat=<id>' nushid.log` (side chats name theirs); an agent's processes: `grep 'pid=<pid>'`; a recovered panic's stack: `printf '%b\n' "$(grep panicked nushid.log)"`. What each failure looks like: `docs/history/debugging-from-the-logs.md`.

## Goldens and renders

- **Goldens** (`app/test/goldens`) pin a component on its own (a card, a row, a menu, a dialog, a pane), in both themes. Full-window goldens are one per main view, with the sidebar hidden: the chat (`chat_spacing_test.dart`: 1700 with the details panel, and 720, where the layout narrows), the chat with its side panes (`right_panes_layout_test.dart`: the browser beside the rail, the rail tucked beside Files and the browser, the panes narrowed and over the transcript, the browser expanded, and 720), Changes (`related_worktrees_golden_test.dart`), the Pull request tab (`pull_tab_golden_test.dart`), Settings' General page, as the modal over the window (`settings_view_test.dart`), Jira (`jira_view_test.dart`), GitHub (`github_view_test.dart`), Chat history (`history_section_test.dart`), the empty window (`sidebar_hide_test.dart`), and on the phone the chat list and a chat (`phone_test.dart`; `message_pins_test.dart`'s pins). The sidebar is in its own goldens only (`sidebar_test.dart` and the like), so a change to it touches only those. A new view gets component goldens and renders; a window golden only if it's a main view without one.
- **Renders** are for looking at a view at full size while building it: `render(tester, find.byType(NushiApp), name)` in a test writes a PNG when `NUSHI_RENDERS` names a folder (`make renders TEST=…`), and nothing otherwise. They're never compared or committed, and a render is not a test: a test's checks run once, in the dark theme, and its light copy and any test that only draws a picture run only while rendering (`harness.dart`'s `renderThemes` and `lightCopy` for a theme loop, `renderTest` for a picture-only test, so none shows as skipped in CI, and `rendersOnly()` in a file of nothing else, whose one skipped test says to run `make renders` rather than `flutter test` on it ending in "No tests ran"; a test of a theme's colours, or a golden in each theme, keeps both). A render draws shadows as the app does; a golden doesn't (a test paints each shadow as a solid block, `debugDisableShadows`, so goldens are the same from machine to machine), so judge a shadow, and what floats on one, from a render. The tests of the window at 1700 and 720 (`frame_test.dart`, the shell with the sidebar shown and hidden, the details and a terminal; `jira_view_test.dart` and `github_view_test.dart`, their lists and an issue's and a pull request's pages; `settings_view_test.dart`, every page of Settings; `fork_chat_test.dart`, `related_worktrees_golden_test.dart`, `preview_tabs_test.dart`, `pull_merge_window_test.dart`, `project_rail_window_test.dart`, the sidebar's project tiles and Change tile…, and the project rail turned on, and others) render it.

## Screenshots

`make screenshots` draws the README's images (`docs/images/`) from the real app: `app/test/screenshots/readme_shots.dart` renders it on a fake daemon with made-up data (`demo.dart`), with the bundled fonts, at real window sizes, its shadows drawn as the app draws them (`withRealShadows`, as a render's). It isn't part of `make check`. Change the demo data there, never use real chats.

## Working notes

- **Claude's Go agent**: every Claude chat runs it (`nushid claude-acp`). Its parity tests replay scenarios in `internal/features/chats/testdata/claude-parity` (`go test ./internal/features/chats -run ClaudeParity`); `make claude-record` records them again through it.
- **Recording ACP by hand**: `testdata/subagents` in `internal/features/chats` were recorded through a `node` that teed claude-agent-acp's stdin and stdout, while Claude ran through it. For the Go agent, a dev daemon with `NUSHI_SHELL_ENV=off` and `PATH` starting with a `claude` script that runs `tee -a in.jsonl | <the real claude> "$@" | tee -a out.jsonl` records claude's side; `claude-tee` (the library's `claudetest/cmd/claude-tee`) does it as a cassette.
- **The fake agent in the app**: build `internal/acptest/fakeagent`, put a `node` that execs it and a `codex` (any script) first on `PATH`, fake Codex's setup (`<data>/agents/codex/node_modules/@agentclientprotocol/codex-acp/package.json` = `{"version": "2.2.2", "bin": {"codex-acp": "dist/index.js"}}`, as `app/test/e2e_rig.dart` does), and start a daemon with that `PATH` and a short `NUSHI_DATA`; its chats are Codex chats. Prompt words: `permission`, `question`, `think`, `pwd`, `many`, `plan`, `tool`, `run`, `stderr`, `garbage`, `safeguards` (a response stopped by Claude's safeguards), `usage` (a cost a quarter dollar more each turn, with tokens, a model and a rate limit), `wait` (until stopped); `FAKEAGENT_LOAD_DELAY` slows `session/load`.
- **Codex, Ante and omp by hand**: a dev daemon with `CODEX_HOME` (holding `docs/user/codex-config.md`'s config) or `ANTE_HOME` at a temp folder, `HOME` at one for omp (`~/.omp`), and `FIREWORKS_API_KEY` read from `fish -l -c` (real `HOME`) inside the launching script, never on a command line or in a file. Quit the dev app before stopping the dev daemon (an app that finds none starts its bundled one with the real `HOME`).
- **opencode by hand**: never with your own `HOME`. `env -i HOME=<scratch> PATH=/opt/homebrew/bin:/usr/bin:/bin:/usr/sbin:/sbin TERM=xterm-256color TMPDIR=<scratch> opencode …` keeps its config, data (the sessions and sign-ins), cache, state and tmp under the scratch folder; `TMPDIR` is there because `HOME` alone doesn't move its tmp. Run `opencode debug paths` that way first and check every path it prints. It has free models of its own, so a prompt there leaves this Mac; the facts were taken against a fake model on localhost, named as a provider in the scratch config ([OpenCode facts](facts/opencode.md)).
- **TUIs by hand**: a pty driver (Python's `pty`) answering the terminal's queries (cursor, device attributes, colours) and typing what's written to a FIFO runs Codex's and Ante's (`codex resume` too); a FIFO write blocks once the driver is gone. Set Codex's `check_for_update_on_startup = false` first (its prompt takes Enter and updates the global Codex). Claude's TUI stops at its trust prompt, and answering writes `~/.claude.json`: use `claude -p` (`--resume`). Headless: `codex exec`, `ante -p --permission-mode strict --session-save`, `omp -p`.
- **Terminals**: the shell is the login shell from `id -P`, never the daemon's `$SHELL`. fish 4 asks Primary Device Attributes at start and waits 10 s; the app answers queries in a replay only for a terminal it opened.
- **The window**: no agent clicks or types into it (AGENTS.md: no synthetic input). Screenshots are 2× points, current only while the window is in front. A phone by hand: decode the QR code from a screenshot (Vision's `VNDetectBarcodesRequest`) and pair from a Dart script on `packages/remote_transport`; a raw Connect call is a POST of `{}` (`content-type: application/json`) on its `makeRequest`.
- **The Dock and launchd**: `osascript -e 'tell application "System Events" to get name of every UI element of list 1 of application process "Dock"'` lists Dock items; `lsappinfo list` says why a quit app keeps one; `launchctl print gui/$(id -u)/com.nushihq.Nushi.daemon` shows the login item; `/usr/bin/log` (not fish's `log`) shows launchd's reasons.
- **The icon** ("the still lake"): `make icons` writes `app/macos/Runner/AppIcon.icon` (Icon Composer, Liquid Glass on macOS 26+), PNGs for older macOS and `docs/brand/`; `app/lib/logo.dart` draws the mark. `NSWorkspace.shared.icon(forFile:)` shows what macOS made of it; a deleted working folder fails actool until `pkill ibtoold`.
- **Slow diffs**: git runs with `GIT_OPTIONAL_LOCKS=0`, so a stale index stays stale (`git diff` ~0.16 s instead of ~0.02 s until a `git status`).
- **The web app's fonts** (`make web-cut`, `tools/webbuild/cut`): JetBrains Mono went from 79 to 54 KB with Brotli (2026-10-31) by losing its hinting and the `calt` ligatures `theme.code` turns off. Every character stays, as a fallback font would leave code's grid: Latin, Greek and the symbols alone would save only 9 KB more. The `wght` axis stays too: CanvasKit draws w600 and w700 through it, and a cut pinned to 400 (29 KB) came out far heavier, in fake bold. On CanvasKit the cut draws the same pixels as the whole font at w400, w600 and w700, and for all its 972 printing characters at w400 (run with `ui_web.TestEnvironment` not forcing the test font); on the VM the phone's goldens differ only by a fraction of a pixel on one `i`.
- **The phone in the iOS Simulator**: a simulator of your own (`xcrun simctl create`, deleted after), the relay and a dev daemon on localhost. Real touches and typing come from an XCUITest bundle whose test loops over commands in a file (`XCUIApplication(bundleIdentifier: "com.apple.mobilesafari")`, coordinates from SpringBoard; a hand-written `project.pbxproj` with one UI-testing target, `xcodebuild test-without-building`). The software keyboard needs the simulated hardware keyboard off (CoreSimulator's `-[SimDevice setHardwareKeyboardEnabled:keyboardType:error:]`; a safaridriver session turns it back on, and its synthetic taps don't count as a user's, so no keyboard). JavaScript in the page through the Web Inspector protocol on the `webinspectord_sim.socket` launchd_sim holds (binary plists: `_rpc_reportIdentifier:`, `_rpc_forwardGetListing:`, `_rpc_forwardSocketSetup:`, then `Target.sendMessageToTarget`; `launchctl kickstart user/foreground/com.apple.webinspectord` in the simulator after a boot): pair from a Dart script on `remote_transport` and put the record in IndexedDB. The 18.3 simulator opens Home Screen web apps in Safari ("In your region…"), so only a Safari tab is testable there. Another agent may have a simulator booted too: take the inspector socket your own `launchd_sim` holds (`lsof -U -a -p <its pid>`; its command line names the device's UDID), give the driver a command file of its own, and after a new build activate the waiting service worker (`postMessage('skipWaiting')`) before reloading, or the page stays on the old build. iOS 26.5's runtime (installed with `xcodebuild -downloadPlatform iOS -buildVersion 26.5`) runs Home Screen web apps as apps (Safari's ⋯ › Share › View More › Add to Home Screen; its own storage, so put the record in again); there XCUITest's drags never start Safari's edge swipe, but a path of XCTest's own does (`XCPointerEventPath` `initForTouchAtPoint:offset:`, `moveToPoint:atOffset:`, `liftUpAtOffset:` in an `XCSynthesizedEventRecord`, `synthesizeWithError:`; 0.4 s from x = 1). On a Flutter page a slower one (0.5 s to 330 points) is taken back by iOS about three times in eight, the same at 56c9bb4's build, and never on a plain page. A new tab per run: `simctl openurl` with a query of its own.
