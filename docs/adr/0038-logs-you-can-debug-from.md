# 0038. Logs you can debug from: slog's text format, a line per thing that happened, never what the user wrote

## Context
The daemon logged about 30 lines through Go's `log`, nearly all errors, into one `nushid.log` that grew forever; agents' stderr was mixed in with no chat or time; the app logged nothing. An agent's exit status was dropped, a panic `acp` recovered went back to the agent unlogged, and "why is this chat stuck" had no record of agents starting, sessions loading, sleep, wake or failed calls. The owner wants a crash, a hang or a misbehaving chat debuggable from the logs alone.

## Decision
- **Format: `log/slog`'s text handler** (`internal/logs`), `key=value` on one line per record: readable by eye, filtered with `grep 'chat=<id>'`. Not JSON: the log is read in a terminal or Console more often than by a program, quoted text stays short, and `grep` on `key=value` needs no tool. The home folder is written `~` in every value.
- **Attributes** so one chat's story can be pulled out: `chat` (and `side` for a side chat), `agent`, `session`, `folder`, and where they help `pid`, `rpc`, `took`, `ran`, `via`, `source` (`agent` for an agent's stderr, `app` for the app's lines).
- **Levels.** `INFO` by default; `DEBUG` with Settings › Logs › Debug lines (`settings.json`) or `NUSHI_LOG=debug`.
  - INFO: the daemon starting (version, build, API, data folder, PID) and stopping (why); an agent's process started (its command line, never its environment) and exited (code or signal, how long it ran, stopped by Nushi); `initialize` (the agent's name, version, the capabilities Nushi uses), `session/new`, `load`, `fork`; chats created, opened from a session, asleep, waking, reopened, archived, moved, rewound, deleted; turns started and ended (stop reason, how long); side chats; apps connecting and disconnecting; terminals opened, restarted, closed; remote access on and off, the relay's state, devices connecting, rejected, paired, revoked; agents found (when it changes), adapters set up and removed; each line of an agent's stderr.
  - WARN: an agent that died; an ACP call that failed (with the agent's error) or took 5 s or more (not a prompt or a question, which take what they take); an API call that failed (with its code) or took 5 s or more; a line from the agent that isn't JSON-RPC (its size only); a notification Nushi couldn't read; a chat that didn't reopen; the app's warnings.
  - ERROR: a panic `acp` recovered, with its stack; a chat whose agent quit; an adapter that didn't set up; the app's uncaught errors with their stacks; a handler's panic `net/http` recovered.
  - DEBUG: every ACP request both ways and every API call, with how long it took; notifications but `session/update` (each chunk of a reply is one); notifications Nushi doesn't follow.
- **Never logged:** message text, prompts, chat titles, tool input and output, file contents, terminal input and output, environment values, tokens and keys, the QR code and pairing secret or code. What an agent sends is logged by method, size and timing, never its body. The client token is masked wherever it would appear; every value is run through a redaction pass for known secret shapes (vendors' key prefixes, bearer tokens, JWTs, passwords in URLs, `NAME=value` and `"name": "value"` pairs whose name says key, token, secret or password, private key headers). A test runs a fake chat's turn at DEBUG with each kind seeded with a marker and greps the log.
- **Agents' stderr** is a record a line, cut at 2 KB, at most 100 lines then 10 a second (what's dropped is counted on the next line). It can contain anything: the redaction pass masks the secret shapes it knows; a prompt an agent echoed to stderr, a key of a shape it doesn't know, or an error message that quotes a file would still be logged.
- **Rotation by the daemon:** `nushid.log` rotates at 10 MB to `.1` and `.2`. Once it holds its socket, the daemon opens the log itself and points its stdout and stderr at it (`dup2`), again after each rotation, so the Go runtime's own crash output (a panic nobody recovered, `fatal error:`, `SIGQUIT`) lands in the current file; the launcher's `>>` catches only what comes before. A second daemon, which stops because one is running, never rotates.
- **The app** catches `FlutterError.onError`, `PlatformDispatcher.instance.onError` and its zone's errors, with their stacks, and logs starting (version), connecting, losing the daemon, an outdated daemon, restarts. Lines go to the daemon (`Log`, API 51) while it answers, else to `app.log` beside it in the same format, rotated the same way; at most 20, then one every 3 s.

## Consequences
- One file, one format, one chat per `grep`: a hang shows as a turn or `session/load` without its end line, a crash as `agent died` with its signal, a daemon crash as the runtime's text after the last record.
- An exception's own message can quote what it choked on; it reaches the log (an app error, an agent's error text). The redaction pass is a net, not a guarantee.
- Agents' own diagnostics are kept at INFO (Claude's adapter writes about 20 timing lines a start); a noisy agent is capped, not silenced.
- The relay keeps its own one-line log (`nushi-relay`, a separate binary); `log` remains only there, in the code generator and in a test peer.

## Alternatives considered
- JSON lines: easier for a program, harder to read; nothing reads the log but a person and `grep`.
- A log file per chat: easier to read one chat, but a crash or an API failure has no chat, and the order across chats is lost; the `chat=` attribute gives both.
- Leaving stderr to the launcher's `>>` and rotating by copy and truncate: loses lines written while copying, and a crash after a rename would land in a copy about to be dropped.
