# 0054. The phone is a web app on the Home Screen, with Web Push (amends 0034 and the push decision)

## Context
The owner decisions (`nushi-mobile-research.md`) said: a native iPhone app, free signing from Xcode until the $99 Apple Developer Program, then pings through APNs only. The owner can't get the program (payments fail; the account is tied to the US). iOS 16.4 and later give a web app added to the Home Screen Web Push with no developer account, no expiry and no re-signing. Everything else in the decisions stands: end to end with Noise, the relay a dumb pipe, notifications that say only what happened, no device modes, revocation and the Mac's on/off switch.

## Decision
**The phone is the Flutter app on the web** (`lib/phone_main.dart`, `lib/phone/`), reusing the Mac's chat widgets, added to the Home Screen (`display: standalone`). `make web` builds it; the relay serves it (`nushi-relay -web <folder> -origin <scheme://host[:port]>`).

**The relay** serves the built files from memory with a strict CSP (`default-src 'none'`; scripts, images, fonts and connections only its own, plus `wasm-unsafe-eval` for CanvasKit and inline styles, which Flutter's engine needs; Trusted Types required; no frames, objects or forms), `nosniff`, `no-referrer`, HSTS, the page and its loader and service worker never cached, hashed names for a year, and a write deadline so slow readers can't hold connections. The origin is https (plain http only on the same machine). ADR 0033's rule stays: a WebSocket with an `Origin` is refused, except, when it serves the web app, exactly that app's origin (as the browser sends it: lowercase, no default port). No other page can open one there.

**Pairing** happens inside the installed app: iOS keeps a Home Screen app's storage apart from Safari's. The cheapest robust way is a link: the Mac's Pair dialog gains Copy link, `https://<relay>/#pair?r=…&i=…&k=…&s=…`, the QR code's parameters in the **fragment**, which a browser never sends to a server; the user pastes it (Universal Clipboard) or AirDrops it (Safari then offers to copy it for the installed app). No camera scanner: Safari has no `BarcodeDetector`, and a Dart QR decoder is more code to carry than the link. The six-digit code check stays. The link must name the relay serving the page. The hello says `"kind":"web"`. Both the phone and the Mac show the daemon's key fingerprint, so a phone paired from a forged link (with someone else's daemon, 0034's table) shows another Mac's.

**Keys on the web.** The device's X25519 static key is made in the app and kept raw in IndexedDB with the pairing: the `cryptography` package's X25519 can't use a WebCrypto non-extractable key. So **script on the app's origin can take the key**, and with it be a paired device (code execution as you on the Mac, ADR 0034's table), until revoked. What limits that: the CSP (no inline script, nothing from other origins, Trusted Types), no third-party code, scripts or fonts in the app, an origin used for nothing else, Revoke on the Mac, and Forget this Mac, which unpairs the device there too and clears the service worker's caches. **A web client's code is only as trustworthy as whoever serves it: the relay's operator can serve altered code that sends the key away.** Use the web app only from a relay you run (here, the owner's Pi): with `-web` the relay's host is trusted for code, not only a pipe (0033). A WebCrypto key Noise could use (non-extractable) would stop a stolen key outliving the attack; the `cryptography` package can't. Noise itself is unchanged (0034); its test vectors run in Chrome too.

**Web Push from the daemon.** The daemon makes a VAPID key once (`vapid.json`, 0600). The phone asks its public key over the channel and subscribes only after a tap (`userVisibleOnly`), then sends its subscription over the channel (`SetPushSubscription`, only on a device's own channel); the daemon keeps it with the device in `devices.json`, and Revoke removes it. The daemon sends **directly** to the subscription's endpoint, RFC 8291-encrypted and VAPID-signed (RFC 8292), written from the RFCs on Go's standard library (smaller to audit than a library and its JWT dependency), and only when the endpoint is https on 443 at a known push service: `web.push.apple.com`, `*.push.apple.com`, `fcm.googleapis.com`, `updates.push.services.mozilla.com`, `*.notify.windows.com`; anything else is refused (no SSRF through a subscription). No gateway: the push services are the only third party, and they see only ciphertext, the time and the size.

**What a push says**: "Claude finished" when a turn ends (not one that was stopped, or that the next queued message follows), "Claude needs you" for a permission prompt, "Claude has a question" for a question, with the agent and the chat's id to open; nothing from the chat, padded to one size. None for a chat a connected device shows (`SetDeviceView`, which the phone repeats while it shows and which lapses after 40 s), none for side chats. A 404 or 410 from the push service forgets the subscription. Tapping one opens the app at that chat.

## Consequences
- No APNs, no Xcode, no expiry; the native app (0034's "phone app's job") is not built. A later native app pairs the same way (the QR code is unchanged) and could push through APNs beside this.
- The push services (Apple's for an iPhone) learn when a chat finished or asked, as ciphertext: timing, never content.
- The device key is as safe as the origin serving the app: weaker than a Keychain key behind Face ID (no app lock on the web).
- The web app works in any browser (Chrome on a Mac too), which makes it testable without an iPhone; the in-Safari, not installed, case only says how to install.
