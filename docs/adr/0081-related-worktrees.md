# 0081. A chat's related worktrees: git says what exists, the tool calls say whose

## Context
An orchestrating chat runs subagents in worktrees off main, and their work should show in the chat. Nothing told Nushi about those worktrees: a chat's `Worktree` is the one it runs in, and `chats.Subagents` is Claude's alone. Claude's own record is thin. A background subagent's worktree reaches ACP nowhere; `.meta.json` names it until a clean removal, and only for the Agent tool's `isolation`; a subagent can also run `git worktree add` itself, which leaves only its Bash input (`docs/facts/claude.md`). And a worktree goes: Claude sweeps a clean one, an orchestrator removes the rest.

## Decision
- **`git worktree list` for the chat's repository says what exists; the chat's tool calls say whose it is.** A listed worktree is related when a subagent's `Paths`, `Diffs` or shell input names it, absolutely or relative to the chat's folder, or when Claude says so (`worktreePath` in a foreground subagent's result, `.meta.json`). The first subagent to name one has it. git, not an agent's word, is what could cover other agents later.
- **Trust neither.** An agent writes `.git/worktrees/*/gitdir` as it writes `.meta.json`. A path counts only if git lists it and it is the top of a work tree whose `--git-common-dir` is the chat's, by real path; failing that, a known one is `removed`. Nothing here joins `Roots`.
- **A chat's own and other chats' worktrees stay out**, and so do those a chat's folder is in. The first chat to find a worktree keeps it.
- **The head is recorded at every look**, and a subagent's end is a look of its own, since a turn ends while background subagents run (ADR 0044). Looks also come with a turn's end, with `GetRelatedWorktrees`, and with a subagent's steps, at most every 5 s. A worktree that goes keeps its record as `removed`, so its commits can be diffed while git keeps them. The base is where it left the chat's branch or the repository's default branch (either copy), the later, as first seen; each look moves it on to where the head left the default branch when that's later and not the head itself (amended 2026-11-09, issue #16: a folder left on an old branch counted every merge since as a subagent's work).

  Amended 2026-11-26 (issue #118): a path git lists again after its record went `removed` is the same worktree back only on the same branch, at its last head or a commit after it. Otherwise it is a new record, and the old one stays `removed` with its last head and its tool call, so its commits can still be opened; a path can then have several records, the latest the live one. Only what names the path since the old one went counts toward the new one: a record keeps where in the chat's order it went removed (the last tool call a look had read then, and when it read them), and the new one is the first call after that to name it, by the rules above (the agent's word first, of a call that owned none of the path's records); a call before that point still running when the look read it (its status says it runs and its end isn't stamped: one its turn's end left so is over) counts as after it, as the step making the worktree again can still run, or wait for a permission, at that look; the old owners' calls go last, as for a first record. A call whose end was stamped before the new worktree's `.git` file was written can only have seen the old one, and never owns the new: so neither the remover still running at the look that saw the path gone, nor a remover in the same gap between looks as the subagent that made it again, takes it. A rewind past that point moves it back to the last tool call the rewind kept, in the record the rewind saves, so a restart keeps it: every call kept came before the point, so none that could have read the old worktree counts, and the calls made since the rewind do; one that kept no tool call leaves the point gone from the chat, and every call there now, all made since, counts, the old owners' last. A look in flight during the rewind, which read the chat from before it, is put right at the next look. A subagent that read the old worktree, or the old owner's earlier steps, never takes it; if nothing since names it, the path gets no new record until something does, as a worktree nobody's subagent names isn't the chat's. A record removed before this was kept has no such place, and is judged as before: every step, a call that had none of the path's earlier records first. A path can also be removed and made again between two looks (an orchestrator's own `remove && add`, or while the chat is idle): a record keeps the modification time of its worktree's `.git` file as first seen (one stat a look, no git), and a look that finds another time takes it as made again, under the same rule: back only on its branch at its last head or after, else removed with its last head, gone after the look before, and a new record by the rule above. git writes that file when it makes a worktree, and also when it moves one (`git worktree move`, at the new path) and when a repair changes it (`git worktree repair` to relative paths, or back); a switch, a commit, an amend, a plain repair, a lock and its undoing, `gc` and `prune` leave it (git 2.56). A moved worktree is at another path: its old path's record goes removed, and the new path is found anew, by whoever names it. One moved away and back, or repaired, in place has a new time on the same worktree, and the rule decides: on its branch at its head or after, it stays one record. What this can't see: a worktree moved back or repaired in place, or its `.git` file touched, in the same gap between looks as a branch switched or reset in it, splits into a removed record and a new one, the live worktree's history and comments on the removed one; a record from before this was kept has no time until its next look; a filesystem whose times are coarser than the gap between the removal and the re-make; a call's end is the daemon's clock and the `.git` file's time the filesystem's, so where those disagree (times coarse, or set by another machine, as on a network share) a remover's end can read as after the re-make, and it counts by its place, as a call with no end stamped (one replayed after a restart) always does; and at the first look after the daemon starts, the look before is unknown, so the new owner is judged as a record from before this. A pull request's wait is kept by record (path, branch and last head), and records of one branch are asked about once a look.
- **A look runs only `worktree list`, `rev-parse`, `merge-base`, `rev-list`, `symbolic-ref` and `for-each-ref`**, so no look runs a filter or a hook, whoever asks for it.
- **"Merged" is what git shows**: a worktree with commits of its own whose `LastHead` is on the chat's branch or its base, at each look. A squash merge leaves nothing for git to see, so it reads as removed; so does a worktree that made no commits, whose head is on the branch without anything having been merged.

  Amended 2026-11-20 (issue #83): a squash merge reads as merged when GitHub says so. Once a worktree with commits of its own that git doesn't show merged is removed, the daemon asks GitHub once whether a pull request with its branch as head, opened in the chat's life, was merged (as a chat's pull request is found, ADR 0059, on the folder's repositories with a sign-in); the answer is kept on the record (`PullMerged`, `PullAsked`), asked again only when GitHub couldn't answer, 5 minutes on, at most 8 a look.

  Amended 2026-11-23: a pull request still open is no answer. Its worktree stays unasked and is asked again at the next looks, after those not yet asked (so open ones can't take every one of the 8), until it merges or closes; "removed" until then.

  Amended 2026-11-23: an open one waits before it's asked again, 5 minutes, then twice as long each time, at most an hour (looks come every 5 s while subagents work, and a pull request can wait days for review: asking at each would spend the sign-in's hourly limit). Once their waits are over, those asked longest ago go first, so more than 8 open ones all get their turn.
- **The app never stages, commits or discards in one.** Its Changes view is read-only, and review comments would go to the orchestrator if they come back, as the subagent has usually exited (the owner, 2026-11-02).

  Amended 2026-11-09: the owner turned comments on. They go to the chat's main agent with the worktree named: Send to agent puts them in the chat's box as for its own, under a lead line giving the worktree's folder and branch, their paths as the worktree has them. A worktree's comments are kept by its folder (`whereIn`), so a file of the same path in the chat's folder shares no comment, draft or sent state with it. Staging, committing and discarding stay off.

  Amended 2026-11-26 (issue #118): a worktree's comments are kept by its record, not its folder, as a path can have several records. The key is the folder for a path's first record, so every comment kept before stays where it is, and the folder with the record's count for a later one; the lead line names the record the comments are on, its branch, and says "removed" only of a removed one.
- **Only a click runs a `GetDiff` there**, as it runs the repository's filters (`git.Status` doesn't). A turn's end, an event or showing the tab again never does: what's read stays, with a line saying it changed. `GetRelatedWorktreeStats` is the automatic read: it costs less than `GetFolderStatus`, as a base that is a commit needs no merge base and no branch name, and a removed worktree's come from its commits alone.
- **A removed worktree's diff is `after` its base, not `since`**: `since` counts its own commit, which would put the chat's last commit under the subagent's work.
- **The record is the chat's** (`ChatRecord.RelatedWorktrees`), read with `GetRelatedWorktrees`; the `related_worktrees` event carries all of them when they change. Unnumbered, as terminals: a client reads them when it shows the chat.
- **Nushi writes nothing for this.** No ref, and no Clean up: Claude's sweep and the orchestrator remove worktrees (the owner, 2026-11-02).

## Consequences
- A removed worktree's commits can be collected by git once nothing else holds them: `LastHead` then names nothing, and its diff is gone. The owner chose that over Nushi keeping a ref.
- A subagent's reading another's worktree before that one's own steps show can take it, as the first to name it. Claude's word comes first, so this is about Bash-made ones.
- A worktree a subagent reaches only through a path it built at run time, or by a relative path from outside the chat's folder, isn't found unless a later step names it.
- A subagent that made no call Nushi can read and left a clean worktree is never seen: there is nothing to show of it.

## Alternatives considered
- **`refs/nushi/*` to keep a removed worktree's head**: reachable for good, but the owner's rule is that Nushi doesn't mess with git refs.
- **The lock's reason** (`claude agent agent-<id> (pid …)`), which `git.List` drops: it names the subagent, but only while it runs, in free text with a pid, and `.meta.json` says the same for longer.
- **The transcript's `cwd`**: stays the chat's folder for a Bash-made worktree, and says nothing `.meta.json` doesn't for an isolated one.
- **Only `worktreePath` and `.meta.json`**: they miss Bash-made worktrees, and every agent but Claude.
- **Watching `.git/worktrees`**: a file watcher per repository for what a look at a subagent's end already gives.
