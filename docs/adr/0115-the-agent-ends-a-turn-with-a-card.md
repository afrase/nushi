# 0115. The agent ends a turn with a card of reply buttons, through Nushi's MCP server

Status: proposed, 2026-11-14. Builds on [0043](0043-an-mcp-server-of-nushis-own-for-a-chats-tools.md) (Nushi's MCP server) and [0068](0068-an-agent-opens-a-preview.md) (a tool drawn by the app).

## Context
The owner: "we should be running our own MCP in nushi so agents can control nushi or talk back to it." The trigger is Claude desktop's `ccd_turn` server. Its `wrap_up` tool, called at a turn's end with `{recap, ask, actions: [{label}], blocked}`, shows a card: the recap, a question, a button per action. A tap sends the label as an ordinary user message, and the box stays usable. Its `update_plan` sets a plan. The owner wants the card most on the phone: one tap keeps an agent going while away.

Nushi already runs its own MCP server. `nushid tools-mcp` (`internal/mcpserver`) is a stdio server named `nushi` in each session's `mcpServers` (`cmd/nushid/jira.go`'s `mcpTools`, `chats.mcpServers` in `internal/features/chats/agent.go`). It asks the daemon over its Unix socket with a key per chat (`internal/features/tools`), and carries `show` and the `preview_*` tools today. It reaches the agents whose `HarnessInfo.ClientMCP` is true: Claude (`claude-acp-go`, which takes stdio, HTTP and SSE) and Codex (codex-acp). Ante's `serve` takes no client servers, omp ignores them in ACP mode, Pi and PiG's RPC have none, and opencode puts a client's tools behind its Code Mode `execute` script (docs/facts). Plans already come through ACP (`plan_view.dart`): Claude's task tools, Codex's plan, Pi's todo extension.

## Decision
- **One new tool, `wrap_up`, on the server Nushi has.** It is a new `tools.Set` (`internal/features/turn`) beside preview's and the servers'. Its name and input are Claude desktop's, so what Claude learned there carries over: `recap` (required), `ask`, `actions` (`[{label}]`), `blocked`. It answers at once with fixed text ("Shown to the user. End your turn."). It never waits for the user: the reply comes as the next prompt. **No `update_plan`**: a second plan would disagree with the ACP plan Nushi already shows.
- **Transport stays ADR 0043's**: stdio, `nushid tools-mcp`, the daemon over its socket, the chat's key in the server's environment. A loopback HTTP server was weighed and dropped: a TCP port any local user can reach where the socket is 0600, a bearer token in a header, and Codex's HTTP support unchecked. The key is tied to one chat, granted in memory, gone when the daemon restarts. It is never in a tool's input or answer, and `tools.Service` logs a tool's name, chat and outcome, never its arguments.
- **Who gets it**: Claude and Codex, the `ClientMCP` agents. Not Ante, omp, Pi or PiG (no way to hand them a server), and not opencode: its `execute` script hides the call's input, so the app can't draw the card.
- **How the agent learns it**: the set's MCP instructions (one short paragraph) and the tool's description, the way `show` does it. Claude Code puts MCP server instructions in its system prompt, so Claude needs no second copy. If Codex turns out to drop server instructions, Codex gets the same paragraph through ACP's client system prompt in append mode, when codex-acp advertises `sessionCapabilities.systemPrompt`. The paragraph is fixed text from Nushi with no chat content. In short: call `wrap_up` last, after a turn that did work or needs a decision; skip it for a one-line answer; offer 2 to 4 short next steps written as the user would say them; don't repeat the recap in the message; subagents never call it.
- **Limits, checked twice.** The daemon refuses a call past these with fixed text naming the limit, so the agent can fix it and nothing is shown: `recap` at most 2,000 characters; `ask` at most 300, one paragraph; at most 4 `actions`, each `label` one line of 1 to 80 characters, all different, none starting with `/` or `!`, so a tap can't run a slash command, a skill or a shell escape. Control and bidi characters are dropped from `ask` and labels. Unknown keys are refused (`tools.Decode`). The app draws the card from the call's raw input, with the same limits (read inside `arguments` on Codex, as `isShow` in `tool_parts.dart` does), and only for a completed call. Past the limits it draws a plain MCP row. One table of cases tests both sides, as `artifactKinds` does for `show`.
- **A button press is the user's act.** The app sends the label through `SendPrompt`, as if typed: plain text, nothing attached, no mode change, no marker. The daemon never sends a label itself. The agent proposes words and nothing else. It can't approve a permission, answer a question card, send as the user, or reach another chat. Buttons only show while nothing waits (below), and a label is shown whole, so what's tapped is what's sent.
- **No annotations, as with `show`.** A `readOnlyHint` asks the harness to run the tool unasked. Unlike `show`, that would be harmless here, since the tool only shows text the agent could have written in its message. Nushi adds no allow rule (ADR 0007). Whether Claude and Codex then run it unasked in their default modes must be recorded before this is built (open question 1). If a harness asks every turn, that agent's chats don't get the tool.
- **Where it shows.** The card takes the tool row's place in the transcript, on `raised` like the findings card (`findings_card.dart`). Top to bottom: the recap as the agent's Markdown (same renderer and link rules as its messages), the `ask` in plain text, then a button per action. On the Mac the buttons are a row of pills; on the phone, full-width buttons stacked above the composer. `blocked` adds a "Waiting on you" pill to the card. In v1 it doesn't change the chat's state or the push.
- **When the buttons show.** Only while the card is the chat's last item, no turn runs and nothing is queued. A tap, or any message the user types instead, removes them. The recap and question stay as a read-only card. The composer works throughout, and a tap leaves a draft alone. With several calls in a turn, only the last can have buttons. A call inside a subagent's steps is drawn as a plain row.
- **History.** The call is in the agent's own history, so a replayed chat (`session/load`, the transcript copy) draws the same card by the same rules. An old chat whose last item is a card still offers its buttons. Tapping one only sends text, as typing would.
- **Outside Nushi.** In `claude --resume`, Codex's terminal or Zed, the server and its instructions aren't there. Old calls show as an ordinary MCP tool row with JSON input, and a call the agent tries gets the harness's "no such tool". Nothing breaks, and the session stays the agent's (ADR 0008).
- **The push carries nothing new.** A Web Push still says "Claude finished" and the chat's id (`internal/features/remote/push.go`). The recap never goes through a push service. The Mac's own notification doesn't quote it either.
- **A setting, on at first.** Settings › General › Chats › "End-of-turn cards" (`turnCards`, `*bool` in `settings.json`, `optional` in the proto). Off, the set lists no tool and no instructions for sessions opened after. Running chats are marked `mcpChanged`, so their Reload applies it now.

## Consequences
- Cost: about 300 tokens of definition and instructions in every Claude and Codex session, and one tool call a turn: the call's output tokens and one more model round. Claude's MCP tools are deferred, so the first call of a session may first need a `ToolSearch` (see open questions).
- Claude may over-call it, on short answers and on turns that only asked something back. Codex's models tend to under-use optional tools without a stronger nudge. Both are checked in recordings and tuned in the instructions' words, not in code.
- A label is written by the agent, which may have read a hostile file or page. The worst a hostile label does is put words on a button. The user must still tap it, it is sent as their message in plain sight, and whatever it asks for still goes through the harness's permissions. Not running slash commands closes the one path where a tap would act without a turn.
- The implementation adds `wrap_up` to docs/security.md, `docs/facts/claude.md` and `codex.md` (asked or not, deferred or not, instructions honoured or not), and "End-of-turn card" to the glossary and the guide.

## Later, not in v1 (each its own decision)
- `set_title` (the chat's title): low risk, but Claude already names sessions, and an injected title could mislead in the sidebar.
- `notify` (a push to the phone): only a fixed "wants you" with no text, rate-limited. Otherwise a nuisance channel.
- `open_side_chat`, `start_chat`, or acting on another chat: an agent starting agents spends money and runs code without the user, and moves injected text sideways. High risk.
- Never: answering a permission or question, changing the mode, queueing or sending a message as the user, reading other chats.

## Alternatives considered
- Reading a recap and buttons from the final message's text (a fenced block, a "Next:" list): it would reach every agent, but a misread puts the agent's words on buttons it never meant, and the convention shows as junk in a terminal.
- An ACP extension method (`_nushi/wrap_up`): the model calls tools, not client methods, so each agent and bridge would need to expose it as a tool. MCP reaches Claude and Codex unchanged.
- Serving it in-process from `claude-acp-go`, as Claude desktop does: Claude only, and Nushi's UI in a public library.
- Doing nothing: the phone user types "go on". It works, at a few taps each turn.

## Open questions for the owner
1. If Claude or Codex asks before every `wrap_up` in their default modes, should Nushi add an allow rule for this one tool in the session's settings? It does nothing but show text, but it would be the first permission Nushi writes, so it amends 0007. Otherwise that agent doesn't get the tool.
2. Should `blocked` count as Needs you (the amber dot, the Dock badge, a "needs you" push), or stay a pill on the card?
3. On at first, or off until tried? The cost is one tool call a turn on every Claude and Codex chat.
4. One switch, or one per agent (Codex might under-call)?
5. Should a tap send the label alone, or put it in the composer first so it can be edited (two taps on the phone)?
