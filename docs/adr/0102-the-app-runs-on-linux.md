# 0102. The app runs on Linux

Status: accepted, 2026-11-08. Builds on [0097](0097-native-code-behind-interfaces.md) (a second platform's set behind its interfaces) and [0101](0101-the-daemon-runs-on-linux.md) (the daemon it talks to).

## Context
The daemon runs on Linux (ADR 0101); the app was the Mac's only. ADR 0097 made the seams for another platform: each native capability an interface, the Mac's implementation in a `_macos.dart` file, the set picked in `main.dart`. This is the app's first Linux step: it builds with `flutter build linux` and starts on a Linux desktop with each capability given a Linux implementation, most of them doing nothing yet. Filling them (notifications, the clipboard's files, fonts, spelling, the default browser for pages, packaging) follows in later steps, each extending this record.

## Decision
- **The runner** is Flutter's GTK template (`app/linux`, `flutter create --platforms=linux`), with the Mac's identity: application id `com.nushihq.Nushi` (the Mac's bundle id; the program's name and both halves of X11's `WM_CLASS`, so a `.desktop` file of that name matches the window), the binary `nushi`, the title "Nushi", 1280×800 at first. Its own channels are in `linux/runner/*.cc`, plain GObject C as the template is, each registered on the view beside the plugins: `nushi/clipboard`, `nushi/browser` and `nushi/desktop`, `nushi/window`, named and shaped as the Mac's where the Mac has the call.
- **One Nushi a user**: the GApplication is unique, so a second launch activates the first over D-Bus, which presents its window (never builds a second), and exits, as the single-instance Mac app does. With `NUSHI_DATA` set (a development run on a data folder of its own, AGENTS.md) it's non-unique, so it runs beside the installed one. With no session bus GLib runs it as non-unique anyway.
- **The system's window decorations**: GTK's header bar on GNOME and Wayland, the window manager's title bar elsewhere, as the template chooses. `AppWindow` says what the chrome is, so no widget asks which platform it's on: `titleInset`, where the main area's top starts with the sidebar hidden (84 on the Mac, past the traffic lights; 8 on Linux, a margin, so the button that shows the sidebar lines up with the sidebar's own icons, and the bars keep their 16); `headersMoveWindow` (false on Linux: `WindowDrag` is its Stack alone, as on the phone, and `TitleBand` only its child); `menuBar` (false on Linux), which gates `main.dart`'s `PlatformMenuBar`, whose provided items (About, Hide, Quit) throw off the Mac (the actions' keys are the window's `Shortcuts` either way); and `present({token})`, which raises the window with a notification click's activation token, without which Wayland may refuse it the focus (through the runner's `nushi/window` on Linux; on the Mac the Swift side already activates the app on that click). Drawing the window's own chrome, as on the Mac, waits for the rounder redesign.
- **The platform's conventions**: what the platform names differently (Show in Finder or Show in Folder, macOS or Linux, Mac or computer, keychain or keyring, Dock badge or App icon badge) and the modifier its shortcuts take (⌘, or Control) are one value, `Conventions` (`conventions.dart`), on `Native`: plain data, so a test or a render shows Linux's on the Mac, with `TargetPlatform.linux` beside it as a Linux machine runs them. Not `defaultTargetPlatform`, which says android under `flutter test`. The words read it: every "Show in Finder", "macOS", "Mac", "keychain" and "Dock badge" the desktop app says (Settings, the previews' and skills' menus, the composer's and the browser's notes, remote access) is the platform's own, so the Mac's are unchanged. The keys move to it later.
- **The phone reads none of it**: its web app shares the widgets but never sets `native`, so a shared widget reads the platform through top-level getters that answer for the phone too, as `speller` did: `conventions` (on the phone, the paired computer's words: the daemon says the system it runs on, `PingResponse.os` from API 112, and the phone keeps it with its pairing, so it names the computer offline too; a daemon from before said nothing and ran on a Mac; before pairing, "your computer"; its modifier stays the phone's own, ⌘, so a shortcut that reads `commandKey` never takes Control on an iPad paired with Linux), `webEmbedded` (`WebViews.embedded`: the Mac's web views; Linux opens pages in the browser), `headersMoveWindow` (none there), `lightsInset` and `hiddenHeaderStart` (no inset there). A test in the browser (`test/web/phone_native_test.dart`), where `native` is unset as on the phone, opens a PDF's preview and a CSV's.
- **`main.dart` picks the set at run time**: `Platform.isLinux ? linuxNative() : macosNative()`, the app's one test of the platform, before `catchErrors` and anything else that may reach `native`. Both sets compile into both apps: an `@Native` symbol or a channel is resolved only on its first call. Tests still start from the Mac's set on every host (`flutter_test_config.dart`), so views and goldens are the same wherever they run; a Linux implementation is tested on any host unless it needs Linux's libc.
- **The edge's check** (`tools/native-edge`): channels, platform messages and FFI in a `_macos.dart` or `_linux.dart` file only; `webview_flutter_wkwebview` in a `_macos.dart` file only, `dbus` (canonical's pure-Dart D-Bus client, a direct dependency now, already locked through `desktop_drop`) in a `_linux.dart` file only. A platform's file names its own platform's files, never the other's; any other file names none, but `main.dart`, which names `native_macos.dart` and `native_linux.dart`.
- **Default apps and the clipboard in the runner's C**, not Dart FFI to GIO (GObject references and `GError`s read better in C, the clipboard needs GTK's main loop anyway, and it mirrors the Mac's Swift side), and never `xdg-open` or `gio`'s command (either may be missing, `gio`'s output is translated, and in a VM `xdg-open` may open on another machine). `nushi/browser` opens an http, https or file address with the app that opens https (GIO hands a local file to it as its path), so a file is shown, never run by the app its type has (ADR 0068, 0094); "refused", "no-browser" and "failed" come back as errors. `nushi/desktop`'s `openAsText` uses the default app for `text/plain`. Show in Folder asks the file manager on the session bus (`org.freedesktop.FileManager1.ShowItems`, which Files, Dolphin, Thunar, Nemo and Caja answer) through `package:dbus`, else opens the folder; as on the Mac, a desktop call that opens nothing throws nothing (it's logged, without the path). The clipboard's files are its `file://` URIs of this machine; its picture, when it holds no text, is its PNG as offered (checked by its signature: no decoding and encoding on the window's thread) or another kind through gdk-pixbuf. Every clipboard read and launch is asynchronous, answered when the owner or GIO replies.
- **Linux's set** (`native_linux.dart`): one `<capability>_linux.dart` for each capability, so each is filled on its own. Working now: file modes (libc's chmod through FFI, with Linux's 32-bit `mode_t`), the window (no menu bar, no drag or zoom), swipes (GTK already gives Flutter the touchpad's pans and the mouse's back button), the clipboard's files and picture, and the desktop (above; a folder opens with GIO's default app for folders, through url_launcher). The rest answer as a platform without them: no diagrams (the source shows), and web views that throw until pages open in the default browser.
- **Notifications** go to the desktop's notification service over the session bus (`org.freedesktop.Notifications`, through `dbus`, `session_bus_linux.dart`), not GNotification, which reopens an app on a click only through a D-Bus-activatable `.desktop` file and is harder to test. Each says it's Nushi's (`desktop-entry` and the icon `com.nushihq.Nushi`, category `im.received`), with the sound `message-new-instant` or `suppress-sound`, and one action, `default`. Its body is escaped where the service reads markup (`body-markup`): a chat's title is the agent's. The summary isn't: the spec allows markup only in the body, and dunst, GNOME Shell and mako show the summary as plain text, so an escaped `&` would show as `&amp;`. The service lists nothing it shows, so `LinuxAlertCenter` keeps each notification's number (sent back as `replaces_id`, so the same one is replaced, never shown twice) and its chat (for Clear), forgetting one the service says is closed; its calls run one at a time, in order. Nothing is asked of the bus until it answers a ping: `dbus` (0.7.15) throws a failed connection where a signal stream subscribes, uncaught, and leaves that client waiting for good on every later call, so a bus that can't be reached (a stale address, or none in `XDG_RUNTIME_DIR`) is as none for the run. A click (`ActionInvoked`) opens the chat and raises the window through `AppWindow.present` with the `ActivationToken` the service sent just before it, when it sends one (dunst on X11 doesn't). The badge is Unity's launcher entry signal (`com.canonical.Unity.LauncherEntry.Update`, `count` and `count-visible`), which Ubuntu's dock, Dash to Dock and KDE show; a desktop without it shows nothing. Permission: allowed while the service runs or the bus can start it, else no answer (no row): the freedesktop service has none to ask, and Settings' way to a system's notification settings stays the Mac's. Tests run the real class against `dbus`'s own server in the test's process, its client given a uid (only Linux's libc would give one), so they run on the Mac too.
- **Fonts**: Settings › Terminal lists fontconfig's monospaced families, as `fc-list :spacing=mono family` prints them (from the app's `PATH`): each font by its first name, fontconfig's backslash escapes undone, each once, sorted, the bundled font left out. No `fc-list`, or one that fails, is no list: the bundled font alone, as before. Not fontconfig through FFI: a command run when the page opens needs no library bound.
- **Spell check** is enchant (`libenchant-2.so.2`, opened with `DynamicLibrary`; libc's `malloc` and `free` through `@Native` for its strings, as the app has no package:ffi), the library GNOME's and KDE's apps check with, over the user's Hunspell, Nuspell or Aspell dictionaries. Its language is the first of `LANGUAGE`, `LC_ALL`, `LC_MESSAGES` and `LANG`, without its encoding or modifier, then that language alone; the C locale, or none, is American English, the app's own. No library or no such dictionary is no speller, as a platform without one: Settings and the composer already allow for that. Ignore lasts the session (`enchant_dict_add_to_session`); Learn adds to enchant's personal list (`$XDG_CONFIG_HOME/enchant/<language>.dic`, by default in `~/.config`), shared with those apps; enchant makes that folder when the dictionary opens, so a test process's `XDG_CONFIG_HOME` is in its own data folder (`flutter_test_config.dart`, through libc's `setenv`, which GLib reads). Its calls run on the UI thread, as the Mac's channel's do on its main thread: a check takes microseconds a word, suggestions 15–35 ms (measured in the x86 VM under Rosetta), asked only when a word's menu opens; opening it takes about 60 ms at launch there. Enchant warns on stderr at launch about providers it can't load; left as it is, as silencing GLib's log from Dart needs a native callback.
- **The installed app is a capability too**, `AppInstall` (`app_install.dart`, `Native.install`): the data folder when `NUSHI_DATA` names none, the packaged daemon and its build, the app's version, starting that daemon and stopping the one in a data folder. The Mac's (`app_install_macos.dart`) is what the app did before, moved: the helper app opened with `/usr/bin/open` (ADR 0036), `lsof` to stop, Info.plist's version, Application Support. Linux's (`app_install_linux.dart`):
  - the data folder is nushid's own (`$XDG_DATA_HOME/nushi` when absolute, else `~/.local/share/nushi`, ADR 0101), so the app and the daemon it starts meet, and the app's own files (`app.json`, `app.log`, `themes/`) sit beside the daemon's as on the Mac;
  - the daemon is `lib/nushid` beside the binary (out of a file manager's way; `Platform.resolvedExecutable` follows a link to the binary), its build its size and mtime as on the Mac, the version Flutter's `data/flutter_assets/version.json` (`version+build_number`);
  - it starts as `lib/nushid -login`, detached (Dart's detached mode: a session of its own, its parent init, checked in a VM), with the app's environment less every `NUSHI_*` and `NUSHID_*` variable, plus `NUSHID_DATA` (the folder `-login` keeps) and, in a development run, the app's `NUSHI_DATA`, as the Mac's `openHelper` passes it. So it has the session's `DISPLAY`, `WAYLAND_DISPLAY` and `SSH_AUTH_SOCK`, as a daemon Launch Services opens has the login's;
  - it stops by the socket's other end: the app connects to `nushid.sock`, the kernel names the listener's pid (`SO_PEERCRED`, through `Socket.getRawOption`), the pid's `/proc/<pid>/comm` must say `nushid` (not `exe`, which says "(deleted)" after an upgrade replaced the file), and it gets SIGTERM: nothing to install, unlike `lsof`, which Arch lacks;
  - the daemon stops itself once its package is gone (ADR 0055's check): an executable `lib/nushid` with the app's `nushi` in the folder above, missing at two checks 30 s apart, so removing the package stops it and an upgrade doesn't;
  - `nushid` refuses arguments it doesn't know, with its usage, rather than starting on the default folder (`nushid -h` did).
- **Start at login** is an XDG autostart entry (`login_item_linux.dart`): `$XDG_CONFIG_HOME/autostart/com.nushihq.Nushi.daemon.desktop` (`~/.config` unless absolute), `Type=Application`, `Name=Nushi daemon`, `Exec=<the package>/lib/nushid -login` (quoted as the desktop entry spec says: a path with a space or a quote reads back the same; one with a `%` isn't written, since GLib looks for the program before it undoes the spec's `%%` and won't load the entry), `NoDisplay=true`, `X-GNOME-Autostart-enabled=true`. Written whole, 0600, when turned on; removed when turned off. It's on while the file is there and its `Exec` names this package's nushid, which exists (and neither `Hidden` nor GNOME's key turns it off): an entry left by a package that moved or went, or by another copy the user kept, is off, and turning it on rewrites it. The session starts it as you log in, with the session's environment, like the Mac's launch agent; the row shows whenever the app runs from a package, without `NUSHI_DATA`.
- **Tests on Linux**: goldens are macOS-only (AGENTS.md), so off macOS `flutter_test_config` neither compares nor writes them; tests that read a file's mode do it through `FileStat`, not BSD `stat`. Every test has a fake `AppInstall` in `native`, so none starts or stops a daemon; the peer-pid stop is tested on Linux against a socket the test listens on, its kill a fake. The runner's C has an integration test, `app/integration_test/linux_channels_test.dart`, run by `tools/linux-channels.sh` on Linux: the real channels in a debug build, under `xvfb-run` and `dbus-run-session`, with throwaway XDG folders whose only default apps are fakes that write down what they get (never the machine's own, never `xdg-open`), and `xclip` owning the clipboard; without that script's folder each test skips. The test of a picture that isn't PNG skips where gdk-pixbuf decodes through glycin and `bwrap` can't run (OrbStack's VMs).
- **The Makefile on Linux**: `DATA` defaults to nushid's own folder (ADR 0101), `make app` runs `flutter run -d linux` (which finds that folder itself), so `make run` meets its own daemon, `make stop` sends SIGTERM to the socket's holder through psmisc's `fuser`, and `make test` leaves out the Mac window's tests, and the tests in Chrome when there's no Chrome.

## Consequences
- The app builds and starts on Linux, finds or starts its packaged daemon in nushid's own folder, restarts it, and shows its views. What doesn't work yet does nothing rather than fail, apart from a file preview or a browser tab (no web view yet). The key labels are still the Mac's.
- A new capability needs its `_linux.dart` beside its `_macos.dart`: `Native`'s required parameters make a set without one fail to compile.

## Alternatives considered
- A `main_linux.dart` entry point: every Flutter command, Make target and CI step would need `-t`, and `main`'s body would move into a shared function. One test of `Platform` in `main` is smaller.
- Conditional imports to pick the set: ADR 0097 refuses them (`dart.library.ffi` holds on every desktop).
- A non-unique GApplication always (the template's): a second launch would open a second window on the same daemon and the same `app.json`. Unique always: a development run would only raise the installed window.
- A systemd user unit for Start at login, and `systemd-run` or `systemctl --user start` to launch: the user manager's environment has no `DISPLAY`, `WAYLAND_DISPLAY` or `SSH_AUTH_SOCK`, so a daemon started that way would differ from one started detached; a transient unit's fixed name is refused while the last one is still stopping (a leftover child holds it up to its stop timeout), failing a restart; and some distributions have no systemd. The autostart entry runs only in a graphical session, as the app does.
- A `nushid -stop` for `make stop`: psmisc's `fuser -k -TERM <socket>` already finds a socket's holder, with nothing added to the daemon.
- Drawing the window's chrome now: it needs drawn close, maximize and minimize buttons and a move from GTK on a press, which on Wayland needs the press's own serial; none of it can be checked without real input.
