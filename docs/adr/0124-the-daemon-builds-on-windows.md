# 0124. The daemon builds on Windows

Status: accepted, 2026-11-13. Builds on [0097](0097-native-code-behind-interfaces.md) (the seams) and [0101](0101-the-daemon-runs-on-linux.md) (a second platform's files).

## Context
Windows is on the roadmap (the owner, 2026-10-27). ADR 0097 put the Mac's own code behind `_darwin.go` files and ADR 0101 gave Linux its `_linux.go` ones, but the calls macOS and Linux share (process groups and signals, flock and fcntl, dup2, open(2)'s flags, a pseudo-terminal, a Unix stat) sat in files every OS compiles: both are Unix, so nothing made them split. This is Windows's first phase: `nushid` and every Go package build with `GOOS=windows`, and the daemon starts and answers its API. Making each part work there, the app, packaging and CI are later phases.

## Decision
- **Files**: code macOS and Linux share is in `foo_unix.go` (`//go:build unix`), Windows's in `foo_windows.go`, beside `foo_darwin.go` and `foo_linux.go` as before. A `foo_other.go` (`!darwin && !linux`) still answers for Windows where Windows has nothing of its own yet; where it has, the stand-in becomes `unix && !darwin && !linux`. A test of Unix behaviour is in a `_unix_test.go`; Windows's own in a `_windows_test.go`, run on Windows. No cgo on Windows.
- **What Windows does now**: the data folder is `%LOCALAPPDATA%\Nushi` (else `~\AppData\Local\Nushi`), local rather than roaming, and given a protected DACL of the user and SYSTEM at each start, Unix's 0700 (the daemon won't start on a link or junction, on one another account owns, or, once the DACL is set on a folder that wasn't already the user's alone, while an entry in it belongs to another account or keeps access of its own: what another account put there while it was open stays under its control; a clean check leaves `entries-checked`, so the walk isn't repeated). The open flags are `openflag`'s (no-follow is CreateFile's `FILE_FLAG_OPEN_REPARSE_POINT`, which opens a link as itself for the stat after to refuse; non-blocking and directory are nothing). `procgroup.Kill` ends a process tree with the system's `taskkill /T /F` by its full path, holding the process's handle so its pid can't be another's, and not at all once it has exited, and a program piped to a bridge (`procgroup.Start`, Pi's and Ante's) joins a job object as it starts, which its Kill ends whole, what it left running after its exit included, and which ends with the process holding it; `Own` starts the command in a console process group of its own (`CREATE_NEW_PROCESS_GROUP`, as acp-go does for an agent), which starts with Ctrl+C off, so a Ctrl+C at the daemon's console doesn't end what it started before it closes its chats, and guards it against cmd.exe (`batchfile`: an npm shim runs as node and its script), and `Session` does nothing (no session or terminal to keep from, and the daemon's console has no window). `filelock.Lock` takes the whole file with `LockFileEx`, as Rust's `File::try_lock`; `Held` is false, since only taking the lock would tell. The log makes the process's standard handles a duplicate of its own (`SetStdHandle`, which the runtime reads for each write of a crash), and is opened shared for delete so it can be renamed to rotate. A Claude record's process is alive when `OpenProcess` gives no exit code yet, or is refused for access; it is the record's process when its creation time (`GetProcessTimes`) is the record's `procStartFt` to the 100 ns, and the record is this host's when its `pidDomain` is `darwin:` and the host's lowercased name (`claudehistory`, docs/facts/claude.md), so a session open in a terminal is open elsewhere there too. A process's exit is logged by its code alone. A daemon with no console (started detached, as the app starts it) starts itself again once with `CREATE_NO_WINDOW`, its stderr `nushid.log` (so why it couldn't start is in the log), and exits (unless `ownDataFolder` refuses the folder: then it stops on that itself, saying why on its stderr, which the app reads into `app.log`), so the command-line programs it starts (an agent's bridge, git, gh) share a console that has no window rather than each opening one.
- **No program from the current folder**: the daemon sets `NoDefaultCurrentDirectoryInExePath=1` in its own environment first thing, and every command and agent it starts gets it (`batchfile.Environ`), so neither CreateProcess nor cmd.exe runs a program by a bare name from the current folder, which for an agent is a chat's project (its `node.exe` or `git.bat`).
- **The environment** agents start with is the registry's, as Windows builds it for a new process, not a login shell's (there is none): [0126](0126-agents-on-windows-start-with-the-registrys-environment.md).
- **Off on Windows**, as ADR 0097's stand-ins answer (`errors.ErrUnsupported` or an empty result): terminals (`Start` refuses; ConPTY is next), reading and signalling processes (`proctree`, `listeners`, `footprint`), `-login` (no exec, no login shell), the keychain, keep-awake and the system's proxies. A file's links and owner aren't read (`regularfile.Owner`), so a preview there can't be saved.
- **claude-acp-go**: its `sessions` opened a sidecar with `O_NOFOLLOW`; v0.4.0 keeps that in a `_unix.go` file and checks for a link first elsewhere, so it builds on Windows with nothing here.
- **`make lint-windows`** builds, vets and lints (golangci-lint; amended 2026-11-23: `unused` was off while Windows's terminal was a stand-in that never started its reading, and since ConPTY, 0132, it finds nothing there) every package for Windows without cgo, tests included, as part of `make lint` and CI's Linux job, so a Unix-only call in a shared file fails there and the `_windows.go` files and their tests are checked on any OS. A test of Unix's behaviour is in a `_unix_test.go` file for it; `testcheck.Fifo` skips a test that needs a fifo.

## Consequences
- `nushid.exe` built on Windows starts on its data folder, serves the API on its Unix socket (AF_UNIX, Windows 10 1803 and later; HTTP/2 without TLS, as everywhere), and its `Ping` says `windows`; no agent is found yet. Nushi still ships only for the Mac and Linux.
- Unix behaves as before. `procgroup`'s `Own`, `Kill` and `Session` are now what `agentproc`, `shellenv` and `homebrew` call, rather than setting `SysProcAttr` themselves.
- `tools/claude-record` builds on Unix only: claude-tee, which it runs, is Unix's.

## Alternatives considered
- A job object for a bound command too: it holds every process below, even one whose parent ended first, which taskkill's tree misses; but `Bound` sets up a command its caller then runs, with no moment after the start to add it in, and a process can only be added after it starts (a race with what it starts at once, which `procgroup.Start` accepts, as acp-go does for an agent) or started suspended, which `os/exec` doesn't do. The next phase, with the terminals.
- Taking a lock and letting it go for `Held`: it races an agent starting at that moment, which ADR 0101 refused for Linux too.
- Running the Linux build under WSL: unchanged code, but the agents, folders and shells are the Linux machine's, not the Windows user's.
