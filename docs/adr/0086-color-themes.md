# 0086. A color theme is a named pair of token sets

## Context
Nushi had one palette, `Tokens.light` and `Tokens.dark`, picked by Appearance. The owner wants to change the colors of tool calls, subagents and the rest later, and to try palettes beside each other (the Clearer step and a bolder Vivid one were two branches). Every color already comes from the tokens (`theme/tokens.dart`); the terminal's ANSI colors and a diff's did not (VS Code's and `diff_view`'s, fixed), so a dark-blue palette would have kept a white diff.

## Decision
- **A theme is a name and two sets of tokens** (`ColorTheme`: `dark`, `light`). Appearance still picks which set shows; the theme picks the palette. Widgets keep reading `t.<token>`: a theme changes values, never names, and nothing outside the tokens holds a color. The terminal's sixteen colors (`Tokens.terminal`, VS Code's unless a theme gives its own), a diff's (`Tokens.diff`, drawn from the surfaces and status colors unless given; Nushi's are `diff_view`'s), hover and pressed (the text's tint unless given) became tokens for that.
- **Built in**: Nushi (the default, unchanged), Vivid (commit a95daedd's bolder step), Solarized, Nord and Catppuccin (MIT each, credited under `docs/development.md`'s Dependencies), each held by the token tests to the same floors as Nushi's: text AA on every fill it sits on, marks 3:1, washes and borders a visible distance off their surface. Where a palette's own inks read under AA on a fill (Solarized's body text is 4.75:1 on its base, under on a hovered row), they're moved in lightness, keeping their hue. Nord has a dark form only: its light set is derived (Snow Storm's surfaces, Polar Night's text, Frost and Aurora taken darker); no theme is dark-only. Tokyo Night came later (2026-11-11): tokyonight.nvim's Night and Day (Apache-2.0), under the next rule.
- **A named third-party theme looks as the tools that ship it draw it** (2026-11-11; the owner: these names are known by many people and have an expected look). What a theme is known by is its published color, unshifted: the window's and the panes' surfaces, the body text of the transcript, code's colors, a diff's fills, the selection, and the terminal's sixteen and its text. Nushi's own roles (labels, pills, links, state words, chat colors, the cards' steps) pick from the same palette: another step of it that holds AA, and only where none does, the palette's ink moved in lightness by the least that passes, hue and saturation kept, said in the theme's file. `syntax.*`, `terminal.*`, `diff.*` and `agentText` are in no contrast test and no warning: their authors chose them and people expect them (Tokyo Night's comments are 2.8:1 on its background); `published_colors_test` holds a built-in's to its source instead. Which variant is which set goes by what other tools ship: Tokyo Night's light set is Day, which kitty, Ghostty, WezTerm and iTerm2's schemes carry in one coloring, where the VS Code theme's Light is VS Code's and Zed's, and the "Light" of Alacritty's themes and Gogh are older, different ones. Day is under AA nearly everywhere outside its editor (its text is 4.52:1 on its background), so every label of Nushi's there is a darker shade of a Day ink; its body text, code, diffs and terminal are Day's own. The picker says a set's known name ("Light: Tokyo Night Day").
- **The user's themes** are files, `themes/<name>.json` in the data folder beside `app.json`: `{"name", "from", "dark": {...}, "light": {...}}`, `from` a built-in's id (Nushi's unless given), each set mapping token names (`base`, `avatars.blue`, `syntax.keyword`, `terminal.red`, `diff.insertedLine`) to `#RRGGBB` or `#AARRGGBB`. What a file doesn't name is its `from` theme's. A file is untrusted input: a regular file only, 64 KB at most, 50 files at most, parsed as JSON and never run; an unknown key or a bad value is a note in Settings and is ignored, a file that's no JSON object is a note and no theme, never a crash. The app watches the folder and reads a file again when it changes. "New from" writes every token of the current theme, so a file starts whole and is edited, not written from nothing.
- **Contrast is a warning for the user's themes**: a pair under its floor is a line in Settings naming it, never a refusal (Nushi is unopinionated). The built-ins can't ship under it: the tests run over every one.
- **The phone** picks from the built-ins, its own setting kept in the browser's storage, read with the pairing before anything shows. Custom themes stay on the Mac.

## Consequences
- A new token is a new field in `Tokens`, its value in every built-in, and a line in `theme_file.dart`'s list (which names it for files); a file written before it lacks the token and gets its `from` theme's.
- `hover` and `pressed` in a file are fixed colors: a file that changes `text` without them keeps its `from` theme's tint, which is near the same text color in practice.
- A picked theme whose file is taken away shows Nushi's until the file is back; the pick stays.

## Alternatives considered
- A theme as a few seeds (base, accent, a hue per accent) that Nushi derives tokens from: less to write, but no one could fix the one pair that reads badly, and the built-ins' hand-held contrast would be a formula's.
- Themes from VS Code or iTerm files: their roles don't map onto Nushi's tokens (a tool call's tint, a subagent's, the findings card) without guessing.
- Refusing a custom theme under AA: Nushi gives warnings, not enforced flows.

## Amendment (2026-11-19): the picker comes first, Mode beside it, the picked theme once
- Settings › Appearance opens on its Theme group: Mode (System, Light, Dark, as segments) is its first row, then the cards, then Your themes. There's no row named Appearance on the Appearance page, and the Layout and Fonts groups follow.
- The picked theme shows once: its card, ringed in `accentInk` with a check. The large picture of its dark and light sets above the cards, and the cards' own Dark and Light tabs (a look that left the appearance alone, beside the real setting), are gone: two light/dark controls that did different things. The cards draw the set the app shows; Mode shows the other.
- A card says the shown set's own name where its palette names it apart from the theme (Catppuccin Mocha and Latte, Tokyo Night Day), as the picked one's large pictures did. A built-in card is its name alone; a user's still says Yours and its file.


## Amendment (2026-11-23): a broken save keeps the last good read
- A file that read as a theme and then reads as none (a save that isn't JSON, a file caught half written) keeps the theme it last read, with the new read's note on its card: the window no longer drops to Nushi's palette while the user fixes the file. A file read broken from the start is still a note and no theme. A watch that ends or fails is started again by New from and Show folder, and either button that can't make the folder or the file says so in a toast.

## Amendment (2026-11-26): code on a diff's change keeps its own contrast
- **On a diff's changed line or changed word, code keeps the contrast its theme gives it on the theme's own background, up to 3:1, by its lightness alone.** The target is the lesser of 3:1 and the colour's contrast on the plain background. A run that reaches it on its fill is drawn as published. One that doesn't keeps its hue and saturation and moves its lightness away from the fill (lighter when it is lighter than the fill, darker when darker) by the least step that reaches the target, the other way only if that side can't. Where neither end reaches it, whichever of the colour, white and black reads best, so a run never reads worse than its own colour did. It covers every colour a run has, the theme's syntax colours and the find's two marks, in every theme, built in or a user's (`codeOnTintContrast` in `syntax.dart`; `diff_view`'s `minTextContrast` does the work).
- **Why**: a theme's code colours are published for its background and its diff fills on their own; nobody checked the two together. Tokyo Night's comment, 2.8:1 on its background, read about 1.1:1 on its changed-word teal, and every built-in set has some code under 3:1 on a changed word. Lightness alone keeps a green string green. 3:1, WCAG's floor for large text and what must be seen, not 4.5, which would recolour most of a light set's code even where it reads. Never more than the colour's own contrast on the background, so a comment on a changed word reads as the theme's comments read everywhere and a theme low in contrast by design stays so.
- **What it leaves alone**: code on the plain background, the gutter, the line-selection band, the fold labels and the text selection. The find's current hit and its other hits differ in hue (the accent's ink and `needs`), which a change of lightness keeps. A pull request thread's hunk (`HunkLines` in `pull_thread_card.dart`) draws its own plain text, which reads 3.27:1 or more on its line tints in every built-in set. Code outside a diff is not covered.
- **Extended to Nushi's own fills (issue 117)**: the same rule covers the fills Nushi paints under code itself: the file viewer's find hits, its current match and its text selection, a hit over the selection too, and a code block's find hits and current match in the transcript and a Markdown preview (`codeOn` in `contrast.dart`, the app's copy of the rule step for step, a translucent colour judged as it shows, as `diff_view` doesn't export its own; a test holds the two to the same answers). The file editor's hits, its selection (the current match is the selection there) and a hit over it (2026-11-27): re_editor paints them under the text it lays out from the spans `EditorSpans` gives each line, so those spans draw each part on its fill by the rule (`EditorInk`, `onFills`), a part that reads as published left in its run. Of the hits it costs what is in sight, not the line: only those re_editor is given to paint (`EditorSight`'s window, in and around what is in sight, of a long line only its cut), the one window both use, kept until what is in sight leaves it; a line's are worked out once while the matches, its part of the window and its length stay the same, and what re_editor is given to paint is read from the same (`LineHits`). A selected part is drawn on its fill whole, so what shows of it is inked in the frame that shows it, however far the view jumps (a scrollbar's drag), and it is drawn again only when the selection on its line changes. The rest of a line keeps the runs its syntax gave it. A selection's change or an edit has re_editor lay out the lines whose spans change; a find's answer and a window taken anew don't, so re_editor is asked to lay the lines in sight out then (kept paragraphs for the lines whose spans didn't change), and only when one of them is drawn otherwise. A window taken anew costs nothing with no matches (find closed, or none found); otherwise each line in sight compares the marks it was drawn for with its marks now, and only one whose marks changed (a long line whose cut moved) is drawn again, to see; one drawn the same keeps its spans. An answer checks the lines in sight the same way. An edit leaves re_editor's last answer painted where it was until the next one, and its hits stay drawn there meanwhile, with nothing laid out for them until that answer. Costs: a step of a selection lays its line out again when the code it adds or leaves is drawn otherwise, as typing in it does; a hit scrolled into sight past the window shows a frame after the scroll, as before, its fill and its ink together. A transcript code block's selection (2026-11-27): its paragraph paints the selection, so the block's text joins the selection through a registrar that passes it on and keeps what it was given (`InkedSelection`, in the markdown package; no selection container of its own, so selecting across the block is as before), and the block's `Marks` draws the selected text again over it, clipped to the selection's boxes, for the selection over the block's fill, or over a hit's or the current match's tint (the paragraph paints its selection over the marks), as the file viewer draws its own. Every built-in set's code reads by the rule on each of these fills in tests that read the pixels (`editor_code_on_test`, `code_block_ink_test`).
- **The terminal's search hits (issue 116)**: xterm draws every hit's text in one colour, on two fills that are Nushi's own: the rest on `needsSoft`, the current one on the accent's hue, as the app's other finds tell theirs. That text is the terminal's own (`terminal.foreground`, else `text`) as published wherever it leaves room for both fills (4.5:1 on each, the fills 2:1 apart), else its lightness alone moved by the least step that does; the terminal's colours themselves stay as published. A user's theme that leaves no room gets a line in Settings' warnings for the search, not a refusal, naming the keys a file sets (`accent` against `needsSoft`; `text`, or only `needsSoft` where the `from` theme gives the terminal its own text, which a file can't set); the hits' text always reads on the current hit, the accent being moved until it does, so that pair has no line. Settings' card shows a set's lowest ratio first, whatever its floor, so the fills' line (always under 2:1) is the one shown more often than not; the text's line on `needsSoft` follows `text on needsSoft`, as low or lower and the same fix, unless the terminal has its own text.
