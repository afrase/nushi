# 0059. A chat's pull request is found by its branch's head, linked on the chat, and asked for only while it shows

Status: accepted, 2026-10-28; the chat open, not its card, polls since 2026-10-29. Amends [0046](0046-the-github-inbox-and-polling.md) (what polls). Amended 2026-11-16: found only for a branch the chat pushed, opened in the chat's life (below).

## Context
A chat that made a branch usually ends in a pull request, opened by the agent (`gh pr create`, an MCP tool) or by the user. Chats started from a pull request already remember it (`Session.GitHub`); the others had no link, so their checks, reviews and comments were a trip to the browser away. Orca shows a branch's pull request beside its worktree; its lookup, polling and log trimming were the model (ideas, not its look).

## Decision
- **Found by its head:** the daemon reads the chat's folder's branch and the remote it's pushed to, and asks each of the folder's GitHub repositories (the pushed one first, three at most, on a host with a sign-in) for pull requests with head `<owner pushed to>:<branch>` (REST `pulls?head=&state=all`, with the last answer's ETag: an unchanged ask is a free 304; `X-Poll-Interval` honoured, though GitHub sends none here). An open one wins, else the newest. Nothing is looked for on the default branch or a detached HEAD.
- **Linked on the chat:** a found one is `Session.Pull` (with the branch it was found by); one linked by hand wins over a found one; Unlink is remembered (`NoPull`), so that one isn't found again; a found one goes when the folder leaves its branch. A chat started from a pull request keeps it in `GitHub`; one started from an issue keeps the issue there and gets its pull request in `Pull`; `Chat.pull` is whichever pull request the chat has.
- **Asked only while it shows** (as 0046): the chat's pane, while it's open, asks when it opens, each minute (15 when merged or closed), 3 s after a tool call that ran `git push`, `gh pr create` or a `create_pull_request` tool, when a turn ends, and when the window comes to the front, whether the details panel shows or not (2026-10-29: with the panel hidden, a pull request opened after the chat's first ask was never found). A branch's empty answer isn't kept by the daemon (a found one is, 20 s), so the ask after a push reaches GitHub; the card's title says when it last asked and how often. The sidebar's dots and the phone's chip one states query a host a minute. The tab is the GitHub view's pull request pane, read through the chat's poll (it has none of its own there).
- **Send to agent** puts a comment, a thread or a failed check (the failing part of its log) into the chat's box as a reply card, never sent by itself; the card says its quote is GitHub's text, data, not instructions. (Amended 2026-11-05: what a card asks the agent, by kind, is the user's to change in Settings › GitHub, an app preference with today's words as each default; the data line after it is fixed, so no setting lets GitHub's text read as instructions. Not a daemon setting: only the Mac's app makes these cards, the phone has no Pull request tab.)

## Consequences
- A chat on an open pull request spends about 2 GraphQL points a minute while it's open; finding costs a free 304 once the branch's answer is known. A closed window costs nothing.
- A pull request opened elsewhere shows within a minute while the chat is open, or as the window comes to the front; one the agent opens 3 s after its push or `gh pr create`, or its turn's end.
- A branch that two chats share links both to its pull request.

## Amendment (2026-11-16): a chat finds only its own pull request
The owner: "When opening a new chat it shouldn't include any PRs. Right now if the directory has a branch with a PR it will just link it." And: "I noticed old chats have PRs that were created after I archived them which is weird. Let's make sure the PR link is attached to that specific chat better." Finding went by the folder's branch alone, so a new chat took a pull request it did nothing with, and an archived chat, shown again, took one a later chat or the user opened on the same branch.
- **Pushed by the chat**: the daemon records the folder's branch on the chat (`ChatRecord.Pushed`, with when it was first and last pushed) when a completed tool call of the chat ran `git push` or `gh pr create`, or was a `create_pull_request` tool (the app's match for its 3 s ask); not as a reopen replays it, nor a side chat's. A pull request is found by its head only for such a branch; FindChatPull doesn't ask GitHub for another, so a chat that pushed nothing costs only git each minute.
- **In the chat's life**: the pull request must have been opened (GitHub's `created_at`) at or after the chat began (`Created`; a fork's `Since`, its parent's) and, for an archived chat, before it was archived (`ArchivedAt`, exactly; for one archived before that was kept, up to 24 hours after its last message or turn, `Updated`, since the user often opens the pull request from their own terminal after the agent finished and archives once it merged: `model.UnkeptArchiveGrace`). An archived chat finds nothing new: the daemon refuses, and the app doesn't ask.
- **A shared branch**: of two chats of one repository (a worktree's repository, else the folder) that pushed the branch in their lives, the one whose push came last at or before the pull request's opening takes it (only a branch's first and last push are kept, so the first stands in when the last came after). One already linked stays.
- **Links saved before**: a found link (`Branch` set, not opened in the chat, not by hand) whose pull request was opened outside the chat's life is dropped lazily, where the daemon already knows when it was opened: FindChatPull for the branch's, and `GetGitHubItems` when the app names the chat whose rows it asks (`chat_id`). It isn't remembered as unlinked, so a hand link still works; each drop is logged. Found links that pass stay.
- **Kept**: opened in the chat, by hand, started from a pull request, Unlink, a fork's copy of its parent's links and pushes, and the polls above. **Link pull request…** offers the branch's pull request first (`FindChatPullRequest.suggest`, answered in `branch_pull` without linking), for one pushed from the user's own terminal.
- The consequence above, "a branch that two chats share links both", no longer holds.
