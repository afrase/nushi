# 0055. Releases from published GitHub releases, and a Homebrew cask in the owner's tap

Status: accepted, 2026-10-27. Follows Sextant's ADR 0058 (`~/Developer/Sextant/docs/adr/0058-releases-and-the-homebrew-cask.md`), which holds for the parts not said here: GitHub's `published` trigger, Homebrew 6's tap trust and the short `afrase/tap/<name>` form, Homebrew 5's removed `--no-quarantine`, Homebrew 7's declarative `postflight_steps`.

## Context
Nushi was installed only by `make install`. The owner asked for a Homebrew tap, with Sextant as the example, and mentioned GoReleaser. Nushi's main artifact is a Flutter app with the Go daemon inside a helper app (ADR 0036); the relay and the phone's web app are what a Pi runs.

## Decision
- **The trigger is a published release**, as Sextant's: `.github/workflows/release.yml` on `release: published` (and by hand for an existing tag) checks the tag (`vX.Y.Z[-suffix]`), checks it out with full history, runs `make check`, then `tools/release.sh X.Y.Z` (the same script runs here), and attaches with `gh release upload --clobber`: `Nushi-X.Y.Z.zip` (`make package`, ad hoc signed), `nushi-relay-X.Y.Z-{linux-arm64,linux-amd64,darwin-arm64}.tar.gz` (static, `CGO_ENABLED=0`), `nushi-web-X.Y.Z.tar.gz` (`make web` under `nushi-web/`), each with a `.sha256`. `macos-26` (what CI's `macos-latest` is), Go and Flutter as CI's, actions pinned by commit, `contents: write` only, values into the shell only through `env`. `make web`'s fallback fonts are cached keyed on `fonts.lock`; a miss fetches them with the lock's checks.
- **No GoReleaser.** It can't build the Flutter app (only Pro takes prebuilt artifacts), so the app's zip, signing and cask would stay outside it; what it would add is the relay's cross-builds and checksums, a dozen lines of shell. Sextant decided the same.
- **Versions** come from the tag: `make package` takes `NUSHI_VERSION` (else the newest `vX.Y.Z` tag, else 0.1.0) into the app's and the helper's `CFBundleShortVersionString` (a suffix kept), the commit count into `CFBundleVersion`, and the daemon's `api.Release` through `-ldflags -X`: `nushid -version`, its start line in `nushid.log`, Ping's `version` (API 74) and Settings › Logs & advanced (the macOS About panel has the app's). `nushi-relay -version` too.
- **macOS 13 and Apple silicon.** Go 1.27 links for macOS 13 at least; the daemon, built with cgo, took the building Mac's SDK as its minimum (27.0 here, 26 on the runner), so it is now built with `-mmacosx-version-min=13.0` in `CGO_CFLAGS` and `CGO_LDFLAGS` (not `MACOSX_DEPLOYMENT_TARGET`: Go's build cache doesn't key on it and reuses objects built for 27), and the app's deployment target goes from 12.0 to 13.0 (SMAppService, Start at login, is 13 too). The daemon is built for arm64 only: `depends_on arch: :arm64`, `depends_on macos: :ventura`.
- **The cask** (`packaging/homebrew/nushi.rb`, pushed to `afrase/homebrew-tap` as `Casks/nushi.rb` with the `HOMEBREW_TAP_TOKEN` secret) clears the quarantine with `postflight_steps`, as Sextant's. Unlike Sextant's, only the latest release updates it (`gh release view`'s tag must be this one): a pre-release, or an older release rebuilt by hand, leaves it alone.
- **The daemon on upgrade and uninstall.** `uninstall quit:` quits the app (an upgrade opens it again). The running daemon keeps its chats through an upgrade; the app offers Restart daemon, as after `make install`. Homebrew can't stop it on uninstall alone: of its directives only `signal` is skipped on upgrades, and `signal` finds processes by a launchd label of the form `application.<id>.<n>.<n>`, while an app opened with `open -n` gets a UUID after them (seen: `application.com.nushihq.Nushi.daemon.102012581.102012586.FD644B38-…`). So the daemon stops itself once its app is gone: its executable missing at two checks 30 s apart (Homebrew's upgrade moves the old app out and the new one in within seconds). That also covers an app dragged to the Trash. No `launchctl:` for Start at login's agent: it isn't the daemon (it only opens the helper at login, ADR 0036), Homebrew runs it on upgrades too, and it also runs `launchctl` through `sudo`, which stopped the test upgrade for an admin password. The login item goes with the app. Chats' data stays; `zap` removes `~/Library/Application Support/Nushi` and the preferences, never an agent's own folders.
- **Signing stays ad hoc.** The owner's own builds use his Apple Development certificate when there is one; a release can't, so each release is a new program to the keychain: the Jira and pasted GitHub tokens need one OK after each upgrade (ADR 0042), and Start at login keeps working (ADR 0036's script).

## Consequences
- **How to release**: add the secret once (a fine-grained token, Contents read and write on `afrase/homebrew-tap` only, as the repository secret `HOMEBREW_TAP_TOKEN`); then Releases › Draft a new release, a new tag `vX.Y.Z` on `main`, Generate release notes, Publish. The files appear on the release within about half an hour (`make check` comes first), and the cask follows. Rebuild one: Actions › Release › Run workflow with its tag.
- Install: `brew install --cask afrase/tap/nushi`. A zip opened by hand meets Gatekeeper (Open Anyway).
- A daemon whose app was deleted stops within about a minute; one started from `app/build` may stop while `make package` rebuilds it.
- If Homebrew restricts `run` steps in third-party taps, the fix is a Developer ID and notarization, as for Sextant.

## Amendments
- 2026-10-27 (step 344, the owner: "It took 20min for a release"): **The parts build in parallel, beside the check.** v0.1.0 took 19.5 minutes: `make check` (12) then `tools/release.sh` (5) in one macOS job. Now `tools/release.sh X.Y.Z [app] [relay] [web]` builds the named parts (all three without one, as here), and the workflow runs the app on `macos-26` and the relays and the web app on Linux (the same `main.<hash>.dart.js` as a Mac builds) as jobs of their own, while a first job checks the tag and looks for a passing CI run on its commit; without one, CI's workflow is called on that commit (`workflow_call`, its checkouts at the commit given). The last job, the only one with `contents: write`, waits for the builds and the check, then attaches the files and updates the cask. About 5 minutes; "within about half an hour" above is now that.
- 2026-10-28 (step 371, the owner: "Why is a daemon reset always required?"): **The daemon restarts itself once nothing runs** ([0056](0056-the-daemon-restarts-itself-when-idle.md)); "the app offers Restart daemon" above is now that, with Restart now for the impatient.
