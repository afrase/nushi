# 0133. Windows reads listeners and memory, and binds a command to a job

Status: accepted, 2026-11-17. Amends [0124](0124-the-daemon-builds-on-windows.md) (the daemon on Windows: off were `listeners` and `footprint`, and a bound command had no job).

Amended 2026-11-24: the Listeners half is gone. `internal/listeners`, its `GetExtendedTcpTable` reader among its Mac and Linux ones, was deleted with the dev servers' identity check it served (ADR 0098's amendment of the same day); memory and the bound command's job hold.

## Context
ADR 0124 left the daemon on Windows reading no processes: `listeners` and `footprint` answered `errors.ErrUnsupported`, so a dev server's port was never checked as its own or named when taken, and the app's memory card stayed off (the daemon's `GetMemory` answers `unimplemented`, and the app stops asking). It also left `procgroup.Bound`'s commands (git, gh, npm, an agent's `--version`, Claude's `mcp` commands) to `taskkill /T`, which follows each process's parent from the command down and so misses one whose parent ended first; `procgroup.Start`'s programs had a job object, but `Bound` sets up a command its caller then runs, and 0124 found no moment after the start to add it to one. `proctree` (Toolhelp's snapshot, a process's command line) comes with the terminals, apart from this.

## Decision
- **Listeners** come from iphlpapi's `GetExtendedTcpTable` (`TCP_TABLE_OWNER_PID_LISTENER`), IPv4's table and IPv6's, through `windows.NewLazySystemDLL` (no cgo), each row a listening socket, its local address and the pid that owns it; a buffer too small is grown and asked again. A row is kept when a connection to localhost can reach it (127.0.0.1, ::1 or a wildcard), as on the Mac and Linux. Windows lists a dual-stack socket (an IPv6 wildcard without `IPV6_V6ONLY`: Go's `":p"`, Node's default) in both tables, as 0.0.0.0:p and [::]:p, and tells no socket's `IPV6_V6ONLY` (seen on Windows 11 23H2, 2026-11-17, for Go's five kinds of listener), so a process's [::]:p beside its own 0.0.0.0:p is one dual-stack `Listener`: were they an IPv4 socket and a v6-only one, that one listener still takes what they take, each family's connections to that process (a Windows test pins this with the two sockets and a dial to each). Each socket is listed once, with the process that opened it, not each holding it, and every user's sockets are listed (the table has them all; a service's on a wildcard is one a connection may reach). The parsing (`tcptable.go`) builds on every OS, so CI's Linux and Mac jobs test it.
- **Memory** is a process's private bytes (`GetProcessMemoryInfo`'s `PROCESS_MEMORY_COUNTERS_EX.PrivateUsage`, Task Manager's "Commit size"): what it alone holds, in RAM or paged out, as macOS's footprint counts what is compressed or swapped; shared pages (DLLs' code, a mapped file) aren't counted, so a tree's sum counts none twice. A process is opened with `PROCESS_QUERY_LIMITED_INFORMATION` alone; one that can't be (a service's, a protected process) reads 0. The process list is Toolhelp's snapshot (pids and parents' pids). A Windows process keeps an ended parent's pid, which may since be another process's, so a process isn't its parent's child when both starts are known (`GetProcessTimes`) and the parent started after it, `proctree`'s rule on Windows; the starts are read only for the processes a walk down from a tree's root reaches, each once a snapshot, not every process's. A walk never visits a process twice, so a loop of parents can't hang it. The app's memory card then shows on Windows with nothing of its own changed.
- **A bound command's cancel kills its group.** Go's `exec.Cmd` runs nothing of the caller's between starting the process and the caller's `Wait`, so a command can't be put in a job of its own once it starts without riding on something the caller sets (Alternatives). Instead, at the first `Bound`, the daemon puts itself in a job (`tracker_windows.go`), whose one limit is `JOB_OBJECT_LIMIT_BREAKAWAY_OK`, whose completion port tells, in order, of each process created below it (`JOB_OBJECT_MSG_NEW_PROCESS`: a process's children are in its job, nested jobs' too) and of each exit. For each new process the tracker opens it (`SYNCHRONIZE`, `PROCESS_TERMINATE` and `PROCESS_QUERY_LIMITED_INFORMATION`), holding the handle while the process lives so its pid can't name another, and reads its parent (`NtQueryInformationProcess`'s `InheritedFromUniqueProcessId`) and its start: a child of the daemon starts a group, and any other process joins the group of its parent, which is still tracked when its child is told of (it created the child, so its own exit is told of after) and started at or before it. `Bound`'s cancel (`cmd.Cancel`) kills the command's group, found by its first process's pid and start: every process in it, one whose parent ended first included, and one the port tells of after the kill as it comes. A group lives while any of its processes does, so a cancel after the command has exited, before `Wait` has taken that, still ends what it left. A command the port hasn't told of yet is killed alone, and its group as soon as it is told of. Nothing is killed by the command's own exit or by the daemon's (the job has no kill-on-close), as a Unix group lives on after its leader. `Bound` takes the command as it is: its input, set before or after `Bound`, a `StdinPipe`, or NUL for none, is exec's own. Without the job (the system refused it), the cancel is the command's tree as before (`Kill`).

## Consequences
- In the app on Windows a dev server's identity check and the "port taken by …" note work as on the Mac (once `proctree` reads Windows's processes, which the check needs for the server's own), and the memory card shows the daemon's, the app's and each chat's.
- A List takes about 0.2 ms (2026-11-17, an i9-9900K, 455 processes, 132 listening sockets); a memory report's snapshot about 14 ms, and the starts its walks read under 1 ms (2026-11-18).
- Every process the daemon starts, bound or not (agents, `Start`'s programs, terminals), and all they start, is in the daemon's job and told of to the tracker, which holds a handle for each while it lives. The job limits nothing else. Without `BREAKAWAY_OK`, a process below the daemon that asks for `CREATE_BREAKAWAY_FROM_JOB` would fail to start (access denied, CreateProcess's flags), where before the job the flag did nothing; with it, such a process starts outside the job, and so outside the tracker's groups, as it asked (`SILENT_BREAKAWAY_OK` would take every child out and leave nothing to track). Since Windows 8 they can make jobs of their own (`Start`'s kill-on-close job nests in it). Putting itself in the job takes the daemon about 0.1 ms, once.
- A process that has exited before the tracker opens it isn't tracked, so neither is what it started: a cancel misses those, as the tree's kill would.
- A cancel reaches further than on Unix in one way: there, a program that means to outlive its command (a daemonizing helper) calls `setsid` and leaves the process group, so a cancel misses it; on Windows a process can't leave its creator's group here once started, so a cancel ends it too. The one documented way to ask out is to be started with `CREATE_BREAKAWAY_FROM_JOB`, which the job allows, and such a process isn't tracked; `DETACHED_PROCESS` only means no console, and a process's creation flags can't be read back. A command that exits by itself still leaves its helpers running; only a cancel while it runs, or after its exit and before `Wait` has returned, ends them.
- Tracking is best-effort: a job's messages to its port aren't guaranteed to arrive (`JOBOBJECT_ASSOCIATE_COMPLETION_PORT`). A lost exit is made up for: at each exit told of and each kill the tracker sweeps for held processes that have exited (`WaitForSingleObject`, no wait) and drops them once the port has given every message queued before the sweep, so their children's are read first (`tracker_sweep_windows.go`); a process a cancel killed before it was told of is let go of the same way. A lost new process isn't: it and what it starts aren't tracked, and a cancel misses them.
- `footprint`'s Toolhelp walk and start-time rule are the same as `proctree`'s on Windows, which the terminals' branch adds; the two are written apart until both are on `main`, and the rule is kept the same in each.
- `listeners` and `footprint` join `procgroup` and the rest in CI's "Go on Windows" job. `listeners`' test of a child's listener in this process's tree skips on Windows until `proctree` reads processes there.

## Alternatives considered
- `NtQuerySystemInformation`'s process list for the snapshot (each process's parent, start and private bytes in one call, wrapped by x/sys): 25–36 ms here against Toolhelp's 13 ms with every process's start read, and its struct is the kernel's own, documented only in part.
- Reading every process's start at each snapshot (the first take of this ADR): it opens every process the user can at each poll of the memory card, where a walk needs only the trees it reports.
- Private working set (`PROCESS_MEMORY_COUNTERS_EX2`, Task Manager's default column): newer than the rest of the struct, and memory paged out isn't counted, so a trimmed process would look small while it holds its memory.
- A kill-on-close job per command, joined by the first read of the command's input, which `Bound` wraps (exec's copy into the input pipe is the one thing run after the start; the first take of this ADR): it tied `Bound` to an order (the input set, or `StdinPipe` taken, before it), gave a command with no input an empty pipe for NUL, and gave one whose input is a pipe of its own (`git cat-file --batch`, an MCP sign-in) no job.
- Starting a bound command suspended (`CREATE_SUSPENDED`) and resuming it once in a job: nothing races, but resuming needs the main thread's handle, which `os.Process` doesn't give (a thread snapshot or the undocumented `NtResumeProcess`), and nothing of the caller's runs after the start to resume it.
- Routing every bound command through procgroup's own runner (`procgroup.Output`, `Run`): no hook needed, but each of the two dozen callers changes, and a new one that runs the command itself silently has no job.
- A placeholder process in each command's job as its parent (`PROC_THREAD_ATTRIBUTE_PARENT_PROCESS`, which passes on its job): a process more for every git call, the command's handles passed through it, and a spoofed parent is what endpoint security watches for.
- Killing what is left of a group when its command exits by itself, or all of them when the daemon dies: Unix doesn't, and a command may leave work running on purpose (git's `gc --auto` detaches on Unix).
