# Security notes

What Nushi reads, writes, runs and sends on your behalf, and what limits it. A security-sensitive change gets its entry here in the same commit ([AGENTS.md](../AGENTS.md)).

- A reply card's lead line names GitHub logins outside the quote ("Review comments from @octo"), so the agent knows whose they are: only what matches a login's shape (letters, digits, dashes, 39 at most, a bot's `[bot]`), else "someone"; the daemon's messages keep logins inside the data. What a card asks the agent (Settings › GitHub, `app.json`'s `cardAsks`) is the user's to write, plain text only (2,000 characters at most, no control characters but line breaks and tabs, no bidirectional overrides; checked as typed and again when read, else the default); the line saying the quote is GitHub's text, data, not instructions, always follows it and no setting removes it.

- **Mermaid** (ADR 0057): an agent's diagram text runs through mermaid.js at its strict level (labels as text, no clicks or links) in a web view that loads only Nushi's page and the pinned script (every other navigation refused); on the Mac one hidden WKWebView draws every transcript block, one at a time, 10 s each at most (a slower one fails, its web view goes and its WebContent process is killed, by WebKit's private `_webProcessIdentifier`, so someone else's diagram can't hold the rest or keep a core busy; a WebKit without it leaves the process to run until mermaid's own limits end it), on Windows one hidden WebView2 the same way, 10 s each at most, every call into its page included (a slower one fails and its web view is closed and a new one made for the next, so it can't hold the rest; its renderer process is WebView2's to end, not killed by Nushi, so a busy core may stay busy until mermaid's own limits end it), on the phone the sandboxed frame of the page previews (its script from the relay, `Cross-Origin-Resource-Policy: cross-origin` for that one file). A parse error's message (mermaid's, about the text) is shown as text.
- **The token** (0600, remade if empty or short) sits beside the socket in a 0700 folder; anything running as you, the agent included, can read it (ADR 0024). Any client with it can: list any absolute folder (`ListFiles`, 20,000 names at most) and read a regular file inside one (`GetFile`, 1 MB at most, no link followed out of the folder), read and watch a file in a chat's folder or worktree (`WatchChatFile`, 5 MB at most, through `os.Root`: no `..` or link out; polled each second while open; a paired phone too), list a folder inside a chat's folder or worktree (`WatchChatFolder`, the Files pane: names, kinds, sizes and times, 2,000 entries a folder at most and 5,000 a call, three levels at most; the path relative, checked by `folderlist.Clean` (no `..`, no `.git`, 4096 bytes, no NUL) and read through `os.Root`, so a link out, a loop or a dangling link is shown as a link and never followed, and `.git` is never listed, nor entered through a link; `git check-ignore` runs on the names, hooks and fsmonitor off; polled each second while open, a stat of each folder and entry sent, git again only on a change; a paired phone too), read the memory of any process tree it names (`GetMemory`, sizes only), open a shell as you anywhere ([ADR 0022](adr/0022-the-daemon-owns-terminals.md); a paired device too, as a full client, ADR 0034; closing kills what has the terminal as its controlling terminal), and add log lines (`Log`: 2 KB a message, 16 KB a stack, 16 attributes, escaped so one can't pose as another). Mentioned and attached files, outside the folder too, go to the agent as `file://` links, which it reads under its own rules (ADR 0091). A device's files sent whole (`SendPrompt`'s `uploads`, 8 MB each, 10 a message) are saved 0600 in the data folder's `uploads/<chat>/<random>/` under their name's last part (control characters and bidi marks dropped; the app shows any file's name with its bidi marks visible), saved only once the chat takes the message (a refused one leaves none), at most 100 MB a chat (the oldest go, never one a queued message still links), removed with the chat (a fork, or a kept side chat, hard-links those it links into its own folder first, a copy where it can't); Nushi never opens or runs them. A refused or failed one's name reaches the app, never the log (`api.loggable`: only too large, or the system's reason).
- **A project's icon** (ADR 0112; `GetProjectIcon`, `internal/projecticon`): for a project's tile in the Mac's sidebar the daemon reads one small image out of the project's folder, a repository anyone may have written. The client names only the folder, an absolute path; the daemon looks at a fixed list of paths in it (`icon`, `logo`, `.github/icon`, `.github/logo`, `assets/icon`, `assets/logo`, `docs/images/logo`, `build/icon`, `src-tauri/icons/icon`, `public/icon`, `public/logo`, `public/favicon`, `static/favicon`, `web/favicon`, `app/web/favicon`, each as `.png` then `.jpg`, and the PNGs of `Assets.xcassets/AppIcon.appiconset`, alone or under `macos/Runner` or `app/macos/Runner`, 64 names of each at most), through `os.Root` and `internal/regularfile`: only a regular file inside the folder, no link followed (not one that stays inside it either), a fifo or device never opened (an icon set only when a folder by Lstat, not a link, and opened as a folder that never waits), 256 KiB at most (a larger one is passed over, not cut). A file is sent only if its first bytes are a PNG's or a JPEG's and its header (`internal/imagesize`; nothing is decoded in the daemon) says 32 to 1,024 pixels a side, no more than half again as wide as high; the type sent is the bytes', not the name's. No SVG (a document, with links and scripts of its author's) and no ICO. The app draws the bytes with Flutter's own decoder, scaled into a tile, and shows the project's initials if they don't decode; it asks once per folder and keeps the answer in memory until it quits, never on disk. The daemon doesn't know the sidebar's projects (the app keeps them), so the folder isn't checked against a list: the call is refused to a paired device (`macOnly`) and the handler checks it came on the Mac's socket (`onMac`), where `ListFiles` and `GetFile` already read any folder. Nothing of the image is logged.
- **A tile's own image** (ADR 0112; `tile_images.dart`): the one file the app itself reads from a place the user picks, in Change tile…'s Choose image…, through the system's file panel. It must be a regular file of 16 MB at most (asked before it's read, and checked again on what was read) whose first bytes are a PNG's (its whole signature), JPEG's, GIF's (87a or 89a) or WebP's, whatever its name (`images.dart`'s `imageKind`, which also says which prompt images go as they are), and which Flutter's decoder decodes; anything else is refused with a line in the dialog, and no SVG is taken. Nothing is kept until Save: then a copy goes to `tiles/` in Nushi's data folder under 32 random hex digits and the kind's ending, written whole, the file 0600 and the folder 0700, and `app.json`'s `projectTiles` names the copy, never the path picked, which isn't read again. A name of any other shape in `app.json` (hand-edited) is no image: nothing outside `tiles/` is read or deleted by name. The copy is deleted when it's replaced or removed, on Reset and on Remove from sidebar. It's only ever kept at a tile's size (its shorter side to the tile's, in the screen's pixels), so a huge picture can't fill memory with its bitmap: a still is decoded at that size; the engine decodes an animated one's frames whole, one at a time while it's decoded or plays, each scaled down and let go, so an animated image of more pixels than 4K (3840 × 2160, read from its header before a frame is decoded) is refused; the file's bytes are in memory while it's decoded and while an animated one plays under the pointer, not at rest. A framing (`TileCrop`, a zoom of at most 8 and a centre, kept in `projectTiles` beside the name) changes none of that: a still is decoded so its framed square is the tile's size, at most 8 times the tile's side, and only that square is kept; Change tile…'s framing square decodes the first frame once, its shorter side at most three times the square's pixels (672 at a scale of 2), and lets it go when the dialog closes. A trim (`TileTrim`, two frame numbers) is no different: the frames before its start are decoded and let go one at a time, never kept; for an animated image the dialog decodes every frame once, in order, keeping only its strip's thumbnails (about 24 at once, at the strip's height) and the frame shown, and holds the file's bytes (16 MB at most) until it closes. Nothing of it reaches the daemon, an agent or the network.
- **Agents run as you** (ADRs 0037, 0048): your CLIs from the login shell's `PATH`, with its environment, secrets included, read by the daemon running your shell (`-l -i -c`, its config runs; 5 s, then killed with what it started); the values stay in the daemon's memory and the agents' processes (names only in the log, at DEBUG; the API carries the shell, when, and why it failed); `NUSHI_*`/`NUSHID_*` (a chat's tools key among them) never reach an agent; a chat's folder reaches the agent only as `cwd`. Claude's agent gets `CLAUDE_CODE_ENABLE_TODO_TOOLS=1` unless that environment sets it, which gives the model Claude Code's task tools: they keep the session's to-do list as files in Claude's config folder (`tasks/`), and run nothing. Adapters (Codex's) install with `npm ci` from lockfiles pinning version and sha512 (no install scripts or optional packages; npm writing only in `agents/`: on the Mac under `sandbox-exec`, on Linux under bubblewrap (`bwrap` from the agents' `PATH`, where `npm` is found too: every file read-only, `/tmp` too (npm's `TMPDIR` and cache are in the install's own folder), `agents/` read-write, a `/dev` and a PID namespace of its own, the network shared; no unprivileged user namespaces or no `bwrap`, no install, never one unsandboxed), reads allowed everywhere on both; your registry applies, checked against the hashes) and run as `node <program>` from the data folder (a project's `node_modules` or `.npmrc` can't swap them; the first `node` on `PATH`). Finding agents runs `--version` (and `claude auth status`) as you, as a chat would, 10 s at most.
- **A side chat's mode** (ADR 0060's amendment, 2026-11-05): the mode is the agent's permission control, and a side chat runs tools in its chat's folder as the chat does. It starts in its chat's mode (and on its picks), set on its session as on any open of a chat's, as Fork chat does, and read once its session has forked; none opens while the chat reopens, moves or rewinds (the agent reports the new session's defaults until the chat's mode is back on it); before, it ran in whatever mode the agent gives a fork (its default), with no way to change it, a chat in Manual or Plan included. If the agent refuses, the side chat shows the mode the agent reports, never the chat's. A mode picked in it changes only its session: not its chat's, and not the mode new chats start in (`agents.json`). Keep as chat keeps it.
- **Codex**: codex-acp tells Codex to trust every session's cwd, so a folder's `.codex/config.toml` (MCP servers, commands' environment, sandbox, plugins) and rules load without asking; Nushi's card is the only warning (ADR 0029), keyed by a hash of every file shown and checked again on "Start anyway"; links aren't followed; Codex's trust record is only read. Codex snapshots each thread's shell environment, secrets included, into `$CODEX_HOME/shell_snapshots/<thread>.sh` (0644).
- **Ante** (`ante serve --stdio` under `nushid ante-acp`): the bridge reads only `ante catalog`, sessions' `meta.json` and a subagent's event log (at most 64 MB, a regular file, for an id of Ante's form or, for a cancelled call, the session's own subagents' logs; shown as any tool call's output), and removes a session's folder only for an id of Ante's form; prompt images go to a private temp folder removed when it ends, a big one decoded and scaled down first (`internal/imagefit`: PNG, JPEG, GIF and WebP with Go's own decoders, none past 36 megapixels by its header (144 MB of 8-bit RGBA, twice that for a 16-bit PNG); one it can't decode goes as it is). **omp** loads a project's extensions, hooks, tools, command modules and LSP servers without asking; the card shows each whole (ADR 0031); its bash asks, its writes don't. **opencode** asks nothing and keeps no trust record (and Nushi's listing the agents runs `opencode --version`, which makes opencode's folders in your home if they aren't there): opening a folder imports its plugins into opencode's own process and starts its local MCP servers at once, and its agents may use every tool unless a rule says otherwise. Nushi's card is the only warning (ADR 0031's amendment; `internal/opencodetrust`): it shows whole, from the chat's folder and every folder above it up to `/` (opencode's own walk, past the repository's root), each `opencode.json`/`.jsonc` (there and in `.opencode`), `.opencode`'s plugins, tools, agents, modes, commands and skills, and `.claude/skills` and `.agents/skills`; above a config, what it imports, starts, runs and allows without asking, the package a model provider imports into opencode (installed from npm if missing), where it sends that provider's requests (your key for it goes with them), the environment variables it takes that key from and the headers it adds (names only), the references it has opencode clone or read, and the files (`{file:…}`) and environment variables (`{env:…}`, names only) it copies into its settings. The home folder's own and opencode's config folder are left out, as is `AGENTS.md`. Nushi only reads, regular files only, and reads nothing through a link: a linked file or folder shows as a link and asks every time, unless the link leads to one of those places or into it (a skill in `.claude/skills` linked to the one in `.agents/skills`, as Link for Claude… makes it), where what it leads to is shown and hashed as itself; such a link is remembered by its text and the path it resolves to, so one that leads elsewhere asks again. Only a link in a skills place that leads into one is remembered: any other (an `opencode.json`, `.opencode` itself, anything in its plugin, agent or command folders) asks every time wherever it leads, since opencode would load what it leads to as more than the skill's file the card shows. To know where a link leads Nushi resolves it, which looks at each name on its way, wherever that is, and opens no file. What a config names outside those places (a plugin's path, a server's script, a `{file:…}`) is named, never read, so a change to it doesn't ask again. The one thing looked at is a plugin's path inside the config's own folder (a stat through an `os.Root`, so nothing outside it, and nothing opened): a file there is one opencode refuses, and the card says it isn't imported while it is a file, where a folder in its place would be. **Pi and PiG** (ADR 0039, 0078) **run every tool call without asking**; a folder's `.pi` or `.pig` loads only once trusted in that agent (the bridge refuses a Pi older than its `Min`, which has that gate), `AGENTS.md`/`CLAUDE.md` regardless; the bridge trashes a session's file only for an id whose header it found. Both bridges read a write's old text from a regular file of at most 1 MB, no links (`internal/toolcall`).
- **opencode's process** (`internal/opencode`; `docs/facts/opencode.md`): your `opencode acp`, 2.0.0 or newer, found and started as every agent is (above); it keeps a server child of its own on 127.0.0.1, with a random port and password, while it runs. Nushi stops it with SIGTERM (`agentproc.StopBySignal`), and closes its input and kills its group only once it has exited or after the grace: its input closing alone makes it exit at once and leave every shell command it ran, the background ones too, running with nothing over them. So stopping the agent ends its background commands, a chat going to sleep included; Nushi neither lists them nor stops one alone. Nushi never opens opencode's store (`opencode.db` in its data folder: every session, and its sign-ins): its sessions are listed, loaded, forked and deleted only by asking a running opencode, and Delete deletes one for good. It is handed no MCP server, so none of Nushi's tools (ADR 0068's note): it calls a client's tools from a script in its `execute` tool and asks nothing, so the user would approve nothing and see each call only after it ran. Of the commands it advertises only `compact` is offered: the others answer at once over ACP and then run a turn Nushi doesn't see, whose permission requests never arrive. One typed by hand goes out as any prompt does.
- **Trust** reads `~/.claude.json`, never writes it ("Start anyway" goes to `trusted.json`); trust of the home folder or `/` covers that folder only, and `~/.claude` is never the home folder's own. It fails closed: it lists any string setting named like Claude's credential helpers (`…Helper`, `…AuthRefresh`, `…CredentialExport`), a skill's raw front matter when it has hooks, a `.mcp.json` it can't read. A chat on a pull request is checked again in its new worktree before the agent starts, and a fork's head counts no earlier trust; its "Start anyway" holds only for the commit the card showed (ADR 0023's amendment).
- **Git** runs as you in a client's folder with `core.fsmonitor` off, `--no-ext-diff`/`--no-textconv`, `core.hooksPath=/dev/null`, signature checks off, `GIT_NO_LAZY_FETCH=1`, `--ignore-submodules=dirty`, and the panel's status without filter drivers (Changes and new worktrees still run them: git-crypt, lfs). Starting a chat on a pull request runs `git fetch` in the folder with the repository's own transport config live (`core.sshCommand`, `remote.<name>.uploadpack`, `credential.helper`, `url.*.insteadOf`), as the user's own fetch would: a downloaded folder's `.git/config` can run a command there, before any card (ADR 0023 accepts what a downloaded folder's `.git/config` brings; blanking those keys would break per-repository ssh setups). Nushi writes into a repository only `.worktrees/`, `info/exclude` and what Stage and Commit write (below), never through a link, switches a folder's branch when the user picks one (`git switch --no-guess`, a local branch, the name checked by git's rules first; its smudge filters run, as for a new worktree), and renames a worktree's branch it made (`git branch -m --`, so an old name like `-f` stays a name; the name checked by its rules and `git check-ref-format --branch`, never one on a remote); reads only regular files, 1 MB at most (64 MiB for Claude's settings and `.mcp.json`); refuses bases and commits starting with `-`; forces a worktree removal or `branch -D --` only when asked after the app showed what's lost (the daemon checks again). Moving a chat writes nothing into Claude's projects folder itself: the Go agent's fork writes the new session there (below; ADR 0014).
- **A file's changed lines** (`GetDiff` with `path`, API 121): the Files pane's source preview asks for one file's change against HEAD, with the file's own folder as `folder`, again each time the shown file changes on disk, a turn ends or the app commits, so with no click behind it. It runs Changes' own git (the raw diff, numstat and untracked listing, filters on as there) over that folder only, and one `ls-files -z -- :(literal)<path>` more; it reads that one file's HEAD text and work-tree text, as Changes does (1 MB a side). The path must be local to the folder (`filepath.IsLocal`, else InvalidArgument), a symlink is skipped (`a link`, never followed: git's text for it is its target's path) and a file git doesn't track, an ignored one included, comes back skipped (`not tracked`), so nothing is compared against text git never had.
- **The Files tree's dots** (`GetDiff` with `names`, API 123): the Files pane asks which files differ from its marks' base when it opens and after its listings change, a turn ends or the app commits, so with no click behind it. It runs `git diff --raw` against the work tree with the repository's own filter drivers off (`noFilters`, as the panel's status), and `ls-files --others --exclude-standard`, which reads no file's content; it reads no text and sends only paths and statuses.
- **Stage and commit** (ADR 0079): only from a click in Changes, the Mac's calls. `StageFiles` runs `git add -A` or `git reset -q` on paths given on stdin, literal, each checked to be inside the folder, as Git above (filters run, as in the user's own `git add`). `CommitStaged` is the one git Nushi runs with the repository's hooks on: `git commit -F -` in the login shell's environment, so pre-commit hooks, `commit.gpgsign` and `gpg.program` run as you, a folder's own included, with no trust card; only `core.fsmonitor` stays off. It refuses when the index or HEAD moved since the app read them, or when files outside the folder are staged, and is killed with what it started after 5 minutes. The message is the user's, 64 KiB at most, never logged; what a failing commit printed reaches the app plain, its last 4 KiB, and never the log (a hook can quote the message: commitlint's `input:`). `WriteCommitMessage` (a click; Claude and Codex) sends the staged diff, secrets' shapes masked, cut at 64 KiB, between random marks, to a throwaway fork of the chat's session in its read-only mode: so to the agent's provider, as anything the agent reads. A permission ask there is declined, the first tool call ends it (one a user's rule allows outright can start), and the reply is only text in the field.
- **MCP**: Claude's config holds secrets in clear; the daemon masks them before they leave it. It runs `claude mcp add-json/remove/login/logout` (names checked, `--`; `login` under `/usr/bin/script`, given the path Go's lookup found, so a relative `PATH` entry such as `node_modules/.bin` never runs a folder's own `claude`; on Linux util-linux's `script -c` takes the command as a shell's line, each word single-quoted and run by `/bin/sh` (`SHELL` set to it), so a name can't split or expand into another command), so a client can add a server Claude runs as you, as a prompt could. The switch writes only the two MCP lists of the project's `.claude/settings.local.json` (atomically, keeping its mode) and may add it to `.git/info/exclude`. A user or local server's switch runs `claude -p --bare` in the folder with two control requests on stdin (the name as JSON), which writes `~/.claude.json` itself; `--bare` runs none of the folder's hooks, helpers or servers. Ante's (ADR 0058): its settings hold secrets in clear too, masked the same way; Nushi writes only `mcp_servers` of `$ANTE_HOME/settings.json` (under Ante's flock, atomically, keeping its mode; a file that isn't JSON refused), so a client can add a server Ante runs as you; Check runs `ante serve` in an empty temp folder, which starts every server in your settings. On a Log in Nushi runs `ante auth login`, or `ante mcp login --force` on Ante 0.2.15, as you, in `$ANTE_HOME`, under `/usr/bin/script` as Claude's (the name checked, after `--`, and only a name in your `mcp_servers`: the command also signs in to providers), having asked `ante <group> login --help` which one it is; Ante opens the browser, listens on a local port and keeps the token in its own files, which Nushi never reads, and any client of the API can start it, a paired phone included, as it can for Claude's. The API's Logout runs `ante auth logout`, with the same check.
- **Skills** (ADR 0051): skills' and plugins' text is its authors' (a plugin's a third party's): shown as plain text (control and bidi characters dropped), never Markdown or links, never sent to an agent. `claude plugin` runs only in Claude's config folder (ids checked, after `--`). Writes are one key each (`skillOverrides`, `disableBundledSkills`, `enabledPlugins`) in your `settings.json` (a link followed) or the project's local settings (links refused), replaced at once. Delete moves a folder to the Trash (`/usr/bin/trash`; on Linux `gio trash` from `PATH`, else refused naming gio) only when it sits right in your skills folder or a project's `.claude/skills` that isn't a link (nor its `.claude`) and holds a `SKILL.md`; Open uses `open -t` (as text, whatever the file is). Other agents (ADR 0052): their settings are written only on a switch, one list each (Codex's `[[skills.config]]` path entries in `config.toml`, as text, the decoded result checked to be the original with only that change; Pi's and PiG's `skills` list in yours or the folder's `.pi/settings.json` or `.pig/settings.json` (there relative, `-skills/<folder>`, every other byte kept, else refused; a linked `.pi` or `.pig` refused); Ante's `exclude_skills`; omp's `disabledExtensions`, only in a file yaml.v3 writes back unchanged; opencode's `policies` in your global `opencode.json`, or an `opencode.jsonc` there without one: one `skill.use` deny entry by the skill's id, put into or cut out of the file's text, every other byte and every comment kept, the decoded result checked to be the original with only that change, else refused naming the file and the entry to add by hand, and a file that doesn't read is never written), links in a project refused, yours followed; a file of yours Nushi makes (Claude's, Ante's, Pi's or PiG's `settings.json`, Codex's `config.toml`, omp's `config.yml`, opencode's `opencode.json`) is 0600 in a 0700 folder if that's new too (`atomicfile.Rewrite`), and one that exists keeps its mode (a project's local settings stay 0644, as git would make them). Link for Claude makes a relative symlink in `.claude/skills` (never through a linked `.claude`, nothing replaced) only to a shared skill some agent lists. A path the app sends (Delete, Link) must be a skill Nushi listed, right in a listed root; the list says of each skill whether its path is one file (`one_file`) and whether Delete (`no_trash`) or Link for the listing's agent (`no_link`) would refuse it, by the checks the calls themselves refuse by (`skillfile.CanTrash` in each reader's own places, opencode's `Refuse`, Claude's `CanLink`), so the app offers neither there and reads nothing from a path's shape, and the calls still check on their own, whatever the app sends; a shared skill goes to the Trash only when it and every link to it can, nothing moved before that is known; a project's linked roots are never listed; a skill folder that is a link is listed as one and Delete moves the link. opencode's places (`.opencode/skills`, `.agents/skills` and `.claude/skills` from the folder up to `/`, and yours) are read as it reads them, groups of skills six folders deep and links inside a place followed (but not a linked group in a project's place), at most 2000 folders a place; a place that itself holds a `SKILL.md` is one skill to opencode and is listed as that file, never as a folder, also when it is found a second way, through a linked group of yours that leads to the folder it is in, so Delete and Link refuse it and the place, with every skill in it, can't go to the Trash; its switch is read from the policies of your global `opencode.json` and `opencode.jsonc` only. No agent runs to list skills. A project's skill is trashed, linked and its settings written through an `os.Root` of its repository, so a folder an agent swaps for a link between Nushi's check and its act can't lead outside; skill folders whose names have control or invisible characters are skipped. Claude's skills and MCP servers run no git in the folder since 2026-10-29: the repository's top and the project are read from its files (`skillfile.Top`, `git.TrustRoot`, whose one `git config --file` only reads the main checkout's config file), as the trust card does.
- **Words Nushi puts in a prompt** (ADR 0016's second amendment): the note of a branch renamed, fixed words around two branch names that git accepts (`check-ref-format --branch`, after Nushi's own rules: no spaces, control characters or `..`); its own text block, never merged into the user's. A user's message the agent replays loses a leading text of exactly that shape.
- **Files someone else chose** (a repository's settings, a skill, a file a model names, a background shell's output (only `<tmp>/claude-<uid>/<project>/<session>/tasks/<id>.output`, `<tmp>` being `$CLAUDE_CODE_TMPDIR` as the daemon has it or `/tmp`, as Claude names it, its last 64 KiB), a folder's `.git` file and the worktree record it names, read for the trust key at 64 KiB) are read through `internal/regularfile`: only a regular file, checked before the open and on the open file (a fifo isn't waited on, a device isn't opened), a link followed only where the agent follows one, and at most so much (64 MiB for agents' settings, 4 MiB for a `SKILL.md`, 1 MB for a write's old text, 5 MB for a preview); one that grows past that while read is refused, not cut (Codex's `config.toml` was cut at 64 MiB and decoded, until 2026-10-29). What a folder brings Codex, Ante, omp and opencode is read for the trust card by one walk (`internal/folderfiles`): each file whole for its hash, at most 4,096 files, folders and links and 64 MiB in all. Past either the walk stops, the card's last row says the rest wasn't read, and the folder can't be remembered (it asks every time); a file over 256 KiB is hashed and named, and none of its text kept.
- **Stopping a background command** (ADR 0065): the daemon reads the command lines of the processes below a chat's agent (`kern.procargs2`, the user's own processes only; never logged) and sends SIGTERM, then SIGKILL, to one process group: the one whose leader is below the agent's process, is still the process found (its start time) and runs exactly the call's command, checked again just before the signal; the SIGKILL only while every process in the group started before the SIGTERM. An agent could start a process whose command line mimics another call's command: it then gets that group stopped, as it could stop it itself. The next prompt carries a fixed `[Nushi]` note naming the task's id. Whether a command runs, and how it ended, is Claude's task status where Claude sent it (claude-acp-go v0.5.0 on, `_meta.claudeCode.task` on the command's call; ADR 0130): read from the agent's own updates, nothing more on disk. Addresses from GitHub leave the daemon only when http(s) (`webLink` checks again). The inbox GitHub gave last sits in `cache/github/<host>.json` (0600). - **What isn't valid UTF-8**: git takes any bytes for a path, a branch or a subject, a file's text is whatever it is, and an agent chooses all of them; a proto3 string can't hold them, and one in an event would end the client's `Events` stream. - **The daemon on Linux** (ADR 0101): its data folder is `$XDG_DATA_HOME/nushi` (an absolute one), else `~/.local/share/nushi`, 0700 as on the Mac. The login shell is your passwd entry's (`getent passwd <uid>`, which asks NSS, else `/etc/passwd`), else `$SHELL`, else `/bin/sh` (not zsh, which Linux often lacks; also for a shell whose `-c` the login line isn't written for). While remote access is on it runs `systemd-inhibit --what=idle:sleep --mode=block tail --pid=<its pid> -f /dev/null` (found on `PATH`), idle and sleep block locks that end with the daemon: the sleep lock is what stops GNOME's idle suspend (gsd-power ignores idle locks); closing the lid still suspends, and a suspend you ask for may first ask to override it; without systemd, or when logind refuses it, the machine may sleep, and the log says so. The data folder `-login` picks from its launcher's environment is passed to the daemon through the login shell (`NUSHID_DATA`), so a profile setting `XDG_DATA_HOME` doesn't move it; the daemon unsets it (and `NUSHID_BIN`, `NUSHID_LOG`) once read, and a terminal, as an agent, gets no `NUSHI_*`/`NUSHID_*` variable, so a dev daemon started from one can't take the real data folder. Proxies come from the environment alone, as the daemon was started with it: HTTPS_PROXY or HTTP_PROXY by the URL's scheme, ALL_PROXY for a scheme whose own is unset (as curl does), each with NO_PROXY; no gsettings, no PAC file. The relay's connection takes an http, socks5 or socks5h proxy, not an https one.
- **The daemon on Windows** (ADR 0124; it builds, and isn't shipped): its data folder is `%LOCALAPPDATA%\Nushi` (else under the home's `AppData\Local`), or `NUSHI_DATA`. Windows has no mode bits for the 0700 the Mac sets, so at each start the daemon gives the folder a protected DACL (`ownDataFolder`): full access for you and SYSTEM, nothing inherited from the folder above (a `NUSHI_DATA` such as `C:\nd` would otherwise inherit Authenticated Users' Modify, and any account could read or plant the token and so reach the socket), which the files in it, the token's and the socket's included, inherit. It refuses to start when the folder is a link or junction (checked on the folder opened as itself, which stays open, not shared for delete, until its DACL is set, so it can't be swapped in between: a junction's DACL would land on its target, and whoever made the junction could point it elsewhere), belongs to another account (an elevated administrator's Administrators counts as yours) or the DACL can't be set. What another account put in the folder while it was open would stay that account's (an entry's owner can always change its DACL, and the folder's reaches neither an entry's own ACEs nor one whose DACL is protected): a planted `agents` folder would run its code as you, a planted `nushid.sock` would get the app's token. So when the folder wasn't already yours alone, every entry in it is checked once the DACL is set, links and junctions as themselves, and the daemon won't start, naming the entry, while one belongs to another account, has a protected DACL or has an ACE letting in anyone but you and SYSTEM; remove it and it starts. A clean check leaves `entries-checked` in the folder, and a folder already yours alone with that file in it isn't walked again, since no other account could have added anything since. At the first command bound to its context (`procgroup.Bound`, ADR 0133) the daemon puts itself in a job object whose one limit lets a process started with `CREATE_BREAKAWAY_FROM_JOB` leave it (`JOB_OBJECT_LIMIT_BREAKAWAY_OK`; without it such a start would fail with access denied), whose completion port tells it of each process created below it and each exit; it opens each new one (`SYNCHRONIZE`, `PROCESS_TERMINATE`, `PROCESS_QUERY_LIMITED_INFORMATION`, the handle held while it lives, so its pid can't name another process), reads its parent's pid and its start, and groups it with its parent, each child of the daemon starting a group. A cancel ends the command's group: what it started, even a process whose parent ended first, and what the port tells of after. Unlike Unix, where a helper that means to outlive the command leaves its group with `setsid`, a cancel also ends a helper the command started to outlive it, unless that helper was started with `CREATE_BREAKAWAY_FROM_JOB`. That is best-effort: the job's messages aren't guaranteed to arrive, and a process whose new-process message is lost, and what it starts, isn't tracked or killed by a cancel; a lost exit is caught by a check of the held handles at each exit and kill, which closes those of processes that have exited. Nothing is killed by the command's exit or the daemon's, as on Unix, and every process the daemon starts is in its job, which limits nothing else; one that asks to break away leaves it, and is then neither tracked nor killed by a cancel. Without that job (the system refused it), the cancel ends the command's process tree with the system's `taskkill /T /F /PID <pid>` (`%SystemRoot%\System32\taskkill.exe` by its full path, never one from `PATH`), which ends that process and every process whose parent chain leads to it; one whose parent ended first isn't found and lives on. The process's own handle is held through the kill, so its pid can't name another process meanwhile, and once it has exited nothing is killed: a stop after the exit (Pi's and Ante's, every time) never reaches a process that has since been given its pid. A program piped to a bridge (Pi, Ante: `procgroup.Start`) is put in a job object as it starts, killed on close, so stopping it ends what it started, even what outlived it; what it starts in the moment before it joins is left. A file opened without following a link (`openflag.NoFollow`, CreateFile's `FILE_FLAG_OPEN_REPARSE_POINT`) opens the link or junction itself, and is refused by the stat after the open rather than by the open, as on Unix. `nushid.log` is opened shared for read, write and delete, so it can be renamed to rotate while open: any process of yours may also rename or delete it then (on Unix any may anyway); its access is the data folder's inherited ACL, as Windows has no mode bits, and the process's standard output and error are a duplicate of its handle. A daemon started with no console (as the app starts it) starts its own program again, with its own arguments and environment and `NUSHID_NO_WINDOW` set (which it then clears), with `CREATE_NO_WINDOW`, and exits: what it starts shares that console, which has no window, rather than opening a window of its own. That daemon's stderr is `nushid.log`, opened by the first only after it has made the data folder and given it its DACL (`ownDataFolder`), so why it couldn't start is in the log the app points at. When `ownDataFolder` refuses the folder, the first starts nothing and stops on the same check itself, saying why on its own stderr, which the app reads (at most about 4 KB) into `app.log`. Whether a Claude record's process is alive, and when it started (`GetProcessTimes`, to match the record's `procStartFt`), is `OpenProcess` with query rights only (refused for access counts as alive, with no start time), nothing else of it read; its `pidDomain` is matched against the host's name (`os.Hostname`). Ante's settings lock is `LockFileEx` on its `.lock` file; no other agent's lock is read. Agents start with the registry's environment (ADR 0126): the system's and your `Environment` keys, read with query rights only, their values kept in memory and never logged, as the login shell's are on Unix; an agent's program is found on that Path with `PATHEXT`'s extensions, never in a folder that isn't absolute. A batch file (`.cmd`, `.bat`) runs through cmd.exe, which reads its command line again by rules of its own (a `"`, `&` or `%` in an argument would end it, start another command or expand a variable), so none is started with Go's quoting (`batchfile`, for every command through `procgroup.Own`, every agent through `agentproc.Start`, and each claude Claude's agent starts): an npm shim (each line that passes on `%*` runs node on one script under the shim's folder) runs as `node.exe`, the one beside the shim, else the first in an absolute Path folder, and that script, with no cmd.exe (and the `NODE_PATH` a pnpm shim sets, its folders as the shim names them, before any already set); any other batch file runs only when its path and every argument have none of `"%!^&|<>()` and no control character, and is refused, saying why, otherwise. The daemon sets `NoDefaultCurrentDirectoryInExePath=1` in its own environment first thing, and every command and agent it starts gets it (`batchfile.Environ`), so neither CreateProcess nor cmd.exe runs a program by a bare name from the current folder, which for an agent is a chat's project. A terminal (ADR 0132) runs on a ConPTY pseudo-console, as you, with the agents' environment (the registry's), not the daemon's. Its program is the one Windows Terminal's default profile opens: for each new terminal the daemon reads Windows Terminal's `settings.json` (the installed app's, its preview's or an unpackaged one's) and the fragments other apps put in `Microsoft\Windows Terminal\Fragments`, regular files only, 4 MiB each at most: yours under `%LOCALAPPDATA%` first, then everyone's under `%ProgramData%`, the order Windows Terminal reads them in, the first that names the profile winning, and a command line in the profile's own entry in `settings.json` above both. Any account may add a file under `%ProgramData%` (Users may create files and folders in `C:\ProgramData`), and Windows Terminal itself checks none, so Nushi reads one there only when all of this holds, read from handles it holds until the file is read (`readMachineFragment`): `%ProgramData%` and each folder below it down to the fragment's (`Microsoft`, `Windows Terminal`, `Fragments`, its source's) is a real folder, not a link or junction, opened as itself and not shared for delete, so none can be renamed or swapped meanwhile; each is owned by SYSTEM, Administrators or TrustedInstaller (not by you: a file of yours there proves nothing about who else could have written its folder); no ACE that applies to a folder below `%ProgramData%` lets anyone else add a file or folder, write, delete, rename or re-own what's in it, or change its access (on `%ProgramData%` itself only the deleting, renaming and changing count, since adding to it can't touch a folder already there); the file is opened once, not followed if it's a link, and on that handle has one hard link only (a second could be another account's link to some other administrator's file), an owner of the three, no ACE letting anyone else write, delete, re-own or change it, and a resolved path (`GetFinalPathNameByHandle`) that is the one looked for under `%ProgramData%`'s own. An ACE of a kind Nushi doesn't read counts as letting anyone in, as does a NULL DACL. A fragment that fails is logged and skipped, and the profile falls back as if it had none (PowerShell 7, else Windows PowerShell); whether installers' fragments pass depends on the folders' ACLs on a real machine, unverified so far: one under a folder that lets Users create files is refused. Whatever can write those files chooses your shell, as it chooses Windows Terminal's. The command line they name isn't run as written: its `%NAME%`s are expanded from the daemon's own environment (not the terminal's), it is split into arguments by the C runtime's rules (`DecomposeCommandLine`), its program is found on the terminal's Path, and it is started on a line joined again with Go's quoting (`ComposeCommandLine`), through `batchfile` as any other command is, so a program that reads its own command line by other rules (cmd.exe's `/c` with quotes inside quotes) may be given a line that means something else than the one Windows Terminal, which passes it on whole, would give it. Closing the terminal closes its pseudo-console, which ends what is attached to it, and kills the program should it outlast a grace; what left the console (a window of its own, a detached program) lives on, as on Unix. The daemon turns Ctrl+C on in itself, under a lock, for that start alone, so the program takes Ctrl+C while the daemon still ignores it. Which program runs on a terminal is read from the system's process list (`NtQuerySystemInformation`, which opens no process), a process's command line with query rights only (`NtQueryInformationProcess`, `proctree`); a dev server's stop is Ctrl+C typed on its terminal, then `TerminateProcess` for what's left under it whose start time still matches, read (`GetProcessTimes`) on the one handle the process is then ended through, so a pid given to another process meanwhile is never ended. Localhost's listeners (ADR 0133) are read from iphlpapi's TCP tables (`GetExtendedTcpTable`): every user's listening sockets, each address, port and owning pid, nothing of the processes themselves, kept for the identity check and never written anywhere. The memory card's figures are each process's private bytes (`GetProcessMemoryInfo`) and the process list Toolhelp's snapshot (pids and parents' pids), each process opened with `PROCESS_QUERY_LIMITED_INFORMATION` alone for that and, only for the processes a walk down from a reported tree reaches, its start time; a process that can't be opened so (a service's, a protected one) counts 0. Everything else that reads the keychain, proxies or keep-awake is off there (ADR 0124).
