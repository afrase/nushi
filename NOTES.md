## Step 33: what the trim pass took out

The app went from 6,623 lines of Dart (after the scroll fix, 6,634) to 6,364: about 270 lines, short of the goal of 6,000. What went, roughly:

Net about −180.
- **No Material ink or elevation**: the theme turns splashes off and gives menus and dialogs one faint shadow and a border; a small `Tap` (hover tint, no ripple) and `IconTap` replace `InkWell`/`Material` pairs and `IconButton`s in the sidebar, Changes list, cards, tool calls, thinking, question options, reply cards, images and the selection toolbar. Dialogs use one `nushiDialog` and a `confirm()` with the app's buttons; text fields take their look from the theme. Mostly line-neutral (theme +46), but it removed most per-site styling.
- **Merged duplicates**: the Changes view and the edit diffs share one `DiffBox` (tool calls −88 with the shorter group label); the Changes view and the details panel share the reload-when-the-turn-ends logic (`FollowsChanges` mixin; details panel −40); one `tryOrShow`/`showError` instead of seven snack-bar blocks; the folder name and path come from one `folderParts`; the daemon's ten one-line wrappers around RPCs went (callers use `daemon.client` directly, −60); the panel's card rows take plain strings.

- The daemon: nothing cheap to take out (`deadcode` finds nothing); unchanged.
- What's left is mostly behavior. Getting under 6,000 would mean dropping features (the compatibility gating for older daemons, the reply-card editing, the side chat's own composer) or reformatting to a wider line; neither seemed right for a trim.

## ACP quirks

- `session/new` requires `mcpServers`: send `[]`, never `null`.
- claude-agent-acp 0.94.0 puts a `messageId` on every `agent_message_chunk`; chunks are grouped into messages by it (by the last message when it is missing).
- The adapter logs progress (`[session/create] ...`) on stderr; nushid copies it into its log.
- Usage (claude-agent-acp 0.94.0, step 20): each turn ends with two `usage_update`s, `{used, size}` and then the same with `cost: {amount, currency: "USD"}`, the session's cost so far. `size` was 1,000,000 for Opus 5.5 here; `used` is the context after the turn. The cost is the session's so far, but across agent processes it isn't reliable: in one probe the first turn after `session/load` carried on from the earlier turns ($0.19 → $0.22), in the app after a daemon restart it started again near zero ($0.15 → $0.02). Nushi shows what is reported. `session/load` itself sends no `usage_update`, so a reopened chat has no usage until its next turn. One `usage_update` after a load also carried `_meta._claude/rateLimit` (five-hour and seven-day utilization); not shown. The prompt result carries ACP's unstable `usage` (`inputTokens`, `outputTokens`, `cachedReadTokens`, `cachedWriteTokens`, `totalTokens`, summed over the turn's model calls, so cache reads can exceed the context) and a `_meta.quota` with the same per model.
- Claude names its sessions itself: soon after the first prompt it sends `session_info_update` with a short title ("Apple" for "Reply with just the word apple."). Nushi uses the first line of the first prompt until then.
- `session/load` on Claude replays the user's messages, the agent's messages and the tool calls (with their final status and output), not permission prompts or questions. Messages carry `messageId`s in the replay too. Loading a session takes under a second once npx has the adapter.
- Claude's tool calls arrive as a `tool_call` with a generic title ("Terminal", "Read File") and empty `rawInput`, then `tool_call_update`s that set the real title (the command, "Read notes.txt"), then content. The first content is the command's description; the final one (with `status: completed`) is the output in a fenced block. Each update's `content` replaces the previous one.
- Claude 2.1.308 searches and lists with `Bash` (`grep -rn`, `ls *.md`), not its Grep and Glob tools, so searches show as commands. A failed command's output starts with `Exit code N`; there's no exit code field. An `Edit`'s ACP `diff` holds the edited snippet (`old_string`/`new_string`), not the whole file. Tool calls carry `locations` (absolute paths) once the real title arrives.
- Claude sends no `agent_thought_chunk`s here: the adapter says recent models stream thinking "omitted" (signature only), and neither `showThinkingSummaries` in the project's settings nor `MAX_THINKING_TOKENS` (Opus, Sonnet, Haiku) changed that. Thoughts are built to ACP and were tried with the fake agent only.
- Claude keeps a todo list (ACP `plan` updates, full list each time) only when its todo tools are on: `CLAUDE_CODE_ENABLE_TODO_TOOLS=1` in its environment. Without it, `TodoWrite` and `TaskCreate` aren't there and Claude says so. With it, Claude uses `TodoWrite` or `TaskCreate`/`TaskUpdate` (the adapter hides the task tool calls and sends the plan). In Plan mode Claude writes the plan before asking to leave Plan mode, so the checklist sits above the approval card.
- `session/cancel` on Claude ends the turn within a second or two with stop reason `cancelled`; the text streamed so far stays. A command Claude runs in the background can finish after the turn and Claude then writes again on its own, outside any prompt (a tool call and a message arrive while the chat is idle).
- Claude sends `available_commands_update` soon after `session/new` (and after `session/load`): about 80 commands, its own and every installed plugin's and skill's (`/code-review:code-review`). A command goes back as an ordinary prompt starting with `/name`. A `resource_link` to a `file://` URI in the prompt makes Claude read the file.
- claude-agent-acp 0.94.0 advertises `sessionCapabilities.fork` (and `close`, `resume`, `list`, `delete`). `session/fork` copies the session's transcript into a new session on the same agent process, which then knows the whole conversation; prompting it doesn't touch the original. Updates for the fork arrive on the same connection, tagged with the fork's session id. `session/close` ends it.
- Replaying (`session/load`) a turn that was cancelled shows a user message "[Request interrupted by user]": Claude stores it in its history.
- claude-agent-acp 0.94.0's `session/fork` with another `cwd` fails ("Internal error"): it looks for the source session only in the new folder's history (and its git worktrees). The SDK's `forkSession` writes the fork next to the source. A transcript copied into the new folder's history and reopened with `session/load` (same id, new `cwd`) does resume, but the adapter's replay of a loaded session reads whichever copy of that id it finds first across all folders, so the replay can be the old, shorter copy. Hence the fork ([ADR 0014](docs/adr/0014-moving-a-chat-forks-it.md)).
- Claude names a session's history folder after the session's cwd: the real path (symlinks resolved, `/tmp` is `/private/tmp`), NFC, every UTF-16 unit that isn't an ASCII letter or digit replaced by `-`; past 200 characters it is cut and a base-36 hash of the path added. `CLAUDE_CONFIG_DIR` moves the whole projects folder.
- After a fork (or a move), the cost Claude reports starts again from about zero.
- claude-agent-acp 0.94.0 advertises `sessionCapabilities.delete`. For a client like Nushi (not its "AIR" clients, which it archives for instead), `session/delete` is the Agent SDK's `deleteSession`: it looks for the session in every project folder (the request has no `cwd`), removes `<id>.jsonl` and the `<id>/` subagent folder, and succeeds for a session that was never written. It tears a session the same process has loaded down first. It leaves the folder's history folder (and an empty `memory/` in it) behind.
- Claude also sends a `tool_call_update` carrying only `_meta.claudeCode.toolResponse` (the raw tool result) before the final one; it changes nothing we show.
- In `auto` mode Claude asked nothing for `curl -X POST` or `touch`; in Manual (`default`) mode it asks before `touch`, with two options, "Yes" (`allow_once`) and "No" (`reject_once`). A permission request names the tool call it is about (`toolCall.toolCallId`), which was sent just before as a `tool_call`.
- To test prompts without a mode picker, a folder with `.claude/settings.json` = `{"permissions":{"defaultMode":"default"}}` starts Claude in Manual mode.
- AskUserQuestion needs the client to advertise `elicitation.form`. Claude first sends a `tool_call` ("Asking for your input", kind `other`), then `elicitation/create` in form mode, tied to it by `toolCallId`. Each question is a property `question_N`: a `string` with `oneOf` (single choice, options with `const`, `title`, `description`) or an `array` whose `items.anyOf` lists the options (multi-select), followed by an optional free-text `question_N_custom` titled "Other". Nothing is `required`. An accept with empty content reads to Claude as "the user did not answer"; it reads each answered question back as `"question"="answer"`.
- The form's properties must be read in wire order (they are the questions' order), so the generated types keep maps of typed values as raw JSON.
- Claude starts new sessions in whatever mode its settings say (`auto` on this machine), and reports modes both as legacy `modes` and as a `mode` config option, as the POC found. Nushi shows only the config option.
- Claude 0.94.0's config options: `mode` (Manual, Accept edits, Plan, Auto, Bypass permissions), `model`, `effort` (category `thought_level`), `fast` (category `model_config`, a select of on/off rather than a boolean) and `agent` (no category: the subagent to run as). `set_config_option` answers with the full new set of options.
- Subagents (claude-agent-acp 0.94.0, step 39): every update a subagent makes (its tool calls, text, thinking) carries `_meta.claudeCode.parentToolUseId`, the id of the Agent/Task tool call that started it; tool calls also carry `_meta.claudeCode.toolName`. The Agent call's `subagent_type` comes in its `rawInput`, sometimes only in a later `tool_call_update`. A subagent's text and thinking are sent only when the client's `initialize` capabilities say `_meta: {"subagent-transcript": true}` (Nushi does now). Claude here (2.1.308) starts Explore subagents in the background: the Agent call completes at once with "Async agent launched successfully…", the subagent works on, and it ends with a `SubagentHandback` tool call whose `rawInput.message` is its report (its output is only `{"success":true,…}`); the main agent is told later. `async_task_*` updates (background tasks) are sent only to AIR clients, so Nushi gets none. After `session/load`, the Agent calls come back (with their type) but not a background subagent's steps or report: they live in Claude's `subagents/agent-*.jsonl` files. A foreground subagent's replay wasn't seen (Claude chose the background each time).
- Forking at a message (claude-agent-acp 0.94.0, step 48): `session/fork` with `_meta.jetbrains.air.fork = {version: 1, messageId}` keeps the conversation up to the agent message with that ACP `messageId`, it included (the SDK's `forkSession(upToMessageId)`); the adapter maps the id to Claude's entry through what it saw live, or by searching the transcript, so it works after `session/load` too (tried: rewound, restarted the daemon, rewound again). The id of an assistant message is Claude's API message id, the same live and in the replay. The adapter reads the meta for any client, not only AIR. A fork's replay shows just the kept part.
- Throwaway sessions (step 50): `session/delete` of a session the process has open tears it down, but Claude then writes a small stub of it back (`last-prompt`, `custom-title`, `cost-state`, about 700 bytes) as it ends; `session/close` first does the same. A second `session/delete` a few seconds later removes the stub. Side chats left such stubs since step 18; they now get the second delete too. A fork's `/context` reports the same numbers as the chat (it was within 0.2k of the chat's `usage_update`).
- Steering (claude-agent-acp 0.94.0, step 47): the initialize response's top-level `_meta.steering.supported` advertises `_session/steering` (`{sessionId, prompt, _meta: {steering: {idleBehavior: "promptRequired"}}}`), which answers `{outcome: "injected"}` when a turn runs or `"promptRequired"` (and does nothing) when none does. An injected message pre-empts the model's current generation; during a foreground tool call it moves that tool to the background, so Nushi steers right after a tool call ends. The running `session/prompt` then ends only once the steered messages are answered. The adapter echoes nothing for the steered message: the client shows it. Claude here won't run a foreground `sleep 30` (its harness moves it to the background and the turn ends early), so long-turn tests use several `sleep 10`s or a long text reply.
- `/context` (claude-agent-acp 0.94.0, step 40) is answered by the adapter itself (no model call, no cost, no usage update) as agent text: a markdown "Context Usage" with the model, the tokens used of the window, an "Estimated usage by category" table (System prompt, System tools, MCP tools, MCP server instructions, MCP tools (deferred), System tools (deferred), Custom agents, Memory files, Skills, Messages, Free space, Autocompact buffer; counts like `2.5k`, `622`, `934.6k`), then tables of MCP tools, custom agents, memory files and skills. It came twice, as two messages with different ids and the same text. It isn't replayed by `session/load`.

The confirmation lists what goes: the agent's history of each session the chat had (id and folder), the scratch folder if there is one, and Nushi's record; it is filled in by `PlanDeleteChat`, and deleting happens in the dialog ("Deleting…", errors shown there). The daemon deletes the history on a new agent process (the chat's own agent stops first), one `session/delete` per session, then the scratch folder, then the record; if the agent fails, the chat stays.

- Worktrees (step 30, [ADR 0016](docs/adr/0016-a-worktree-per-chat.md)): "New worktree" is a switch in the Environment card, shown while the chat has no messages and its folder is in git. Flipping it moves the chat (a new session, as for any chat without messages) into a new worktree, or back to the repository, which removes the unused worktree and its branch (plain `git worktree remove` and `git branch -d`, so git keeps them if anything is in them). The choice is remembered per repository (`worktrees` in `app.json`) and applies to the folder's "+" in the sidebar and to a chat without messages moved by the folder control. The switch isn't in the header's folder control (when the panel is hidden): the header doesn't know whether the folder is in git.

A worktree chat with messages moved elsewhere with the folder control (after a confirmation saying the worktree and branch stay) leaves them on disk, and since step 35 the chat keeps them (`EarlierWorktrees` in the session file, beside `Earlier`); Delete… lists each with the same two safe choices as its own worktree, under "A worktree it ran in before it moved" (API 23: `PlanDeleteChatResponse.worktrees`, `DeleteChatRequest.worktrees` by path; the single fields stay for older apps).
- The branch's diff (step 31): `GetDiff` and `GetFolderStatus` take a base branch and count from `git merge-base HEAD <base>` (committed, uncommitted and untracked together). A worktree chat's Changes view has Branch | Uncommitted above its list, Branch first; the choice is per chat, remembered across launches since step 35 (`uncommitted` in `app.json`: the chats showing Uncommitted; a deleted chat's id is dropped), and the Changes card follows it ("Branch +2 −1" or "Uncommitted +1 −0"). A base that no longer exists shows git's error in the view.
- Worktrees when a chat ends (step 32): Archive leaves the worktree and branch alone. Delete… lists them as two checkboxes under what always goes: "Remove the worktree" (on unless it has uncommitted or untracked files, which it then counts in red) and "Delete the branch" (on unless the branch has commits its base doesn't have, `git rev-list <branch> --not <base>`, counted in red; else "main has all of its commits"). The branch can only go with the worktree (git won't delete a branch a worktree has checked out), so its box is disabled while the worktree's is off. The daemon checks again when deleting and refuses to lose changes or commits unless the request says to force (the app sets that only when the warning was shown and the box ticked); `--force` is passed only then. Removing the worktree and deleting the branch happen before Claude's history is deleted; if either fails, the chat stays.
- A worktree folder removed outside Nushi: opening the chat leaves a notice ("Couldn't reopen the chat: its worktree … was removed outside Nushi; deleting the chat cleans up its branch …"), sending a prompt says the same, the Environment card says so in red, Changes says "The folder is gone." Delete offers both choices as usual; removing the worktree is then `git worktree prune` (which drops only the records of worktrees whose folders are gone). The same check covers any chat whose folder is gone. If Nushi can't inspect the worktree (its base branch was deleted, say), the dialog says both stay.
- A chat without messages that leaves its worktree (step 30's switch) now uses the same inspection: the worktree and branch go only if nothing would be lost.
- A chat started in a subfolder of a repository runs in the same subfolder of its worktree and is listed under that subfolder. The base is the folder's branch, or the commit when `HEAD` is detached; a repository without commits can't have worktrees (git says so). ## Security notes to look at

- Agents run as you, with your environment, through `npx --yes @agentclientprotocol/claude-agent-acp@0.94.0` (downloaded from npm on first use, pinned by version, not by hash). npx runs in the daemon's data folder, never the project's, so a project's `node_modules` or `.npmrc` can't swap the adapter (flagged by the automated security review in step 3). The chat's folder must be an absolute path to an existing folder and reaches the agent only as the session's `cwd`.
- A panic while handling something the agent sent is turned into a JSON-RPC error instead of crashing the daemon, and a malformed elicitation form is refused (automated security review, step 5).
- `ListFiles` (step 16) lists any absolute folder the client names (with the client token), through `git ls-files` or a directory walk, 20,000 names at most; it reads names, not contents. Mentioned files go to the agent as `file://` links, which Claude reads with its own permissions.
- `GetDiff` runs `git` in the folder the client names, as you, with `core.fsmonitor` off and `--no-ext-diff`/`--no-textconv`. Clean filters (`filter.<name>.clean`) still run when `git diff` reads the work tree, as they would for your own `git status` there: a filter needs a config entry, which a cloned repository can't carry, so it takes someone who can already write your `.git/config` or global config. The automated review in step 10 suggested going further (an empty attribute source, or diffing blobs without git's work-tree comparison); I left that for you to decide. A symlink in the work tree is shown as its target path (as git sees it), never followed.
- Agent text is rendered as markdown. Since step 25 its images show when they are local files (an absolute path or a `file:` URL, read as you; nothing leaves the machine) or `data:` URLs; a remote (http/https) image only loads after a click on its "Load image", one image at a time (an image URL in a tool's output could otherwise leak data to a server, or tell it when the reply was read). Links open in the default browser on click, http and https only (step 12); a link's text can differ from where it goes, as on any web page. (Both from the automated security review in step 4. Since step 13 diffs are no longer put into markdown, so the fence that guarded them is gone.)
- Moving a chat (step 22) writes in Claude's own data: a copy of the session's transcript goes into `~/.claude/projects/<new folder>/` (mode 0600) for the length of the fork, then is removed; Claude writes the fork there. Nushi refuses session ids with path separators and never replaces a transcript already there; the original is only read.
- Worktrees (steps 30–32) run `git worktree add/remove/prune`, `git branch -D` and `git status`/`rev-list` in the chat's repository, as you. `git worktree remove --force` and `git branch -D` past unmerged commits run only when the Delete request says to force, which the app sends only after showing what would be lost; the daemon checks again before acting. The base branch a client sends to `GetDiff`/`GetFolderStatus` is refused if it starts with `-`, so it can't become a git option.
- Commits (step 43): `GetDiff` with `commit`/`since` and `ListCommits` run `git diff`, `git show`, `git log` and `git rev-parse` on the names the client sends; a name starting with `-` is refused so it can't become an option, as for the base. They read; nothing in the Changes view writes to git ([ADR 0019](docs/adr/0019-changes-read-only-toward-git.md)).
- Review comments (step 45) go to the agent as an ordinary prompt the user sends; they quote the file's lines as the diff showed them.
- The client token (`token`, mode 0600) sits next to the socket in a 0700 folder; any process running as you can read it ([ADR 0005](docs/adr/0005-clients-authenticate.md)).
