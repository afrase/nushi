**Noise patterns, and why**: IK because the phone has the daemon's key from the QR code, so it's pinned from the first message and a relay can't swap it, the phone's own key travels encrypted (the relay can't tell devices apart), and it's one round trip with forward secrecy. `psk1` binds the QR code's one-time secret into the first message, so the daemon rejects a phone without it before answering and keeps waiting for the right one. Not XX (sends a key the phone already has, one more message) and not KK (a device id would go in the clear). ADR 0034 has the full reasoning and the threat model.

**What the relay sees**: both ends' IP addresses, the rendezvous ids and the listen keys' public halves (the daemon's long-lived id links all its phone connections, until a revoke moves it), connection and message timing and sizes, how many connections a daemon has. ## Agent facts (claude-agent-acp 0.94.0; Claude Code 2.1.303, then yours, 2.1.310)

Until milestone Z the adapter ran the Agent SDK's own Claude Code, 2.1.303 (the facts below were seen with it; this file said 2.1.308–309, the terminal's `claude` of the time, which ran only `claude mcp`). Since then it runs yours (`CLAUDE_CODE_EXECUTABLE`): 2.1.310, tried by hand in milestone Z (a turn with a command, a reopen after a daemon restart). `claude.Tested` lists both; a failed start with another version says so.

What the code depends on, and how the adapter behaves. Everything Nushi does about it is in `internal/claude*`.

**Sessions**
- `session/new` requires `mcpServers`: send `[]`, never `null`. Claude starts a session in the mode its settings say; it reports modes both as legacy `modes` and as a `mode` config option (Nushi shows only the option). Config options: `mode` (Manual, Accept edits, Plan, Auto, Bypass permissions), `model` (Default, Opus 5.5, Fable 5.1, Sonnet 5.5, Haiku 5.5), `effort` (category `thought_level`), `fast` (category `model_config`, a select), `agent` (no category). `set_config_option` answers with the full set.
- Claude names a session itself soon after the first prompt (`session_info_update`); until then Nushi uses the prompt's first line. A fork is titled "<title> (fork)", a fork of a fork "(fork) (fork)": ignored, so a moved or rewound chat keeps its title. Asking `/context` before the first message makes Claude name the chat after it, so it isn't asked then.
- Claude keeps a session on disk only once it has a message: `session/load` of an empty one fails, and Nushi then starts a new one. `session/load` replays the user's and agent's messages and the tool calls (final status and output, `messageId`s included), not permission prompts or questions; a cancelled turn replays as "[Request interrupted by user]". It sends no `usage_update`. Loading takes under a second. A loaded session is on Claude's default model and effort, not the ones picked before (Haiku came back as Opus 5.5).
- Claude's history folder for a session is named after its cwd: the real path (symlinks resolved, `/tmp` is `/private/tmp`), NFC, every UTF-16 unit that isn't an ASCII letter or digit replaced by `-`; past 200 characters cut, with a base-36 hash of the path. `CLAUDE_CONFIG_DIR` moves the projects folder.
- `sessionCapabilities`: `fork`, `close`, `resume`, `list`, `delete`. `session/fork` copies the transcript into a new session on the same process (updates come tagged with the fork's id); with another `cwd` it fails, since it looks for the source only in the new folder's history, so a move copies the transcript there first ([ADR 0014](docs/adr/0014-moving-a-chat-forks-it.md)). After a fork the reported cost starts again near zero.
- Forking at a message: `_meta.jetbrains.air.fork = {version: 1, messageId}` on `session/fork` keeps the conversation up to that agent message, it included, for any client, after `session/load` too ([ADR 0020](docs/adr/0020-rewind-through-a-vendor-fork.md)). The adapter is recognized by `agentInfo.name` `@agentclientprotocol/claude-agent-acp`.
- `session/delete` (for clients that aren't AIR, which get archiving) deletes `<id>.jsonl` and `<id>/` in whichever project folder has them, succeeds for a session never written, and leaves the history folder behind. Deleting a session the process has open, or closing it, makes Claude write a ~700-byte stub back as it ends; a second delete a few seconds later removes it. So side chats ended other than by closing them are deleted by a fresh agent once the one they ran on has stopped.

**Updates**
- Every `agent_message_chunk` has a `messageId`; chunks group by it. Claude sends no `agent_thought_chunk`s here (thinking is "omitted" for recent models).
- A tool call arrives as a `tool_call` with a generic title and empty `rawInput`, then `tool_call_update`s with the real title, `locations` and content; each update's content replaces the last. A command's first content is its description, the last its output in a fence; a failed command's output starts with `Exit code N`. An `Edit`'s diff holds the snippet, not the file. One update carries only `_meta.claudeCode.toolResponse`. Claude searches and lists with `Bash`, not Grep and Glob.
- Plans (`plan` updates, the full list each time) come only when Claude's todo tools are on (`CLAUDE_CODE_ENABLE_TODO_TOOLS=1` in its environment); Nushi doesn't set it.
- `available_commands_update` (about 80 commands, plugins' and skills' too) comes after `session/new` and `session/load`. A command is an ordinary prompt starting with `/name`; a `resource_link` to a `file://` URI makes Claude read the file.
- Usage: each turn ends with two `usage_update`s, `{used, size}` and the same with `cost` (USD, the session's so far; not reliable across processes). One carried `_meta._claude/rateLimit`. The prompt result's unstable `usage` sums the turn's model calls.
- `session/cancel` ends the turn in a second or two with `cancelled`; streamed text stays. A command Claude ran in the background can finish later and Claude writes on its own, outside any turn.
- A cancel kills the background subagents too (and the commands they started: their output files end "[killed]"), and no update says so, unless the session's `_meta.claudeCode.options.perTaskStopAffordance` is true (on `session/new`, `load`, `fork`: the adapter passes `claudeCode.options` to Claude Code as host options). Claude Code 2.1.310's own description of the option: a host that renders a per-task stop control declares it, and "an interrupt … spares running background agents/workflows (Stop only aborts the turn)"; "ABSENCE also fails closed: the interrupt kills background tasks, since the user would otherwise have no way to stop a runaway one". Claude Code's terminal has that stop (its task list), so Esc there spares them. Nushi declares it since step 226: a cancel then leaves a background subagent running, it reports, and Claude answers the report on its own. The per-task stop the option promises, `_session/async_task/stop {sessionId, asyncTaskId}`, answers `{stopped: false}` for a client that isn't AIR (its tasks are never "announced"); Claude's deferred `TaskStop` tool stops one when asked.
- Background subagents hold the turn (claude-agent-acp 0.94.0, `Turn.deferredSettle`, for v1 clients only: a v2 client is told "idle" instead): when the turn's model work ends (its result) while subagents the turn started run in the background, the adapter keeps `session/prompt` unanswered until they have ended and Claude has answered their reports, so that their permission requests land inside a turn. Seen: a reply at 10:24:29, `end_turn` at 10:26:09 after the subagent's `sleep 90`. The turn's result is the `usage_update` with `cost` and `_meta._claude/origin {kind: "human"}`; a subagent's report is answered under `{kind: "peer", from: <agentId>, name, body: "[Subagent hand-back] …"}`, then the task notification `{kind: "task-notification", producer: "session-task"}`, and the held prompt is answered between the two. Asked to wait for its subagent, Claude does the same (no tool call waits: it ends its turn saying it will report when the subagent does). While the turn is held: a new `session/prompt` answers the held one at once (`end_turn`) and is answered itself at once, the subagent running on (the user "moving on outranks the hold"); `_session/steering` is `injected` and answered at once, but the prompt stays held; `session/cancel` answers it `cancelled`. After a steered message, the result of the work it cut short comes too (cost, `human`), before the steered work's own. Nushi treats the held turn as over at its result (step 226).
- Permissions: in Manual mode Claude asks with "Yes" (`allow_once`) and "No" (`reject_once`); the request names the tool call sent just before. `.claude/settings.json` = `{"permissions":{"defaultMode":"default"}}` starts a folder in Manual mode, for testing.
- Questions (AskUserQuestion) need `elicitation.form` in the client capabilities: a `tool_call` ("Asking for your input"), then `elicitation/create` in form mode tied to it. Each question is `question_N`, a `string` with `oneOf` or an `array` with `items.anyOf`, followed by an optional free-text `question_N_custom` titled "Other"; nothing is `required`, and the properties must be read in wire order. An empty accept reads to Claude as "no answer".
- Subagents: with `_meta: {"subagent-transcript": true}` in `initialize`'s client capabilities, a subagent's tool calls, text and thinking all carry `_meta.claudeCode.parentToolUseId` (tool calls also `toolName`); the Agent call's `subagent_type` is in its `rawInput`, maybe in a later update. Background subagents: the Agent call completes at once with "Async agent launched…", and the subagent ends with a `SubagentHandback` call whose `rawInput.message` is its report (its own output is only an acknowledgement). After `session/load` the Agent calls come back, but not a background subagent's steps or report. Messaging one: `SendMessage`'s `rawInput.to` is the subagent's `agentId`.
- Subagents (Claude Code 2.1.303): foreground subagents end with a `SubagentHandback` too, and their Agent call's output is then only a pointer ("This agent's report was delivered to you as a message from \"<agentId>\" (its SubagentHandback call)…"). The Agent call's `rawInput` comes in pieces over several `tool_call_update`s: `description`, `subagent_type`, `model` (`sonnet`, `haiku`, `opus`: the model option's values), `effort` (`low`…: the effort option's values), `prompt`, `run_in_background`; `model` and `effort` only when Claude picks them. The call's last update carries `_meta.claudeCode.toolResponse` with `agentId`, `agentType`, `resolvedModel` (`claude-sonnet-5-5`: the model it ran on, even when inherited), `totalDurationMs`, `totalTokens`, `totalToolUseCount`, `usage`, `handbackReport.text`; no effort. The subagent's own updates carry only `parentToolUseId` and `toolName`, no model. `session/load` replays the Agent call with its whole `rawInput` but no `toolResponse`, and no subagent's steps or report, foreground ones included. `async_task_*` updates go only to AIR clients; the ACP subagents RFD form (child sessions) only to clients that advertise `subagents` (see Later ideas).
- Background shells (what a client that isn't AIR sees): a Bash call with `rawInput.run_in_background: true` completes at once; its last update's `_meta.claudeCode.toolResponse.backgroundTaskId` is the task's id and its output text says "Command running in background with ID: <id>. Output is being written to: <tmp>/claude-<uid>/<project>/<session>/tasks/<id>.output. You will be notified when it completes. To check interim output, use Read on that file path." That file fills as the command writes and ends with "[exited with code N]" or "[killed]". Claude 2.1.303 has no BashOutput (it said so, and reads the file with Read); stopping is the deferred `TaskStop` (found through `ToolSearch`), input `{task_id}`, response `{message, task_id, task_type: "local_bash", command}`. When a command ends, Claude gets a task notification the client never sees; Claude then runs a turn of its own, whose last `usage_update` has `_meta._claude/origin = {kind: "task-notification", producer: "session-task", runId}`, naming no task. `async_task_*` updates and the `_meta.jetbrains.air` `backgrounded` marker go only to AIR clients. A client that sets `_meta.terminal_output: true` in its capabilities gets Zed's terminal extension instead: every Bash call's output moves to `_meta.terminal_output` (content becomes a terminal reference), and a background command's `terminal_exit` (exit code null) comes when its task ends; Nushi doesn't use it, since it would change how every command reads. Background commands outlive Claude: after the daemon stopped (and Claude with it), `sleep 300` still ran, and its file never got an end line.
- Messaging a subagent: claude-agent-acp 0.94.0's child sessions (the RFD form) take only `cancel`; a v1 client has no way to prompt one. Claude Code 2.1.303's deferred `SendMessage` tool (`{to: <agentId>, message, summary, type: "message"}`) reaches a subagent by the id the Agent call's result gives (a background call's output ends "agentId: <id>"; a foreground one's names it in its pointer to the report; `toolResponse.agentId` too). It answers `{success, message: "Resuming agent …", resumedAgentId}`: a finished subagent runs again under its first Agent call (its steps carry that call's `parentToolUseId`) and ends with another `SubagentHandback`; a running one takes the message as it goes. Tried five times (three finished, one running, one finished after a daemon restart): Claude passed the text verbatim each time and the subagent acted on it; Claude then relays the reply in its own words, sometimes adding its own checks.
- Steering: `initialize`'s top-level `_meta.steering.supported` (not `agentCapabilities._meta`, which has `claudeCode.promptQueueing`) advertises `_session/steering`, answered `injected` while a turn runs or `promptRequired` (doing nothing). An injected message pre-empts the model and moves a foreground tool to the background, so Nushi steers right after a tool call ends; the running prompt ends once the steered messages are answered; the adapter echoes nothing.
- `/context` is answered by the adapter itself (no model call, no cost), as agent text, twice (two message ids, the same markdown): "Context Usage", then an "Estimated usage by category" table (System prompt, System tools, MCP tools, MCP server instructions, MCP tools (deferred), System tools (deferred), Custom agents, Memory files, Skills, Messages, Free space, Autocompact buffer; counts like `2.5k`, `934.6k`), then more tables. Claude keeps the answer in the conversation (5–7k tokens each time), so it runs in a throwaway fork (about 1.3 s; same numbers within 0.2k). It isn't replayed.
- The adapter logs progress on stderr; nushid copies it into its log.

## Agent facts (Ante 0.2.14, through the bridge)

What the bridge (`internal/ante`) depends on, seen with `ante serve --stdio`; the protocol is Ante's open `crates/protocol-shape/src/msg.rs` at v0.2.14.
- Ops go in as `{"op": …, "id": "op_<ULID>"}` (a bad id is an `Error`); events come out with `parent`, the op they answer. An input's op id is its turn's id. No greeting.
- `StartSession{cwd}` answers `SessionStart` (session id, cwd, permission mode, model with `effort` and maybe `supported_efforts`, provider); unset fields come from `~/.ante/settings.json` (the user's default model, Kimi K3 here). `ResumeSession` answers `SessionEnd` (of any running one), `SessionStart`, `ExtensionRefreshed`, then the saved event log, with no end marker: the bridge sends `ContextReport` right behind it and takes its answer as the end (the host answers ops in order). Permission mode always comes from the current settings on a resume; the model is the session's.
- Live, the host echoes every input as `UserInput` (steers too, which the docs say it doesn't); streams `MessageDelta`/`ThinkingDelta`, then repeats the whole text (dropped once deltas came; replays have only the whole texts). A turn can hold several `AgentMessage`s; the bridge names them `<turn id>.<n>`.
- An approval (`TurnPause.Approval`) comes before the call's `ToolStart`; a denied call ends with a `ToolEnd{Denied}` and no start. `AcceptAlways` would write an allow rule into `settings.json`, so the bridge never offers it. Questions are `TurnPause.Question` (AskUser), answered with `QuestionResponse`.

## Agent facts (PiG 0.5.3, through the bridge)

What the bridge (`internal/pig`) depends on, from driving `pig --mode rpc` (the darwin-arm64 release, checked against its `SHA256SUMS`, in a temp `HOME`) and from PiG's source and bundled docs (`pig docs`; `coding/cli/rpc_*.go`). RPC mode is Pi 1.4.0's protocol.
- `pig --version` prints `0.5.3+1.4.0.74f46864` (PiG, then the Pi it ports and Pi's commit) and writes nothing. Install: `curl -fsSL https://pi-in-go.dev/install.sh | sh`, `npm i -g @pi-in-go/pig`, or a GitHub release.
- Framing: a command per line, with an `id` the response repeats (`{"type":"response","id","command","success","data"|"error"}`); events carry no id. Responses can come out of order. A line that isn't JSON answers `"command":"parse"` without an id; an unknown command `success:false`. Closing stdin ends RPC mode after it cancels what runs.
- `prompt` (`message`, `images: [{type:"image", data, mimeType}]`) answers once accepted, before the run: `disposition` `started`, or `handled` when an extension's command took it (the answer comes after the command ends, its dialogs included). A run ends with `agent_settled {aborted}`; several `agent_end`s can come before it (retries, compaction). A second prompt during a run is refused without `streamingBehavior`.
- Events: `message_start` (an assistant message has its `timestamp` and `responseId` from the start), `message_update` (`assistantMessageEvent`: `text_delta`, `thinking_delta`, `toolcall_start/delta/end` with the call in `toolCall` or `partial.content[contentIndex]`), `message_end` (the final message: `usage`, `stopReason` `stop`/`length`/`toolUse`/`error`/`aborted`, `errorMessage`); `tool_execution_start {toolCallId, toolName, args}`, `_update {partialResult}` (a command's output so far), `_end {result: {content, details|structuredContent}, isError, durationMs}`; `queue_update`, `session_info_changed {name}`, `thinking_level_changed`, `compaction_*`, `auto_retry_*`, `extension_ui_request`, `extension_error`. A message's `timestamp` is the one in the session file; no event carries a message's entry id.
- Tools: `read {path, offset, limit}`, `bash {command, timeout}`, `edit {path, edits: [{oldText, newText}]}` (its result's `details.patch`), `write {path, content}`, `grep`, `find`, `ls`; extensions and MCP servers add theirs. Calls in one message run at once (an edit and a write started together). **No permission prompts and no modes**: every call runs without asking (only an extension can block one).
- `abort` (answers after the run settled): a running command ends "Command aborted" (failed), a queued steer comes in as a user message and the next model call ends `stopReason: "error"`, "This operation was aborted". `steer` queues a message "after the current tool batch and before the next model call" (`disposition: queued`); it comes back as a user message's events.
- Models: `get_available_models` lists every model PiG has a key for (`FIREWORKS_API_KEY`: Fireworks' 24, `fireworks/accounts/fireworks/models/…`); `set_model {provider, modelId}`. Thinking levels are the model's (`get_available_thinking_levels`: DeepSeek V4.1 Flash off, low, high, max). The session keeps both (`model_change`, `thinking_level_change` entries), so a reload is on the model it had. A new session starts on `defaultProvider`/`defaultModel`/`defaultThinkingLevel` from `<agent dir>/settings.json`, else (Fireworks) Kimi K3.
- `get_session_stats`: `contextUsage {tokens (null right after a compaction, until the model answers again), contextWindow, percent}`, `cost` (USD, the session's, compactions' summaries included), `tokens {input, output, cacheRead, cacheWrite, total}` (the session's), `userMessages`, `assistantMessages`, `toolCalls`, `toolResults`, `totalMessages`. No breakdown of the context, and no count of compactions (the bridge counts the branch's `compaction` entries).
- `get_commands`: extensions' commands, prompt templates and skills (`/skill:<name>`); a prompt `/name args` runs or expands them. PiG's own slash commands (`/model`, `/compact`, `/name`, `/tree`, `/trust`…) are the terminal's: sent as a prompt they reach the model as text. RPC mode has commands for what some of them do (`set_model`, `compact`, `set_session_name`, `fork`); the bridge offers `/compact` and `/name` itself (below). Stock pig's built-in extensions: llama.cpp, codemode, tool-search, mcp, pig-login (`/llama`, `/mcp`, `/sprite`).
- Compaction: `compact {customInstructions?}` aborts a running prompt first, then answers once done: `{summary, firstKeptEntryId, tokensBefore, estimatedTokensAfter, usage?, details?}`, or `success:false` ("Nothing to compact (session too small)", "Already compacted", "Compaction cancelled" after an `abort`, which cancels it). Every compaction, asked for or PiG's own, is `compaction_start {reason: manual|threshold|overflow}` then `compaction_end {reason, result?, aborted, willRetry, errorMessage?}`, written before the command's answer; PiG's own come inside a run, before `agent_settled` (one can come before the model call, when the context is already past the line). The session gets a `compaction` entry (`summary`, `firstKeptEntryId`, `tokensBefore`, `details {readFiles, modifiedFiles}`); the summary is markdown with fixed sections and ends with `<read-files>`/`<modified-files>` lists.
- **Automatic compaction is on by default** (`compaction.enabled: true`): when the context passes the window minus `compaction.reserveTokens` (16,384), keeping the last `keepRecentTokens` (20,000) whole; per-model overrides in `compaction.modelOverrides`. `set_auto_compaction` writes `compaction.enabled` to PiG's global settings, not the session's; each pig reads its settings when it starts.
- `set_session_name {name}` writes a `session_info` entry and `session_info_changed {name}` before its answer.
- Plans: PiG has no todo tool. Pi's todo extension (in PiG's bundled examples) keeps its list in its tool's result `details.todos [{id, text, done}]`, which RPC mode passes whole in `tool_execution_end` and the session's tool result message; its plan-mode extension in an entry of its own (`appendEntry`: `entry_appended {entry: {type: "custom", customType, data: {todos: [{step, text, completed}]}}}`) and a widget's text lines.
- Extensions' dialogs: `extension_ui_request` `select {title, options}`, `confirm {title, message}`, `input {title, placeholder}`, `editor {title, prefill}`, each with an optional `timeout` (ms, after which it answers itself), answered by `extension_ui_response {id, value | confirmed | cancelled}`; `notify {message, notifyType}`, `setStatus`, `setWidget`, `setTitle`, `set_editor_text` want no answer. **PiG 0.5.3's `/sprite`, answered, hangs pig in RPC mode** (it stops answering anything, `abort` and `get_state` too, until stdin closes); an extension of ours (a Node `select`, `confirm`, `input`, and a tool that asks) worked.
- Sessions: `<agent dir>/sessions/--<cwd, / as ->--/<time>_<uuid v7>.jsonl` (the agent folder `~/.pig/agent`, or `$PIG_CODING_AGENT_DIR`, `$PIG_HOME/agent`, `$XDG_CONFIG_HOME/pig/agent`; `$PIG_CODING_AGENT_SESSION_DIR` or the settings' `sessionDir` move the sessions; files 0644, folders 0700). A header line `{type:"session", version:3, id, timestamp, cwd, parentSession?}`, then entries `{type, id, parentId, timestamp, …}` making a tree; the leaf is the last appended. A new session's file is written with its first message: a session whose prompts were only extensions' commands has none.
- `--session <file>` opens a session (pig moves to the header's cwd; a gone folder is an error); an id found only in another folder's sessions makes pig ask on stdin "Fork this session into current directory? [y/N]", so the bridge passes the file. Opening appends nothing (unless an old file migrates or the branch has no thinking level entry). `get_entries` answers every entry of every branch and `leafId`.
- `fork {entryId}` (a user message's) and `clone` switch the process to a new session: the branch before that message, or all of it, entry ids kept, header `parentSession` = the source's path, written at once when it holds a message; the source isn't changed. A fork at the first message is an empty session.
- Two writers: PiG takes no lock or owner file (each entry is appended by an open, write, close). Nushi and a terminal `pig -p --session` on one session each appended to their own branch; a later resume followed the last writer's.
- Delete in PiG's `/resume` runs `trash <file>`, else unlinks.
- Trust: RPC mode can't ask; a folder's `.pig/{settings.json, mcp.json, extensions, skills, prompts, themes, SYSTEM.md, APPEND_SYSTEM.md}` and `.agents/skills` load only with a decision in `<agent dir>/trust.json` (`{"<canonical path>": true|false}`, the nearest ancestor's), `defaultProjectTrust: "always"` in the user's settings, or `--approve` (checked: a project prompt template loaded only once `trust.json` said true). Regardless of trust: `AGENTS.md`/`CLAUDE.md` from the folder up to `/` and the agent folder, the project `sessionDir`, and a migration that renames a project's `.pig/commands` to `.pig/prompts`.
- MCP: `<agent dir>/mcp.json` and a trusted folder's `.pig/mcp.json` (`{"mcpServers": {…}}`); the built-in mcp extension connects them in RPC mode too; `pig mcp list --json` starts every server to check it.
- An extension that fails to load stops pig at start ("Error: Failed to load extension …: TypeScript extensions need Node.js 22.13 or newer"); the bridge's error then carries that line.

## GitHub facts (October 2026; the test repository afrase/nushi-gh-test)

- **Auth**: go-gh v2.17.0's `TokenForHost` reads `GH_TOKEN`/`GITHUB_TOKEN` (github.com, `*.ghe.com`, localhost) or `GH_ENTERPRISE_TOKEN`/`GITHUB_ENTERPRISE_TOKEN` (any other host), then gh's config, then runs `gh auth token --secure-storage --hostname <host>` (the token on its stdout). gh keeps its token in the keychain by default, so the last is the usual path; it runs once a host while the daemon runs. `KnownHosts` is gh's hosts (and `GH_HOST`). gh's token here is an OAuth token (`gho_`) with `gist, read:org, repo, workflow`; `/user`'s `X-OAuth-Scopes` says so. A fine-grained token sends no scopes.
- **Rate limits**: every answer has `X-Ratelimit-Limit`, `-Remaining`, `-Reset` and `-Resource` (`core`, `graphql`, `search`…); `/rate_limit` costs nothing. A spent primary limit is 403 or 429 with `X-Ratelimit-Remaining: 0`; a secondary one has `Retry-After`; a GraphQL one is a 200 with an error of type `RATE_LIMITED`. A 304 to `If-None-Match` costs nothing. Points: the inbox query about 2, a pull request whole about 2 (its threads' 50 comments each make most of it), states 1, a blobs batch 1.
- **GraphQL**: a document may hold only the fragments it uses; one field can't be asked twice with different arguments (alias one: `commentCount: comments { totalCount }`). `review-requested:@me` is me or a team of mine (`user-review-requested:@me` me only). A pull request's `reviewThreads` give `isResolved`, `isOutdated`, `diffSide`, `line`/`startLine` (an outdated thread's `line` is null: `originalLine`), `subjectType`, and `viewerCanReply/Resolve/Unresolve`; `startLine` equals `line` for a one-line thread. `latestReviews` and `reviewRequests` give reviewers and their states; `reviews(states: PENDING)` only ever shows my own pending review. A check run's `databaseId` is its Actions job's id; a status context's `targetUrl` and a check run's `detailsUrl` are whatever posted them.
- **Writes**: `addPullRequestReview` with `event` and `threads` creates and submits a review in one mutation; into a pending review, `addPullRequestReviewThread` then `submitPullRequestReview`. GitHub refuses an approval or a request for changes of one's own pull request ("Can not approve your own pull request") and a thread on a line outside the diff ("Line could not be resolved"). `addPullRequestReviewThreadReply`, `resolveReviewThread`, `unresolveReviewThread`, `addComment` (a pull request's or an issue's node id).
- **REST**: `GET /repos/{o}/{r}/actions/jobs/{id}/logs` answers 302 to a link good for a minute on another host (fetched without the token); the log starts with a byte order mark and each line with a timestamp. `GET /repos/{o}/{r}/compare/{base}...{head}?per_page=1` gives `merge_base_commit` and up to 300 files with `previous_filename`. Nushi sends `X-GitHub-Api-Version: 2022-11-28` (GitHub's default, supported until 2028-03-10).
- **Text as GitHub shows it** (its anonymous `POST /markdown`, mode gfm, on 54 tricky texts in `internal/githubapi/testdata/markdown_github.json`): HTML comments vanish, and one never closed hides the rest; GFM's tag filter writes `<script>`, `<style>`, `<textarea>`, `<title>`, `<xmp>`, `<iframe>`, `<noembed>`, `<noframes>`, `<plaintext>` as text; other tags its sanitizer doesn't keep (`<template>`, `<svg>`, `<math>`, `<select>`, `<object>`, `<noscript>` parsed with scripting off) are unwrapped, their text shown (CDATA in `<svg>` too); `hidden` and `style` attributes go, so their text shows; link reference definitions and a table's cells past the header's don't show; images go through camo (`camo.githubusercontent.com`) with `data-canonical-src`.
- **Checking out a pull request**: a branch of the base repository is `refs/heads/<head>`; a fork's head is the base repository's `refs/pull/<n>/head`, which anyone can fetch and nobody can push to. The Actions of a public repository run on pushes and pull requests both, so a pull request's head has each check twice.

## What Nushi changes outside its data folder (milestone Z)

Everything else Nushi writes is in its data folder (`~/Library/Application Support/Nushi`, or `NUSHI_DATA`): chats, settings (`app.json`), trust answers (`trusted.json`), remote keys, the log, scratch chats' folders, and the adapters (`agents/`). Outside it, each change is one you ask for, or the agent's own doing while you use it:

| Claude's MCP servers | `~/.claude.json`, through `claude mcp add-json/remove/login/logout` | The MCP view's Add, Edit, Remove, Sign in and out. |

## Security notes to look at

- GitHub (ADRs 0045, 0046): a host's token is gh's (read through go-gh in the daemon, which may run `gh auth token`; the token is on its stdout, never an argument) or a pasted one in the login keychain ("Nushi GitHub"); it's in the daemon's memory while it runs and goes only in the `Authorization` header of requests to its own host, never to a job log's link (another host). A host must be github.com, gh's, or given a token before any token is read for it: go-gh gives `GH_ENTERPRISE_TOKEN` for any host. Agents get the daemon's environment (ADR 0028): a `GH_TOKEN` in your shell reaches them as it would a terminal's; Nushi adds none. GitHub's text (anyone's who can comment) is rendered as GitHub renders it, parsed as a browser does, and written back from what GitHub's sanitizer keeps; tested against GitHub's own renderer and fuzzed (no hidden comment's text comes out, no word GitHub's page doesn't show, no link but http, https and mailto, no image but http and https). Addresses from GitHub (checks', statuses', items', comments') leave the daemon only when http or https; the app's `webLink` checks again before opening. In a message for an agent, GitHub's text is only between two lines with a random mark, said to be data; authors outside the repository are marked. The API's own line for a failed call quotes GitHub's error message (it names what failed, not what was sent, in every case seen).

- Jira (ADRs 0042, 0043): the API token is in the login keychain under "Nushi Jira", readable by the daemon's build that stored it, and by a later build only after your OK in macOS's prompt; another program asking gets the prompt (`security find-generic-password -w` included), though any program of yours can delete the item without one. The token goes to the site (or Atlassian's gateway) over HTTPS through the system's proxy, as Basic auth; it's in the daemon's memory while it runs. An issue's text is anyone's who can edit it: it's rendered as escaped Markdown (fuzzed), links only http, https and mailto, images only the issue's attachments fetched by the daemon. A chat's tools key (in its MCP server's environment, and on Claude Code's command line, so in `ps`) grants that chat's issue's four tools while the daemon runs; the tools server takes neither the client token nor anything else. What an agent writes through them is its harness's to allow.
- govulncheck (step 180, `make lint`) reports one advisory with no fix: GO-2026-5932, `golang.org/x/crypto/openpgp` is unmaintained and unsafe by design. Only a module-level finding: Nushi requires `golang.org/x/crypto` for the relay's autocert and the Noise channel and never imports `openpgp`, so nothing calls it and `make lint` passes; the advisory stays until x/crypto drops the package.
- PiG (ADR 0039) runs as you: your `pig` (found on the login shell's `PATH`), one `pig --mode rpc` per chat in its folder, through `nushid pig-acp`. **It runs every tool call without asking**: there is no mode or permission prompt to show. A folder's `.pig` (settings, MCP servers, extensions, prompts, skills) loads only when you trusted it in PiG; `AGENTS.md`/`CLAUDE.md` load regardless, as instructions. The bridge reads PiG's session files (headers, names, first messages) and moves a session's file to the Trash only for an id whose header it found in PiG's sessions folder. A write's old text, for its diff, is read from a regular file of at most 1 MB without following a link (`internal/toolcall`, shared with Ante's bridge).
- The log (ADR 0038): what an agent writes to stderr is logged, through a redaction pass for known secret shapes; an agent that echoes a prompt or a key of another shape to stderr puts it in `nushid.log` (in the 0700 data folder; the file itself is 0644 when the launcher's `>>` created it, 0600 when the daemon did). The client token is masked by value. `Log` lets any client with the token, or a paired device, add lines (capped: 2 KB a message, 16 KB a stack, 16 attributes); `\n` and quotes are escaped, so a line can't pose as another.
- The daemon's helper (ADR 0036): `start-daemon` (the launch agent's program) is a script sealed as a resource of the app's signature, not code of its own, so launchd doesn't pin it to a hash; it runs only `open` on the helper beside it. Turning Start at login on adds a background item macOS lists under Login Items.
- Sessions started elsewhere (ADR 0035): listing starts the agent and reads, never writes: Claude's `~/.claude/sessions/*.json` and the first records of transcripts under `~/.claude/projects`, Codex rollouts' first lines and lock files, omp session headers and lock files (F_GETLK on a file opened read-only; no lock is taken), Ante's `meta.json`, and `lsof -F n -- <events.jsonl…>` for Ante. Opening runs the agent in the session's folder after the trust card, as a new chat. A paired phone can list and open too (a full client).
- Remote access (ADRs 0033, 0034; the review ran on it during milestone V): the daemon's Noise private key is in `remote-key.json` (0600) beside the token, readable by any process of yours, the agent included (as ADR 0024 says of the token). A paired phone is a full client: chats, permission answers, terminals, MCP changes; not the Mac's calls (SetRemote, StartPairing, ConfirmPairing, RevokeDevice: "permission denied" on a channel). The remote API server has no token check: the handshake authenticated the device. The Mac app asks Allow or Deny for any pairing that reaches its code, whoever started it. The pairing code is the only thing that stops someone who saw the QR code within its 5 minutes; the Mac's dialog says to allow only if the phone shows the same code. The PAC file is fetched directly and evaluated by CFNetwork in osascript, asked only scheme://host:port/.

- Codex runs as you: your `codex`, through `@agentclientprotocol/codex-acp` 2.2.2, set up like Claude's adapter. codex-acp tells Codex to trust every session's cwd, so a folder's `.codex/config.toml` (MCP servers, the environment of every command, sandbox settings, plugins) and rules load without Codex asking; Nushi's card is the only warning (ADR 0029). The card's key is a hash of every file it showed, computed with the card and checked again on "Start anyway"; links aren't followed. Codex's trust record is read, never written. Agents get the login shell's environment, secrets included (ADR 0028).
- Ante runs as you through the bridge, `nushid ante-acp`, which starts `ante serve --stdio` (the `ante` on `PATH` or in `~/.ante/bin`, 0.2.14 or newer) in the chat's folder. The bridge never reads Ante's settings; it reads `ante catalog` (models only) and each session's `meta.json`, and removes a session's folder only for an id of Ante's form (`ses_` and a ULID). A Write's old text, for its diff, is read only from a regular file of at most 1 MB, without following a link. Prompt images go to a private temp folder the bridge removes when it ends. The trust card shows the nearest `.ante/settings.json` (ADR 0031).
- omp runs as you (your `omp` under your Bun) and loads a project's extensions, hooks, tools, command modules and LSP servers without asking; the trust card shows each such file whole (ADR 0031). Its bash asks first; its writes don't.
- Codex snapshots the shell environment of each thread into `$CODEX_HOME/shell_snapshots/<thread>.sh`, secrets included (`FIREWORKS_API_KEY` was in the test home's), mode 0644. That's Codex's own feature (ADR 0028 gives agents the login shell's environment); your `~/.codex` would get the same.
- Memory: `GetMemory` reads the footprint of the daemon's process trees, and of the process tree a client names (`app_pid`, any process of yours), for any client with the token: sizes only.
- Agents run as you: Claude and Codex as your own CLIs (found on the login shell's PATH) under their adapters, which Set up installs into `<data>/agents/<agent>` with `npm ci` from the lockfiles in `internal/<agent>/adapter` (every package pinned by version and sha512; no install scripts; no optional packages; npm under `sandbox-exec`, writes allowed only in `agents/`; your npm settings apply, so a registry you name there is where the packages come from, checked against the lockfile's hashes). The adapter runs as `node <its program>` in the data folder, so a project's `node_modules` or `.npmrc` can't swap it; the Node is the first on PATH. A chat's folder reaches the agent only as `cwd`. Finding agents runs each CLI's `--version` (and `claude auth status`) under `sandbox-exec` with writes and the network denied (ADR 0037).
- A panic on something the agent sent becomes a JSON-RPC error; a malformed form is refused.
- `ListFiles` lists any absolute folder a client names (names, 20,000 at most); mentioned files go to the agent as `file://` links.
- Git runs as you in the folder a client names: `core.fsmonitor` off, `--no-ext-diff`/`--no-textconv`, hooks off (`core.hooksPath=/dev/null`), signature checks off, no lazy fetch of a partial clone's missing objects (`GIT_NO_LAZY_FETCH=1`: the fetch would run the transport the repository's config names), no status inside submodules or nested repositories (`--ignore-submodules=dirty`, which would run their filters), the panel's status without the repository's own filter drivers; Changes and new worktrees still run them (git-crypt, lfs). Nushi writes into a repository only `.worktrees/` and `info/exclude`, never through a link there. Files are read only when regular, and at most 1 MB of each (64 MiB for Claude's settings and `.mcp.json`). Names starting with `-` are refused as bases and commits. Worktree removal and `branch -D` force only when the request says so, which the app sends only after showing what would be lost; the daemon checks again.
- Agent markdown: local images only from regular files of 20 MB at most, remote ones after a click; links open http(s) only, in the browser.
- Moving a chat writes a copy of the transcript (0600) into Claude's projects folder for the fork, then removes it; never replaces one there.
- MCP: Claude's config holds secrets in clear; the daemon masks them before they leave it. It runs `claude mcp add-json/remove/login/logout` (names checked, `--`), so a client can add a server Claude runs as you, as a prompt could. The on/off switch writes the project's `.claude/settings.local.json` (its two MCP lists only, atomically, keeping its mode) and may add it to `.git/info/exclude`.
- Terminals: any client with the token can open a shell as you anywhere; they must stay off remote access ([ADR 0022](docs/adr/0022-the-daemon-owns-terminals.md)). Closing kills what has the terminal as its controlling terminal.
- Background shells: the daemon reads the output file a Bash call's output names (only a regular file, no link, named `<task id>.output` in a `tasks` folder; its last 64 KB), once a second while the command runs, and shows it in the app.
- Trust lists any string setting named like Claude's credential helpers (`…Helper`, `…AuthRefresh`, `…CredentialExport`), a skill's raw front matter whenever it has hooks (by text or by YAML key), and a `.mcp.json` it can't read or parse (each whole, or past 256 KB where it is): it fails closed. The MCP list leaves such a file out, as Claude does.
- Trust reads `~/.claude.json`, never writes it; "Start anyway" goes to Nushi's `trusted.json`. Trust of the home folder (or `/`) covers that folder only, never the folders under it, and `~/.claude` is never listed as the home folder's own.

## Working notes

- ACP is the library `github.com/afrase/acp-go` (ADR 0041). Changing it and Nushi at once: `go work init . ../acp-go` here (the `go.work` is ignored); `make lint` builds golangci-lint into `bin/` since `go tool -modfile` refuses a workspace. Before committing a version change, build once without it (`GOWORK=off make check`) to check Nushi against the tag in `go.mod`. A library fix is its own commit and release there, then `go get github.com/afrase/acp-go@vX.Y.Z` here.

- Lint exclusions (milestone AC). A report that's wrong for one line: `//nolint:<linter> // <why>` on that line, or on the function's line for one that covers it (contextcheck's mark on a function that rightly starts its own context stops the report spreading to its callers). nolintlint refuses a nolint without a linter and a reason, or one that silences nothing. Exclude by path in `.golangci.yml`'s `exclusions.rules` only where a whole package or kind of file is about what the linter reports (tests' temp files for gosec, the API's proto int32s), with a comment saying why; turn a linter off in `disable` only when it doesn't fit the code at all, with the reason on its line. Two conventions without a comment each: `_ = json.Unmarshal(…)` on an agent's payload is best-effort decoding (what it leaves out stays zero, which the code handles), and `defer f.Close() //nolint:errcheck // read-only`. Dart: `// ignore: <rule>` on the line below a comment saying why, `// ignore_for_file: <rule>` at a file's top when the whole file is about it (the marks' path data); a rule that doesn't fit the code at all goes `false` in the root `analysis_options.yaml` (or the app's, for the app only) with the reason above it. govulncheck: a finding in the standard library is fixed by raising the `go` line's patch version in `go.mod` and `tools/lint/go.mod`, a module's by `go get` of the fixed version; one with no fix goes under "Security notes to look at" with its advisory id.
- The icon (step 123): "the still lake" from the naming pass. `make icons` (`tools/icongen`) writes `app/macos/Runner/AppIcon.icon` (Icon Composer: a teal fill, the rings as a glass layer, the light and its glow above; macOS 26 and later draw it in Liquid Glass with dark, clear and tinted looks), the PNG set for older macOS (one ring at 16 and 32 px, thicker lines at 64), and `docs/brand/` (the icon and the bare mark for the README). `app/lib/logo.dart` draws the mark on the "Start a chat" pane. To see what macOS makes of a compiled icon, `NSWorkspace.shared.icon(forFile:)` on the built app; actool keeps a daemon, so a deleted working folder fails it until `pkill ibtoold`.
- A phone by hand, before the phone app: decode the app's QR code from a screenshot (a few lines of Swift with Vision's `VNDetectBarcodesRequest`) and pair from a Dart script on `packages/remote_transport`; a raw Connect call is a POST of `{}` with `content-type: application/json` on the transport's `makeRequest`.

- The Dock by hand (milestone Y): with the Dock hidden, `osascript -e 'tell application "System Events" to get name of every UI element of list 1 of application process "Dock"'` lists its items; `lsappinfo list` says why an app that quit still has one ("exited-with-subordinates", and the coalition). `launchctl print gui/$(id -u)/com.nushihq.Nushi.daemon` shows the login item's job; `/usr/bin/log` (not the shell's `log`) shows launchd's reasons when a job fails.
- Screenshots of the app window are current only while it's in front: macOS stops Flutter drawing an occluded window.
- To watch the fake agent in the app: build `internal/acptest/fakeagent`, put a `node` that execs it and a `claude` (any script) first on `PATH`, make Claude look set up (`<data>/agents/claude/node_modules/@agentclientprotocol/claude-agent-acp/package.json` with `{"version": "0.94.0", "bin": {"claude-agent-acp": "dist/index.js"}}`, as `app/test/remote_e2e_test.dart` does), and start a daemon with that `PATH` and `NUSHI_DATA` (a short path: the socket path has a length limit). Its scripts answer prompt words: `permission`, `question`, `think`, `pwd`, `many`, `plan`, `wait` (until stopped).
- Terminals: the shell is the user's login shell from `id -P` (the user database), never the daemon's `$SHELL`. fish 4 asks the terminal's Primary Device Attributes as it starts and waits 10 seconds for the answer; the app answers queries in a replay only for a terminal it opened itself (anyone attaching later would answer twice).
- Driving the app by hand: System Events' `click at` doesn't reach a Flutter window; a few lines of Swift posting `CGEvent` mouse and key events do. Typing: key codes (a unicode string on key code 0 isn't taken), with the flags set on every event (else a shift sticks), and a moment after the click that focuses the box; a window resizes by dragging its corner. Screenshots are 2× the window's points.
- App tests get a data folder in the temporary folder (`FLUTTER_TEST`); never point them at the real one.
- Ante and omp by hand: start the dev daemon with `ANTE_HOME` set and `HOME` at a temp folder (omp keeps everything under `~/.omp`), the key read from `fish -l -c` with the real `HOME`. Quit the dev app before stopping the dev daemon: an app that finds no daemon starts its bundled one through the login shell, with the real `HOME` and none of the dev daemon's environment.
- Agents in a terminal by hand (milestone X): a small pty driver (Python's `pty`) that answers the terminal's queries (cursor position, device attributes, colours) and types what's written to a FIFO runs the Codex and Ante TUIs; a FIFO write blocks once the driver is gone. Turn off Codex's update check first (`check_for_update_on_startup = false`): its prompt takes Enter and updates the global Codex. Claude's TUI stops at its trust prompt in a folder it doesn't know, and answering it writes `~/.claude.json`: use `claude -p` (and `-p --resume`) instead. Headless sessions: `codex exec`, `ante -p --permission-mode strict --session-save`, `omp -p`.
- Codex by hand: start the dev daemon with `CODEX_HOME` at a temp folder holding the config above, and `FIREWORKS_API_KEY` read from `fish -l -c` inside the launching script, never on a command line or in a file. `codex resume` in a pty needs answers to the terminal's colour and cursor queries.
